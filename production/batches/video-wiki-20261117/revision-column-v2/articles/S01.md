## 전투를 저장하는 두 가지 방법

경기가 끝난 뒤 방금 싸운 장면을 다시 본다고 해 봅시다. 화면 녹화와 게임 리플레이는 모두 과거를 보여 주지만, 보관하는 것은 다릅니다. 녹화는 이미 그려진 그림과 소리의 연속을 보관합니다. 카메라 밖에 있던 병력의 위치를 나중에 알아내거나, 그때 보지 않았던 곳으로 게임 카메라를 옮기는 일은 그 영상만으로 할 수 없습니다.

게임 리플레이는 그 장면을 다시 만들 자료를 보관하는 쪽입니다. 다만 “키보드 입력 몇 개만 있으면 어떤 게임이든 복원된다”는 뜻은 아닙니다. 시작 상태, 그때 사용한 규칙과 맵, 사건이 일어난 순서가 함께 맞아야 합니다. 게임에 따라 상태 기록이나 중간 저장점도 섞습니다. 이 글에서는 먼저 아주 작은 게임을 직접 복원해 보고, 그 방법이 커다란 전략 게임에서 왜 까다로워지는지 살펴봅니다.

## 화면보다 먼저 존재하는 ‘상태’

모눈종이 위에 병사 한 명이 있다고 합시다. 이 병사는 오른쪽으로 한 칸 이동하거나, 에너지가 남아 있을 때 사격할 수 있습니다. 컴퓨터가 기억할 최소한의 상태를 다음처럼 정합니다.

| 기억할 항목 | 예제의 시작값 | 필요한 이유 |
| --- | --- | --- |
| 병사의 위치 x | 0칸 | 다음 이동이 어디서 출발하는지 알아야 한다 |
| 남은 에너지 | 2 | 사격을 허용할지 판단한다 |
| 표적의 체력 | 3 | 명중 뒤 남은 체력을 계산한다 |
| 현재 틱 | 0 | 어느 명령을 지금 적용해야 하는지 정한다 |

이 값들을 모은 것이 Game State(게임 상태)입니다. 상태는 화면의 픽셀과 다릅니다. 병사의 옷 색이나 화면 해상도는 바꾸더라도 위치와 체력이 같으면 예제의 전투 규칙은 그대로 이어갈 수 있습니다. 반대로 같은 그림처럼 보여도 남은 에너지가 다르면 다음 사격의 결과가 달라집니다.

이제 시간을 작은 순서 번호로 나눕니다. 이 예제의 Tick(틱)은 게임 규칙을 한 번 진행하는 단계입니다. ‘몇 초 뒤’라는 모호한 메모 대신 ‘3번 틱에서 사격’이라고 적으면, 화면을 초당 몇 장 그리든 사건을 적용할 자리가 정해집니다. 틱의 빈도와 화면의 FPS는 같은 값일 필요가 없습니다.

## 명령 한 줄이 다음 상태를 만든다

다음 세 명령을 보관하겠습니다. 명령에 들어 있는 값과 처리한 뒤의 결과를 구별해서 보세요. 리플레이 파일의 간단한 명령 목록에는 위치 결과를 매번 전부 적지 않습니다. 오른쪽으로 움직이라는 요구를 기록하고, 위치는 규칙이 계산합니다.

| 틱 | 보관한 명령 | 처리 직후의 상태 |
| --- | --- | --- |
| 1 | 오른쪽으로 1칸 이동 | x=1, 에너지=2, 표적 체력=3 |
| 2 | 오른쪽으로 1칸 이동 | x=2, 에너지=2, 표적 체력=3 |
| 3 | 사격 | x=2, 에너지=1, 표적 체력=2 |

표의 마지막 줄이 성립하는 이유도 규칙으로 적어야 합니다. ‘사격’ 명령을 받으면 먼저 에너지가 있는지 검사하고, 있다면 에너지를 하나 쓰고 표적 체력을 하나 줄입니다. 그 규칙이 없는 입력 기록은 뜻을 해석할 수 없는 메모입니다.

{{diagram_replay_trace}}

그림의 파란 점은 병사의 현재 위치이고, 얇은 윤곽은 이전 위치입니다. 사격 틱에서는 병사가 더 이동하지 않습니다. 대신 에너지와 표적 체력만 바뀝니다. <b>명령마다 바뀌는 상태 항목이 다르다</b>는 것을 이처럼 눈에 보이게 추적하면 리플레이 오류를 찾기도 쉬워집니다.

설명용 처리 절차는 아래와 같습니다. 실제 게임의 파일 형식이 아니라 위 표를 그대로 실행하는 의사코드입니다.

```text
state = {x: 0, energy: 2, targetHP: 3}
commands = {1: MoveRight, 2: MoveRight, 3: Fire}

for tick in 1..3:
    command = commands[tick]
    if command == MoveRight:
        state.x += 1
    if command == Fire and state.energy > 0:
        state.energy -= 1
        state.targetHP -= 1
    draw(state, camera)
```

다시 보기에서는 state를 시작값으로 되돌리고 같은 명령을 같은 틱에 넣습니다. 그러면 같은 표가 다시 만들어집니다. 카메라는 draw에만 넘겼습니다. 따라서 카메라를 옮겨도 표적의 체력 계산에는 참여하지 않습니다. 이것이 ‘세계를 복원하는 일’과 ‘그 세계를 바라보는 일’을 나누는 가장 작은 예입니다.

## 무엇을 보관하면 다시 만들 수 있을까

우리 예제의 상태 변화는 수식으로도 짧게 적을 수 있습니다. 여기서 S는 위치·에너지·체력의 묶음, C는 명령, F는 한 틱의 게임 규칙입니다. n은 순서를 나타내는 틱 번호입니다.

$$
S_{n+1}=F(S_n,C_n)
$$

이 식이 말하는 것은 ‘현재 상태와 이번 명령을 규칙에 넣어 다음 상태를 만든다’입니다. 시작 상태 S₀, 명령의 목록, 같은 F가 준비되면 처음부터 순서대로 계산할 수 있습니다. 반면 F를 바꿔 사격 피해를 두 배로 만들면, 세 번째 명령부터 이전 경기와 다른 전투가 됩니다. 예전 리플레이가 새 패치에서 그대로 작동하는지 별도로 다뤄야 하는 이유가 여기 있습니다.

실제 파일의 내용을 ‘명령만’으로 단정해서도 안 됩니다. Blizzard가 공개한 s2protocol은 스타크래프트 II 리플레이의 헤더·게임 세부 정보·초기화 자료와 게임/메시지/추적 이벤트를 구분해 해독합니다. 추적 이벤트에는 유닛의 생성·죽음이나 일부 위치 정보도 있습니다. 이 자료는 ‘리플레이가 압축 동영상과 다른 종류의 기록’임을 확인해 주지만, 공개 파서만으로 게임의 실행 규칙 전체를 얻는 것은 아닙니다. [Blizzard의 s2protocol](https://github.com/Blizzard/s2protocol)

## 난수는 ‘아무 숫자’가 아니다

이번에는 사격이 가끔 빗나가게 바꿔 보겠습니다. 같은 명령을 다시 넣어도 명중 여부를 매번 새로 뽑는다면 표적 체력은 달라집니다. 예전 경기에서는 맞았는데 다시 보기에서는 빗나갈 수 있겠죠.

이를 다루는 한 방법이 Random Seed(난수 시드)와 난수 생성기의 상태를 함께 관리하는 것입니다. 컴퓨터의 의사난수 생성기는 정해진 규칙으로 수열을 만듭니다. 같은 알고리즘과 초기값에서 같은 순서로 값을 요청하면 같은 수열을 얻습니다. 그런데 시드만 같아도 안심할 수는 없습니다. 원래는 전투가 두 번째 값을 썼는데, 다시 보기에서는 장식용 불꽃이 난수를 한 번 먼저 가져갔다면 전투가 받는 값이 달라집니다.

따라서 전투와 장식 효과의 난수 흐름을 분리하거나, 중요한 결과를 명시적으로 기록하는 식의 설계가 필요합니다. 어떤 방식을 쓰든 핵심은 ‘다시 계산할 때 필요한 조건을 통제하는가’입니다. 수치 계산과 실행 순서의 아주 작은 차이도 누적될 수 있다는 결정론의 제약은 Glenn Fiedler의 네트워크 물리 설명에서 확인할 수 있습니다. [Deterministic Lockstep](https://gafferongames.com/post/deterministic_lockstep/)

## 빨리 감기와 되감기는 왜 다를까

우리 예제를 3번 틱까지 빨리 감으려면 세 명령을 화면에 그리지 않고 순서대로 처리하면 됩니다. 반대로 3번 상태에서 2번 상태를 얻는 일은 일반적으로 ‘한 틱을 빼기’만으로 되지 않습니다. 체력이 0이 되어 제거된 유닛은 제거 전의 세부 정보를 현재 상태에 남기지 않았을 수 있습니다.

이때 Snapshot(상태 스냅샷), 즉 특정 틱의 상태 묶음을 저장해 두면 출발점으로 사용할 수 있습니다. 10분 지점으로 이동하려면 가장 가까운 이전 스냅샷을 불러와 그 지점 이후의 명령만 재생하는 식입니다. 스냅샷 간격이 짧을수록 찾는 시간은 줄어들지만 저장 공간과 상태 직렬화 작업은 늘어납니다. 이 균형은 경기 길이와 편집/관전 기능에 맞춰 고릅니다.

{{diagram_replay_seek}}

그림에서 주황색 표시는 저장해 둔 상태이고, 파란 화살표는 다시 실행할 명령 구간입니다. 목적지에서 가장 가까운 ‘이전’ 상태를 고르는 이유는, 그 뒤의 사건을 빠짐없이 순서대로 적용해야 하기 때문입니다. 이 그림은 자체 리플레이 설계 예시이며 특정 게임이 이 간격으로 저장한다는 뜻은 아닙니다.

## 작은 리플레이를 검증하는 방법

완성 여부를 화면이 비슷해 보이는지만으로 판단하지 말아 봅시다. 위 예제를 한 번 실행하면서 틱마다 x·에너지·체력을 기록합니다. 다시 실행한 결과와 세 값이 모두 같은지 비교합니다. 다르면 가장 먼저 달라진 틱의 직전 상태, 적용한 명령, 난수 상태를 나란히 놓습니다. 끝난 뒤의 큰 차이보다 최초의 작은 차이가 원인을 찾는 데 유용합니다.

그다음 카메라 위치만 바꾸어도 상태 기록이 같게 나오는지 확인합니다. 마지막으로 사격 피해 규칙을 바꿔 실행해 보세요. 같은 명령 기록이라도 규칙의 버전이 다르면 결과가 달라진다는 사실을 직접 확인할 수 있습니다. 이런 실험이 가능해지면 리플레이는 ‘영상을 다시 틀기’가 아니라, <b>과거의 상태 전이를 같은 조건에서 다시 실행하도록 설계하는 일</b>로 이해됩니다.
