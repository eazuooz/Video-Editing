## 도구를 썼다는 말보다 어떤 문제를 해결했는지 보여 주기

소개서에 사용한 AI 이름이 여러 개 적혀 있습니다. 그런데 결과물에서 무엇을 직접 판단했고 어떤 문제를 해결했는지는 보이지 않습니다. 반대로 도구 목록은 짧아도 변경 전후와 검수 근거가 분명하면 작업을 이해하기 쉽습니다. 도구의 사용과 결과에 대한 책임을 함께 설명하는 방법이 필요합니다.

기존 수업은 AI 경험을 요구하는 분위기를 풍자한 짧은 장면입니다. 실제 채용 시장 전체의 통계나 특정 회사의 정책으로 읽지 않습니다. 여기서는 자체 인벤토리 기능 하나를 작업 기록으로 남기는 사례를 통해, 자동화 경험을 구체적인 개발 경험으로 설명해 보겠습니다.

## 기능의 이름보다 해결할 상황을 적기

자체 인벤토리는 최대 10칸이고 같은 물약은 한 칸에 5개까지 쌓을 수 있습니다. 처음 버전에서는 아이템을 추가할 때 전체 개수만 보고 빈칸이 있다고 오판하는 문제가 있습니다. ‘AI로 인벤토리를 만들었다’ 대신 이 상황과 기대 결과를 쓰면 어떤 문제를 다루었는지 보입니다.

예를 들어 물약 4개가 든 칸 하나와 다른 아이템 9칸이 가득 찬 상태에서 물약 2개를 추가합니다. 기존 칸에는 하나만 더 들어갈 수 있고 새 칸은 없습니다. 남은 하나를 거절할지, 전체 추가를 취소할지 정책을 먼저 정해야 합니다. 코드 생성 이전에 필요한 판단입니다.

## 자동화한 부분과 결정한 부분을 구별하기

자체 작업에서는 AI에게 가능한 추가 수량을 계산하는 코드 초안을 요청하고, 사람은 부분 수용 정책과 UI 피드백을 정했다고 합시다. 이를 그대로 기록하면 됩니다. 직접 작성하지 않은 줄을 모두 직접 썼다고 말할 필요도 없고, 도구를 썼다는 이유로 설계와 검수 역할을 지울 필요도 없습니다.

초안에 발견된 문제도 남깁니다. 같은 아이템을 여러 칸에서 찾지 못했는지, 최대 묶음 수를 넘겼는지, 실패해도 수량이 소모되었는지 설명합니다. 어떤 오류를 어떤 근거로 고쳤는지가 실제 경험을 보여 줍니다.

## 결과 화면과 상태 자료를 연결하기

물약 아이콘 옆 숫자만 보면 내부 수량과 일치하는지 모릅니다. 추가 전 상태, 입력 수량, 실제 반영 수량, 남은 수량을 함께 기록합니다. 자체 예에서는 4→5, 반영 1, 남음 1입니다. 화면 알림도 이 결과와 맞아야 합니다.

</image>

빈 인벤토리, 꽉 찬 인벤토리, 같은 아이템이 있는 경우와 없는 경우를 나누어 검사합니다. 자동 테스트가 가능하면 반복 계산을 맡기고, 화면에서 읽히는지는 실제 UI로 확인합니다. 테스트가 통과했다는 말만 쓰기보다 어떤 동작을 검증했고 어떤 부분은 보지 못했는지 설명합니다.

## 재현 가능한 작은 결과를 남기기

실행 방법과 검사용 시작 상태를 준비합니다. 보는 사람이 긴 플레이를 하지 않아도 문제가 생기던 상태와 수정된 결과를 확인할 수 있으면 좋습니다. 원본과 수정본을 구별하고 변경 이유와 남은 한계를 기록합니다. 비공개 회사 자료나 권한 없는 자산을 공개할 필요는 없습니다.

화려한 편집 영상만 있으면 실패와 경계 조건을 판단하기 어려울 수 있습니다. 짧은 데모와 필요한 코드, 자료 흐름 그림을 함께 연결합니다. 전체 프로젝트를 무조건 공개하는 것보다 공개 가능한 범위에서 문제를 충분히 설명하는 것이 중요합니다.

## 모르는 부분을 감추지 않아야 다음 질문에 답할 수 있다

코드가 작동하지만 왜 그런지 설명할 수 없는 부분이 있다면 학습 대상으로 남깁니다. 작은 입력을 바꾸어 결과를 예상하고 실행해 보며 이해를 확인합니다. 도구가 쓴 설명을 그대로 외우기보다 실제 자료가 어떤 순서로 바뀌는지 추적합니다.

검수하지 않은 성능이나 대규모 동시 사용을 보장하지 않습니다. 현재는 작은 단일 플레이 인벤토리에서 확인했고 저장이나 네트워크 동기화는 다루지 않았다고 적을 수 있습니다. 범위를 알면 다음 개발자가 무엇을 재사용하고 무엇을 더 확인해야 하는지 판단할 수 있습니다.

## 작업 기록은 다음 제작에도 쓸 수 있다

이 기록은 누군가에게 보여 주기 위한 포장으로만 끝나지 않습니다. 다음에 상점 구매를 만들 때 부분 추가와 비용 차감의 순서를 다시 검토하는 기반이 됩니다. 도구 이름이 바뀌어도 상태와 경계 조건을 설명한 자료는 남습니다.

자동화를 활용한 경험을 잘 전달하려면 ‘무엇을 요청했나’에서 ‘무엇을 결정하고 확인했나’까지 이어져야 합니다. 문제, 선택, 변경, 증거가 연결되어 있으면 다른 사람도 결과의 의미를 이해하고 다음 질문을 할 수 있습니다. 그것이 반복해서 사용할 수 있는 개발 기록입니다.
