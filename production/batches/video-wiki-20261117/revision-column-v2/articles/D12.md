## 문을 누른 뒤 아무 일도 없으면

잠긴 문 앞에서 상호작용 버튼을 눌렀습니다. 문은 그대로이고 소리도 안내도 없습니다. 플레이어는 세 가지를 구분하기 어렵습니다. 입력을 못 받은 것인지, 받았지만 조건이 안 되는지, 어딘가에서 처리 중인지입니다. 같은 버튼을 여러 번 누르는 행동은 조작을 몰라서가 아니라 현재 상태를 알 수 없어서 나올 수 있습니다.

좋은 응답을 만든다는 것은 모든 입력을 성공시키거나 매번 큰 효과를 터뜨리는 일이 아닙니다. <b>받은 요청, 적용할 규칙, 처리 상태, 실제 결과를 서로 구별해 전달하는 것</b>입니다. 이 글에서는 잠긴 문과 저장 버튼이라는 두 작은 사례로 그 구조를 만들어 보겠습니다.

## 입력을 알아본 것과 문을 연 것은 다르다

잠긴 문을 누르면 손잡이가 짧게 움직이고 ‘열쇠가 필요합니다’라는 안내가 나온다고 합시다. 문은 열리지 않았지만 시스템이 상호작용을 알아봤다는 사실은 전달됩니다. 이것이 Acknowledgement(수신 확인)입니다. 문이 실제로 열리고 통행 가능 상태로 바뀌는 Completion(완료)과는 다른 단계입니다.

{{diagram_feedback_door}}

그림의 문은 두 경우 모두 잠겨 있습니다. 오른쪽만 열려 있다면 성공과 실패를 비교하는 그림이 되겠지만, 여기서는 같은 거절 상태를 어떻게 알려 주는지 비교합니다. 안내를 추가해도 규칙을 쉽게 바꾸거나 거절을 성공처럼 포장한 것이 아닙니다.

NNGroup의 ‘시스템 상태의 가시성’ 설명도 사용자의 입력이 등록되었는지, 처리가 이어지고 있는지를 알 수 있게 하는 적절한 피드백을 다룹니다. 우리 게임에 옮길 때는 어떤 상태가 플레이어의 다음 판단에 필요한지 구체적으로 골라야 합니다. [Visibility of System Status](https://www.nngroup.com/articles/visibility-system-status/)

## 거절 이유는 다음 행동과 연결될 때 유용하다

‘사용할 수 없습니다’라는 문구를 모든 상황에 쓰면 반응이 없다는 문제는 일부 줄여도 다음 선택은 여전히 막힙니다. 열쇠 부족, 처리 중, 거리 부족은 모두 문을 당장 열지 못한다는 결과가 같지만 해결할 행동은 다릅니다.

| 현재 조건 | 알려 줄 정보 | 플레이어가 다음에 할 수 있는 일 |
| --- | --- | --- |
| 문까지 너무 멀다 | 상호작용 거리 밖 | 가까이 다가가기 |
| 열쇠가 없다 | 필요한 열쇠의 조건 | 다른 길에서 찾거나 목표를 바꾸기 |
| 문이 열리는 중이다 | 이미 진행 중 | 기다리거나 이동 준비하기 |
| 문이 이미 열렸다 | 통행 가능 | 지나가기 |

그렇다고 모든 내부 조건과 오류 코드를 길게 보여 줄 필요는 없습니다. 플레이어가 바꿀 수 없는 서버 내부 변수보다 지금 행동에 필요한 이유가 중요합니다. 여러 조건이 동시에 안 맞으면 어느 이유를 우선할지도 정합니다. 멀리 서 있는 사람에게 소지품 검사부터 안내할지, 우선 가까이 오게 할지의 차이입니다.

## 기다리는 동작에는 시간이 아니라 상태가 필요하다

저장 버튼을 누르는 예로 바꿔 보겠습니다. 버튼 애니메이션이 끝났다고 파일 저장이 끝난 것은 아닙니다. 처리 시작과 실제 성공을 나누지 않으면 데이터가 아직 기록되지 않았는데 ‘저장 완료’가 표시될 수 있습니다.

상태를 Idle(대기), Processing(처리 중), Succeeded(성공), Failed(실패)로 정합니다. 입력을 받으면 조건을 확인하고 처리 중으로 넘어갑니다. 저장 결과가 성공으로 돌아왔을 때만 완료를 표시합니다. 실패하면 이유와 다시 시도할 경로를 보여 줍니다. 아래는 저장 기능 자체가 아닌 상태 연결의 의사코드입니다.

```text
저장 요청:
    이미 처리 중이면 새 저장을 중복 시작하지 않는다.
    아니라면 상태를 Processing으로 바꾸고 저장을 시작한다.

저장 결과 수신:
    현재 요청의 성공이면 Succeeded로 바꾼다.
    현재 요청의 실패이면 Failed로 바꾸고 재시도 방법을 표시한다.
```

시간표의 끝에 무조건 ‘성공’을 예약해 두는 방식과 비교해 보세요. 성공이 되는 근거는 대기 시간이 다 됐다는 사실이 아니라 실제 결과입니다. 진행률을 알 수 없다면 정확하지 않은 퍼센트를 꾸며 내기보다 진행 중임을 나타내는 표시가 적절할 수 있습니다.

## 중복 입력과 늦게 온 결과도 같은 구조로 다루기

처리 중 버튼을 다시 눌렀을 때 새 작업을 또 만들지, 같은 작업의 상태를 보여 줄지 정해야 합니다. 단순히 버튼의 색을 바꾸는 것만으로 중복 요청이 막히는 것은 아닙니다. 입력 처리 쪽에서도 현재 상태를 확인해야 합니다. 반대로 버튼을 비활성화했다면 왜 기다려야 하는지가 읽혀야 합니다.

비동기 작업에서는 이전 요청의 결과가 늦게 도착할 수도 있습니다. 예를 들어 저장 A가 늦어지는 동안 저장 B를 새로 시작하도록 허용했다면, A의 성공 안내가 B의 상태를 완료로 바꾸지 않게 요청을 식별해야 합니다. 이 예제에서는 한 번에 하나만 허용해 복잡도를 낮췄지만, 기능을 넓힐 때 어떤 조건이 추가되는지 알고 있어야 합니다.

## 누른 의도와 확정도 나눌 수 있다

컷신 건너뛰기를 한 번 누르면 안내만 보이고, 계속 누르고 있으면 확정 표시가 차오르게 만들 수 있습니다. 첫 입력을 알아봤다는 신호와 돌이킬 수 없는 실행을 분리하는 예입니다. 중간에 버튼을 놓으면 무엇이 취소되고 무엇이 유지되는지도 알려 줍니다.

{{existing_image_0}}

기존 영상의 자체 메뉴 도식에서는 확인과 돌아가기처럼 다른 의도를 서로 다른 결과로 연결합니다. 같은 의도로 쓰기 쉬운 입력을 여러 개 받는 것과, 다른 결과의 입력까지 섞는 것은 구별해야 합니다. 여러 키를 허용할 때도 게임 전체의 조작 약속을 유지하는지 먼저 확인합니다.

길게 누르기가 모든 상황의 정답은 아닙니다. 자주 반복하는 가벼운 행동에 매번 긴 확정을 요구하면 조작이 번거로워질 수 있고, 오래 누르기 어려운 사람을 위한 다른 방법도 필요할 수 있습니다. 잘못 실행했을 때의 비용과 반복 빈도에 맞춰 확정 방법을 선택합니다.

## 무엇에 응답하지 않을지도 정하기

아무 의미 없는 키를 누를 때마다 경고를 띄우면 중요한 안내가 묻힙니다. 플레이어가 실행 가능한 것처럼 읽을 대상, 현재 도구와 관련된 행동, 실패했을 때 다음 선택이 달라지는 요청에 우선 응답합니다. 장식 오브젝트를 향해 버튼을 눌렀을 때까지 모두 실패 팝업을 만들 필요는 없습니다.

효과의 크기도 역할에 맞춥니다. 입력 수신은 작은 변화로 충분할 수 있고, 중요한 성공은 더 선명하게 보여 줄 수 있습니다. 소리·색·모양·문구가 서로 다른 상태를 말하지 않는지도 확인합니다. 빨간 경고음을 내면서 ‘성공’이라고 쓰면 플레이어는 다시 해석해야 합니다.

## 검수할 때 ‘무반응’이라는 말을 분해하기

잠긴 문을 준비하고 거리 부족, 열쇠 부족, 열리는 중, 열린 뒤에 같은 입력을 넣습니다. 각 경우에 무엇을 받은 것인지, 왜 다음 상태로 가지 않았는지, 다음에 무엇을 할 수 있는지를 화면만 보고 설명할 수 있는지 봅니다.

저장 예제에서는 처리 시간을 늘리고, 실패를 일부러 돌려주고, 처리 중 재입력을 해 봅니다. 결과 확인 전 성공을 말하지 않는지, 중복 요청이 생기지 않는지, 실패 뒤 복귀할 길이 있는지를 확인합니다. 이 테스트를 하면 UI 꾸미기와 실제 상태 설계가 연결됩니다.

반응 좋은 게임은 모든 것을 즉시 끝내는 게임과 같지 않습니다. 기다려야 하는 행동도 <b>무엇을 기다리는지, 무엇이 이미 반영되었는지, 언제 다음 행동을 할 수 있는지</b>가 읽히면 플레이어가 상황을 판단할 수 있습니다.
