## 기획서가 길어질수록 같은 기능이 달라지는 이유

몬스터를 수집하는 작은 게임을 기획한다고 합시다. 처음에는 ‘싸우고, 약해진 몬스터를 포획한다’는 한 문장이었습니다. 며칠 뒤에는 포획 도구의 종류, 사용 조건, 성공률, 가방이 가득 찼을 때의 처리까지 생겼습니다. 그런데 프로그래머는 ‘실패하면 턴을 쓴다’고 이해했고, UI 담당자는 ‘실패하면 도구만 소모한다’는 예전 문장을 보고 화면을 만들고 있습니다.

두 사람이 문서를 안 읽어서만 생긴 문제일까요? 같은 기능의 규칙이 여러 장소에 흩어져 있고, 어느 문장이 기준인지 보이지 않았다면 성실하게 읽어도 다른 결론에 도달할 수 있습니다. 계층형 아웃라인은 이 문제를 다루는 방법입니다. 중요한 것은 예쁜 들여쓰기가 아니라 <b>관련된 판단을 한곳에서 찾고, 바뀐 범위를 따라갈 수 있게 만드는 것</b>입니다.

이 글에서는 한 가지 포획 기능을 평평한 메모에서 구현·검수 가능한 설명으로 바꾸어 보겠습니다. 이것은 모든 게임에 적용할 유일한 문서 양식이 아니라, 문서가 해결해야 할 질문을 찾기 위한 예입니다.

## 제목을 달기 전에 독자의 질문을 적기

기획서를 읽는 사람은 매번 첫 페이지부터 끝까지 감상하지 않습니다. 작업 중 생긴 질문의 답을 찾습니다. 이번 기능에서 각 담당자가 찾을 질문을 먼저 써 보겠습니다.

| 작업 중인 사람 | 실제로 확인할 질문 |
| --- | --- |
| 규칙 구현 | 누구에게 언제 포획을 시도할 수 있는가? |
| UI 구현 | 버튼은 어느 조건에서 켜지고, 거절 이유를 어떻게 표시하는가? |
| 애니메이션 제작 | 던지는 동안 다른 행동을 할 수 있는가? 성공 뒤 무엇이 보이는가? |
| QA | 실패·가방 부족·중복 입력일 때 어떤 결과를 확인해야 하는가? |

이 질문 없이 ‘시스템, 콘텐츠, UI, 기타’부터 만들면 같은 조건이 시스템 설명과 UI 설명에 각각 복사될 수 있습니다. 분류표는 생겼지만 기준 정보가 두 군데가 된 셈입니다. 따라서 먼저 기능의 결정이 어디에 한 번만 적힐지 정하고, 다른 위치에서는 그 항목을 참조하게 합니다.

## 평평한 메모에 숨어 있던 두 관계

다음 메모를 보겠습니다. 항목을 줄바꿈하는 것만으로는 서로 어떤 관계인지 알 수 없습니다.

```txt
몬스터볼 선택
대상의 체력
가방 공간
던지기 연출
성공 처리
실패 처리
경험치 지급
결과창
```

여기에는 ‘포획 기능 안에 어떤 하위 규칙이 있는가’라는 포함 관계와 ‘어떤 처리를 먼저 하는가’라는 시간 순서가 섞여 있습니다. 두 관계를 같은 들여쓰기로 해결하려 하면 문서가 불분명해집니다. 가방 공간은 던지기 다음에 존재하는 것이 아니라, 시도를 허용할지 판단하는 조건입니다. 결과창은 포획 기능의 일부인 동시에 처리 결과를 표시하는 화면입니다.

<image source="notion-file-block://41b0b1ff-a61e-8112-ab88-c259362ab3dd/07652553-a8fd-4f5f-a9de-61787ec20a97?space_id=cc7962ab-bf9b-46ae-bfcc-f6a88421e46b&name=outline_tree.png">
자체 아웃라인 구조. 가지는 처리 순서나 중요도 순위를 뜻하지 않습니다. 포획 기능의 조건·순서·결과·예외를 찾을 위치를 보여 줍니다.
</image>

그림의 가지는 시간 순서가 아닙니다. ‘사용 조건’ 아래에 대상·도구·저장 공간을 두었다는 것은 그 세 조건을 함께 검사한다는 범위 설명입니다. 성공 처리가 조건보다 덜 중요해서 밑으로 내려간 것도 아닙니다. 상위 항목의 어떤 내용을 구체화하는지 보여 주는 구조입니다.

이제 같은 수준의 제목에는 가능하면 같은 종류의 정보를 놓습니다. ‘사용 조건 / 처리 순서 / 결과 / 예외’처럼 독자가 찾을 질문으로 나누면, 조건을 알고 싶은 사람이 연출 문단을 읽으며 추측하지 않아도 됩니다.

## 한 항목을 실제 규칙으로 내려쓰기

‘사용 조건: 가방에 공간이 있어야 한다’고 쓰면 충분할까요? 아직 시점이 남았습니다. 포획을 누를 때 검사할지, 성공이 결정된 뒤 검사할지에 따라 결과가 달라집니다. 애니메이션 도중 다른 보상이 들어와 가방이 찰 수도 있습니다. 이번 시제품에서는 복잡도를 줄이기 위해 아래처럼 결정하겠습니다.

```txt
포획
  목적
    약해진 야생 몬스터를 동료로 얻는다.
  사용 조건
    야생 몬스터를 대상으로 한다.
    포획 도구를 1개 이상 보유한다.
    시작 시점에 보관 칸을 1칸 예약할 수 있다.
  처리 순서
    조건 검사 → 칸 예약 → 입력 잠금 → 도구 소모 → 결과 판정
  결과
    성공: 예약 칸에 몬스터 저장 → 결과 표시 → 전투 종료
    실패: 예약 해제 → 실패 표시 → 상대 턴으로 이동
  취소·예외
    시작 전 거절: 도구와 턴을 소모하지 않는다.
    처리 도중 중복 입력: 새 시도를 만들지 않는다.
```

여기의 ‘칸 예약’은 독자가 반드시 따라야 하는 정답이 아니라 <b>이번 예제에서 선택한 설계</b>입니다. 성공 뒤 검사하고 초과분을 별도 보관함에 보내는 대안도 가능합니다. 중요한 것은 선택한 조건과 결과가 서로 모순되지 않게 이어져야 한다는 점입니다. 한 줄의 조건을 쓸 때 “언제 검사하며 실패하면 무엇이 남는가”를 함께 묻는 습관이 문서의 빈틈을 줄입니다.

## 아웃라인과 흐름도는 서로 대신할 수 없다

아웃라인은 관련 규칙이 어디에 묶였는지 보여 줍니다. 하지만 중간에 거절되면 어느 경로로 빠지는지, 성공과 실패가 어디에서 나뉘는지는 흐름도로 보는 편이 분명할 수 있습니다. 앞서 정한 문장을 아래 순서에 옮겨 보겠습니다.

<image source="notion-file-block://41b0b1ff-a61e-8142-b16c-ebf8db462e0a/3b835f00-300b-41f9-b583-406782fd7f7c?space_id=cc7962ab-bf9b-46ae-bfcc-f6a88421e46b&name=capture_flow.png">
자체 포획 규칙의 흐름. 시작 조건에서 거절되면 비용을 쓰지 않습니다. 도구를 소모한 뒤의 실패는 다른 결과입니다. 이 차이를 문장·UI·QA 사례에서 같은 이름으로 연결해야 합니다.
</image>

첫 갈림길은 시작 조건입니다. 여기서 거절되면 아직 도구를 소모하지 않았으므로 그대로 선택 화면에 남습니다. 통과한 뒤에는 도구를 소모하고 결과를 판정합니다. 이 두 실패를 같은 ‘실패’라는 단어로만 써 두면 비용 처리도 헷갈립니다. <b>시도할 수 없음</b>과 <b>시도했지만 성공하지 못함</b>을 나누어 이름 붙이는 편이 구현과 안내 문구를 연결하기 좋습니다.

흐름도를 그리다 빠진 조건이 보이면 아웃라인의 해당 규칙을 수정합니다. 도식을 따로 만든 채 문서와 다른 상태로 두면 다시 기준이 둘로 갈라집니다. 그림은 문서의 대체물이 아니라 문장 속 관계를 드러내는 다른 표현입니다.

<image source="notion-file-block://41b0b1ff-a61e-8155-aae6-c5847ff9f9ac/a66d03d6-6efa-449f-8a4b-3d0c02b824aa?space_id=cc7962ab-bf9b-46ae-bfcc-f6a88421e46b&name=yamyam-outline-0043.jpg">
영상 00:43 · 전투 아래에 기술 선택과 아이템 사용을 묶고, 몬스터볼의 사용 조건과 처리 결과를 같은 가지에서 찾는 자체 설명 화면입니다. 가상의 기획 메모이며 개발사의 원본 문서는 아닙니다.
</image>

## UI 문서에 규칙을 다시 복사하지 않기

포획 버튼 설명에 ‘도구가 있어야 사용 가능’이라고 따로 적으면 그 문장도 규칙입니다. 나중에 보관 칸 조건이 추가됐는데 UI 문장만 고치지 않으면 화면과 게임이 달라집니다. 대신 UI 문서는 규칙 항목을 참조하고, 이 화면만의 표시 방식에 집중하게 합니다.

| 규칙 항목 | UI가 받아 표시할 상태 | 화면의 책임 |
| --- | --- | --- |
| 포획/사용 조건 | 사용 가능 | 선택 가능한 버튼과 대상 강조 |
| 포획/사용 조건/도구 없음 | 시도 거절 | 도구 부족의 이유와 필요한 행동 안내 |
| 포획/사용 조건/보관 칸 없음 | 시도 거절 | 보관 공간을 정리할 경로 안내 |
| 포획/처리 중 | 입력 잠금 | 중복 클릭이 새 시도처럼 보이지 않게 표시 |
| 포획/결과 | 성공 또는 실패 | 결과와 이후 이동을 일치시켜 표시 |

이런 식으로 쓰면 규칙 문서의 조건과 UI의 표현을 구분할 수 있습니다. ‘버튼을 회색으로 만든다’는 화면의 구현 선택이고, ‘시도를 허용하지 않는다’는 게임 규칙입니다. 둘을 한 문장으로 묶어 버리면 접근성 표시 방식이나 UI 외형을 바꿀 때 규칙까지 흔들릴 수 있습니다.

영상 02:00 · 자체 제작한 계층 도식. 소리·밝기·언어는 같은 단계이고, 음악·효과음·목소리는 소리의 세부 항목입니다. 파란 연결과 아래 단계의 연결을 비교하면 순서와 소속의 차이를 읽을 수 있습니다.
</image>

## 구조가 생겼는지 확인하는 작은 검수

동료에게 문서를 주고 다음 세 상황의 결과를 찾아 달라고 해 봅시다. 도구가 없을 때, 포획을 누른 직후 한 번 더 누를 때, 실패한 직후입니다. 우리가 만든 예제의 답은 각각 ‘시도 거절·비용 없음’, ‘새 시도를 만들지 않음’, ‘도구는 소모됨·상대 턴’입니다. 여러 문단을 추측해 엮어야 답이 나온다면 해당 조건과 결과를 더 가깝게 배치해야 합니다.

다음으로 “실패해도 플레이어 턴을 유지한다”는 변경을 가정합니다. 결과 항목, 턴 처리의 참조, 안내 문구, QA 사례 중 무엇을 고칠지 찾습니다. 문서 구조가 좋다는 것은 모든 변경이 한 줄로 끝난다는 뜻이 아닙니다. <b>연결된 수정 범위를 찾을 수 있고, 같은 규칙을 모르게 두 번 고치지 않게 되는 것</b>입니다.

## 얼마나 깊이 나누어야 할까

제목 아래 문장이 한 줄뿐인데 다시 제목을 여러 단계 더 만드는 것은 오히려 탐색을 어렵게 만들 수 있습니다. ‘포획/예외/실패/일반 실패/처리’처럼 내려가면 독자는 어떤 항목을 열어야 할지 먼저 해석해야 합니다. 같은 질문을 묶는 데 필요한 만큼만 나누고, 자주 함께 확인하는 조건과 결과는 가까이 둡니다.

작은 팀의 첫 시제품이라면 목적, 플레이어 행동, 성공·실패 조건, 가장 불확실한 부분 정도로 시작할 수 있습니다. Unity의 GDD 자료도 콘셉트 설명과 기능별 문서를 분리하는 모듈식 구성을 제시합니다. 템플릿의 모든 항목을 채우기보다 지금 필요한 결정을 찾는 참고로 사용하는 편이 적절합니다. [Unity Game Design Document Template](https://connect-prd-cdn.unity.com/20201215/83f3733d-3146-42de-8a69-f461d6662eb1/Game-Design-Document-Template.pdf)

계층형 아웃라인은 기획 내용을 자동으로 좋은 게임으로 바꾸지는 않습니다. 정한 규칙이 재미있는지는 시제품에서 확인해야 합니다. 대신 팀이 같은 규칙을 찾고, 그 규칙을 바꾼 이유와 범위를 추적하게 합니다. 문서의 분량보다 <b>질문 하나를 가지고 필요한 답에 도달할 수 있는가</b>를 기준으로 구조를 다듬어 보세요.
