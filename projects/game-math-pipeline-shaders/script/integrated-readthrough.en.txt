In Townscaper, adding buildings and turning the view changes where roofs appear and how they overlap. How does a computer turn these three-dimensional changes into one image? We will follow vertices toward the screen, connect depth to visibility, and use shaders to calculate surface color. First, let us trace the route from the buildings and camera to the resulting picture.

This is the graphics pipeline: a sequence that transforms vertices and textures into an image. We will use a basic triangle rasterization pipeline. Engines can run stages in parallel or rearrange work, but this conceptual order reveals what information each stage needs.

First we set the camera, its viewing direction, and the output region, along with lighting and fog. Then we find objects that could be visible. Detailed work on an object hidden outside the room may contribute nothing to the image.

For each candidate we choose a material, including textures and shaders, and submit its vertices and triangles to the graphics API. A distant object may use a simpler mesh, called a level of detail, or LOD. The pipeline now has the data needed to decide where to draw it.

The vertex shader transforms each vertex and prepares shading data. The pipeline clips parts outside the view and culls unwanted faces. Rasterization finds which screen samples a remaining triangle covers. The pixel shader then evaluates color from the interpolated data, materials, and lighting.

A computed color does not necessarily survive. A nearer surface can hide it, and empty areas of a leaf texture may be discarded. Surviving results replace or blend with existing color. Notice how processing moves from objects to vertices, triangles, and pixels. We will now examine the memory those operations use.

The game does not have to run a software loop over every pixel. It prepares data and state, submits work through the API, and supplies shaders for vertex and pixel calculations. The division varies by platform, while avoiding invisible work and unnecessary CPU–GPU waiting remains useful.

The frame buffer stores the resulting colors. Think of it as memory containing a color for each image location. Formats vary; its purpose here is to hold the image being constructed. What happens if we redraw the same image while the display is reading it?

Double buffering separates the displayed image from the image under construction. The front buffer represents the displayed frame, while rendering prepares a back buffer. A completed image can be presented through a role change or copying. Real systems may use more buffers and display synchronization; the key is separating construction from presentation.

In Portal, carrying a cube makes it cover parts of the platforms and walls behind it. When several surfaces project onto the same place in the image, the renderer needs a way to decide which surface remains visible. A depth buffer records which surface is in front at each sample. Consider a convention where smaller values are nearer. If the stored value is 0.7 and a new value is 0.3, the new surface wins and updates color and depth. A later value of 0.8 fails because it is farther away.

Depth is not necessarily distance in meters or the raw clip-space z. It is mapped from the depth after perspective division. A conventional near-zero, far-one setup commonly clears to one and accepts smaller values. Reverse Z uses the opposite ordering. The clear value and comparison function must agree.

With output storage ready, we prepare the input. Rendering state selects shaders, textures, matrices, and light parameters. A matrix shared by an object's vertices can be supplied as a constant, while positions vary per vertex. We do not need to duplicate every shared value in each vertex.

Vertex attributes depend on the surface. Position locates it; UV selects texture locations; the normal describes surface orientation. Vertex color can control color or blending. A tangent basis interprets normal-map directions, and a skinned mesh also needs joint indices and weights.

A basic mesh can provide position, normal, and UV. For our tangent-space normal-mapping path, add a tangent and handedness sign. The remaining axis comes from their cross product and that sign. This is one practical data format, not a claim that tangents can never be reconstructed another way.

UI elements such as text may need only screen position, color, and UV, with no lighting normal. A flame or debug marker can have a 3D position while outputting an assigned unlit color. Vertex layout follows the calculations required, not simply whether an object is three-dimensional.

A lightmapped surface can have separate UV sets for material textures and baked lighting. Its tangent basis supports the accompanying normal mapping, not ordinary lightmap lookup itself. Skinning adds joint indices and weights. Our four-influence example is a chosen layout, not a universal engine limit.

We can group all attributes of each vertex in an array of structures, or group positions, normals, and other attributes separately in a structure of arrays. Unused streams can be omitted. In a packed block, stride locates the next vertex and offset locates an attribute. Performance depends on how the data is accessed and on the hardware.

The vertex shader prepares clip-space position and the values used downstream. It can skin vertices, transform normals, calculate light vectors, fog factors, or projected texture coordinates. Correctly prepared inputs can pass through unchanged. Gouraud shading evaluates lighting here as well.

Follow one position from model coordinates into the world, then into camera coordinates and finally clip space. With row vectors, the model, view, and projection matrices multiply on the right in that order. Precombining them lets each vertex use one matrix multiplication. Mathematical multiplication order and memory storage order are separate choices.

Before perspective division, clipping removes parts outside the viewing volume. A triangle crossing the boundary must be cut, not discarded entirely. In the basic Direct3D convention, x and y lie between minus w and w, while z lies between zero and w. OpenGL's default depth convention differs.

Sutherland–Hodgman clipping handles one boundary plane at a time. In the start-vertex output convention, an inside-to-inside edge emits its start; outside-to-outside emits nothing; outside-to-inside emits the intersection; inside-to-outside emits the start and intersection. One circuit produces the clipped polygon's vertices.

Where should an edge that leaves the visible region be cut? A point travelling from the inner endpoint to the outer one eventually touches the boundary. Lowercase t is the fraction travelled. Interpolating the texture coordinates by that fraction keeps the pattern continuous at the cut. Collect the surviving vertices in order and close the polygon. Remove duplicate points and draw it only if it still has area.

Not every off-screen portion has to be clipped geometrically in the same way. Scissoring rejects samples outside a screen rectangle. A guard band extends the permitted region to reduce some geometric clipping. This optimization does not remove the need to handle the near plane or valid homogeneous coordinates.

Backface culling can skip the rear faces of a closed opaque object, which are normally covered by its front surfaces. It does not guarantee that half the triangles disappear. Terrain and freely viewed objects differ, while thin leaves or visible interiors may require different settings.

Hardware commonly distinguishes faces by projected clockwise or counterclockwise winding. Which winding is front-facing is a configurable convention, not an automatic consequence of coordinate handedness. A mirrored transform can reverse it. Some effects deliberately render front and back faces in separate passes.

In 3D, compare the outward normal with a vector from the eye to the surface. A positive dot product indicates a back face. For a right-facing normal and an eye on the right, the eye-to-surface vector points left, producing a negative dot product: the eye is on the front side. Checking only the normal's z component fails for off-axis perspective geometry.

The remaining triangles undergo perspective division and viewport mapping. Their coordinates can be fractional, while screen samples occupy defined locations. Rasterization decides which samples belong to each triangle. Shared-edge rules prevent adjacent triangles from both claiming or both missing the same boundary sample.

Covered samples receive interpolated UVs, normals, and other attributes. Perspective-correct interpolation can differ from a simple screen-space average. Directions such as normals may need renormalization afterward. Hidden samples can sometimes fail an early depth test before expensive shading; shader behavior determines when that is valid.

In the same game, the room remains visible through a glass pane while its opaque frame blocks the view. Beyond resolving what is in front, we also need to determine how each surface contributes to the visible color. The pixel shader evaluates material, lighting, and any fog to produce color and alpha. Alpha testing discards cutout samples; alpha blending combines surviving color with the background. With straight alpha, quarter-opacity red over blue yields 0.25 red and 0.75 blue. Depth writes and ordering must also suit the material.

In Super Mario Odyssey, Mario remains partly visible through the water, then changes appearance as he jumps out. The pipeline we have followed calculates the visible color of surfaces such as this water and the glass we just saw. We will now implement its programmable stages in HLSL: the vertex and pixel shaders. We begin with an unlit texture, then add lighting, normal mapping, and skinning. We will distinguish legacy shader-model notation from modern syntax while following the same data flow.

A float4 groups four numbers, such as x, y, z, and w; a float2 can hold UV coordinates. A semantic after the colon labels how data connects between stages. The vertex shader's UV output supplies the pixel shader's UV input. Modern Direct3D uses SV_Position for clip-position output.

The simplest vertex shader transforms position to clip space and passes UV unchanged. HLSL mul treats a vector in its first argument as a row vector, so this example places modelToClip second. Do not mix this with the matrix-first column-vector convention. The host code must supply matrices under the same convention.

The pixel shader samples the texture and multiplies by a constant color. A texel of (0.8, 0.4, 0.2) multiplied by (1, 0.5, 1) becomes (0.8, 0.2, 0.2). This is componentwise multiplication, not a matrix product. Alpha can also be scaled, but the blend state decides how transparency is composited.

Legacy POSITION and COLOR outputs correspond to SV_Position and SV_Target in our modern example. Texture and sampler declarations must also match the target environment. Updating a shader requires checking input formats, data types, and coordinate spaces, not merely replacing a few names.

Now add light while keeping one local light and constant ambient illumination. The vertex shader supplies model-space position, normal, and UV alongside clip position. The pixel shader receives their interpolated values and reads separate diffuse and specular material textures. Shared UV coordinates do not make their roles identical.

Normalize the surface normal. Light position minus surface position gives the vector to the light; its length supplies distance, while its normalized value supplies direction. Normalize the sum of view and light directions for the halfway vector. With radius four and distance one, linear attenuation is 1 minus one quarter, or 0.75. This is our example's falloff, not the physical inverse-square law.

Diffuse uses the nonnegative normal–light dot product. Specular raises the nonnegative normal–halfway dot product to an exponent. Ambient joins the diffuse illumination before multiplying by diffuse material color; specular material color scales the separate highlight. For an opaque one-sided surface, suppress the highlight when the light is behind it. Perform these color calculations in linear space.

We want the colour that one point on the surface sends to the screen. Keep the camera and light fixed and raise only the specular strength at the same point on the sphere. The broad base stays the same while the small highlight grows clearer. The yellow dot marks the surface point we are reading. Separating the base and highlight terms shows where to look when the surface gets too bright.

Repeating all work per pixel can be costly. An alternative computes light directions, halfway vectors, or falloff at vertices and interpolates them. Pixel work decreases, but interpolated data grows and nonlinear calculations are approximated. The tradeoff depends on vertex count, screen coverage, and data transfer as well as arithmetic.

The placement of a clamp matters. Endpoints of 0.5 and minus 0.5 interpolate to zero at the midpoint, which remains zero after clamping. Clamp the endpoints first, and they become 0.5 and zero; their midpoint is 0.25. Interpolation and clamping do not commute. Interpolated distance falloff is still an approximation.

The same pixel shader can work in view space if all positions and directions agree on that space. The eye is at the origin, so the view direction is the negative surface position. Normalize its xyz components, not a four-component position containing w. Giving a direction w equal to zero excludes translation.

Shared world or view space can reduce per-object preparation of lighting coordinates. Normals require an inverse-transpose transform under nonuniform scaling. A space whose axes align with the world can still have a different origin. Consistent reference frames and transform conditions matter more than the space's name.

Now move the lighting result itself into the vertex shader. That produces Gouraud shading: interpolate diffuse and specular illumination instead of computing them from a normal at every pixel. The light direction must be a float3. Pixel work becomes simpler, but a small highlight between vertices can be missed.

The pixel shader multiplies each material texture by its interpolated illumination and adds the results. It need not know whether one light or three produced those values. Defining the interface between stages lets the same shader serve multiple lighting setups.

For three directional lights, initialize diffuse illumination with ambient and specular with zero, then accumulate each light's contribution. This can form a useful object-inspection lighting setup. Manually unrolling a loop is not automatically faster; inspect compiled code and measure actual performance.

Keep the lighting model and add normal-map detail. Reconstruct the bitangent from the normal, tangent, and handedness sign. Dot light and halfway vectors with each basis axis to express them in tangent space. Treating this transpose as an inverse requires an orthonormal basis.

Decode a normal by doubling its RGB values and subtracting one, then renormalize because filtering and quantization can change its length. Normalize interpolated lighting directions and apply the same Blinn–Phong calculation. Handle zero-length vectors, including coincident light and surface positions or a degenerate halfway vector, explicitly.

Keep surface shading and animate the geometry. A skinned vertex supplies bind-pose position and normal, joint indices, and weights. Blend the bind-to-current joint matrices using those weights. The constant array contains joint matrices, not vertices. Its size and the index type must match the actual input format.

In the row-vector example, a four-by-three matrix maps a four-component position to three coordinates. Keep w equal to one for positions and zero for directions. Send the skinned position to clip space, and the existing pixel shader shades the animated surface. Matrix transfer and branching costs need target-specific measurement.

A skinned normal-mapped surface also transforms its normal and tangent. Blending matrices can disturb length and orthogonality, so verify normalization and reorthogonalization, with separate care for nonuniform scaling. Reconstruct the bitangent and tangent-space lighting vectors, then reuse the normal-mapping pixel shader.

We began with one texture, then added lighting, normal mapping, and skeletal motion. Geometry deformation and surface color can belong to different stages. Knowing each stage's inputs, outputs, and coordinate spaces gives us a reliable way to combine features and diagnose errors.

Consider a 640-by-480 sample image. Filling a 4:3 display gives square pixels. Filling a 16:9 display with the same sample count gives a pixel aspect ratio equal to display aspect divided by sample aspect: four thirds. Each displayed pixel is wider than it is tall.

To keep objects from stretching in split screen, the camera needs the shape of its viewport. Splitting the screen side by side narrows each player's viewport while its height stays the same. Aspect ratio is viewport width divided by height. Narrow the viewport at fixed horizontal field of view and it admits more of the world vertically.

Now we want the angle between the top and bottom of the visible region. A ray from the camera to the top edge shows half of that angle. The arctangent of the reciprocal vertical zoom gives that half angle. Double it for the full vertical field of view. Change only the viewport width. The horizontal rays stay put while the angle between the vertical rays changes.

With the viewport shape fixed, we can decide which depths it admits. The near and far clipping planes bound that depth. The projection matrix maps the interval into the specified depth range. In the traditional OpenGL example, forward z is negative and depth after division runs from minus one to one. In the Direct3D example here, forward z is positive and depth runs from zero to one.

Move one point from the near plane to the far plane to check the two projection matrices. At the near plane the point reaches the start of that convention's depth range. At the far plane it reaches the end. The displayed matrix uses column vectors. Transpose it when moving to row-vector code to keep the same transformation. Check the coordinate conventions actually selected by the graphics API and camera configuration.

The same split produces a different viewport shape on a wider display. Widen only the display. With horizontal field of view fixed, the side rays keep their directions while the vertical rays draw closer. Projection therefore uses the shape in which the viewport is displayed as well as the number of samples.

Next, predict texture placement from UVs. Under repeat addressing, adding an integer preserves the repeated sample location. A rectangle from five to six and minus one to zero covers one repeat. Wider ranges add repetitions, while changing the directions of UV edges rotates or shears the pattern.

Apply all six sets to the same quad. A spans 1.1 by 1.5 repeats; B is one integer-shifted repeat. C has tilted UV axes, and D shears the pattern. E sends a horizontal screen edge along the vertical UV direction, rotating the image. F covers a larger tilted region, producing many smaller repeats. Inspect the UV differences along two edges.

Keep the shape and white light fixed, then vary only material. Diffuse color controls the body; specular color controls the highlight. With zero specular color there is no highlight regardless of exponent. Smaller exponents spread the highlight, while larger ones tighten it. Distinguish a red body with a white highlight from a blue body with a red highlight.

A and F have zero specular color, leaving red and blue diffuse bodies. H adds a tight pale highlight to red; I adds a broad white highlight; J uses a blue highlight. On a blue body, B has a tighter red highlight than C or E. D uses a darker body, while G removes diffuse reflection entirely. Changing individual terms creates distinct appearances.

Storing a normal in a texture means mapping the three components of its arrow into colour channels. Its horizontal component uses negative and positive values for left and right, but the red channel cannot store negative values. We remap the component range into the colour range. As the arrow leans right, the red swatch brightens. An eight-bit channel rounds to discrete steps, so even the central direction can pick up a small error.

Now tilt the arrow obliquely. Its projections onto the three axes tell us which colour channels change. The same rule is applied independently to each component. The colour stores a direction. Applying a display gamma conversion as if it were paint would tilt the decoded arrow incorrectly.

Finally, recover a model-space direction. Divide RGB by 255, double it, and subtract one to decode the tangent-space normal. Prepare an orthonormal vertex basis, then reconstruct the bitangent using the cross product and handedness sign. Multiply the decoded components by tangent, bitangent, and normal respectively, then add them.

Let's see where the reconstructed normal should point across a mirrored texture. Hold the outward normal and rightward tangent fixed and flip only the handedness sign. The third axis obtained from their cross product reverses with the sign. Even with the same texel, the contribution along that axis is now added the other way, tilting the reconstructed arrow on the surface.

There is one common test when the method is applied to different faces. Locate the tangent, bitangent and normal on each face, then distribute the three decoded components along those axes. The axes follow the face as it turns. Seeing the direction arrow turn with the pattern gives a visible check of the transformation. Normalize the reconstructed direction after quantization and compare it with the light in the same space.

The object we began with now connects to vertices, coordinate spaces, textures, normals, and depth. The vertex shader prepares positions and attributes; rasterization fills the surface; pixel shading and output operations determine what remains visible. To diagnose an image, follow the same route: where the surface is, which way it faces, and how its color was computed.
