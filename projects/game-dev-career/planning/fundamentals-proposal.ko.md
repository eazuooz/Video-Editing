# 게임 개발, 무엇부터 공부해야 할까?

상태: 내용 선택을 위한 조사·제안. 녹음용 대본 아님.
작성: 2026-09-19. BGM: Discovery — Scott Buckley (사용자 선택 완료).

## 이번 영상의 중심

사용자 최신 요청: 포트폴리오 설명은 제외하고, 기획자·프로그래머·2D·3D 아티스트가 실제로 무슨 일을 하고 어떤 기본기를 공부하는지 설명한다. 내용을 먼저 검토받고 대본을 만든다.

핵심 문장: 기본기는 새로운 요구가 생겼을 때 무엇을 바꾸고 왜 바꾸는지 판단하게 해주는 힘이다.

회사·게임 규모·세부 직무에 따라 분담과 요구 역량이 다르다. 아래는 입문 영상의 학습 제안이며 모든 회사의 공통 채용 기준이나 정해진 합격 과정이 아니다. 학습 순서·연습 과제·보물상자 예시는 채널의 구성 제안이다.

## 1. 기획자: 플레이 경험을 규칙과 전달 가능한 설계로 만든다

### 실제 업무
플레이어에게 어떤 선택과 경험을 줄지 정하고, 규칙·보상·난이도·동선·정보 전달을 구체화한다. 프로그래머·아티스트와 구현 범위를 맞추고, 플레이 결과를 관찰하며 고친다. 시스템/전투/레벨/콘텐츠/내러티브 등 분야별 업무는 다르다.

### 기본기와 공부 거리
1. **읽기·논리적 글쓰기·문서 구조**: 목적, 용어, 조건, 동작, 결과, 예외를 구분한다. 표·흐름도·변경 기록으로 동료가 같은 규칙을 이해하게 한다.
2. **규칙을 분해하는 논리력**: 시작/종료 조건, 상태 변화, 자원 소모, 실패 처리, 중복 입력을 생각한다. 문법을 몰라도 조건과 순서를 이해하는 연습이 필요하다.
3. **게임 분석과 가설**: 재미있다/지루하다에서 멈추지 않고, 플레이어의 선택·위험·보상·피드백이 어떻게 연결되는지 설명한다.
4. **수치·스프레드시트**: 비율, 확률, 평균, 기대값, 증가 곡선, 간단한 함수와 그래프. 전투 피해량·성장·경제를 다루는 분야에서는 더 깊어진다.
5. **관찰·소통·수정**: 의도와 관찰을 구분하고, 구현 제약을 듣고, 변경 이유와 영향을 전달한다.

### 영상용 예시
“상자를 열면 좋은 보상을 준다”를 다음 질문으로 구체화한다.
- 어느 거리에서 어떤 입력을 받는가?
- 열쇠가 필요하고 사용 후 사라지는가?
- 가방이 가득 찼다면 어떻게 되는가?
- 이미 열린 상자에 다시 입력하면 어떻게 되는가?

문서작성 능력이란 팀이 이 질문을 같은 뜻으로 이해하게 만드는 능력이라는 설명으로 연결한다. 가정한 수치나 규칙은 교육용 예시라고 분명히 한다.

### 시작 연습
익숙한 기능 하나를 한 페이지로 정리 → 다른 사람이 읽고 질문한 모호한 부분 수정 → 종이/스프레드시트/간단한 시제품으로 규칙 확인.

근거: [ScreenSkills가 개발한 영국 직무 표준 Design games](https://www.ukstandards.org.uk/en/nos-finder/SKSIM7/design-games-)의 설계 문서, 협업, 시제품, 테스트, 게임 경제·진행 체계 항목. 문서 형식과 연습 순서는 채널 제안.

## 2. 프로그래머: 규칙과 데이터를 컴퓨터가 일관되게 처리하게 만든다

### 실제 업무
입력·이동·전투·아이템 같은 기능을 구현하고, 잘못된 동작을 추적하고, 성능과 데이터 처리를 개선한다. 게임플레이/클라이언트, 서버, 그래픽스, 엔진, 도구 개발은 전문성이 다르다.

### 기본기와 공부 거리
1. **기초 C++**: 변수·타입, 조건문·반복문, 함수, 배열·문자열, 구조체·클래스, 참조·포인터, 값과 객체의 수명. 작은 프로그램을 실행하고 상태를 설명한다.
2. **메모리와 자원 관리**: 스택/동적 메모리의 개념, 소유권과 수명, RAII와 스마트 포인터. 포인터 이해와 모든 메모리를 수동으로 관리하는 습관을 혼동하지 않는다.
3. **자료구조**: 배열/vector, 연결 리스트, 스택/큐, 해시 테이블, 트리/그래프. 데이터를 찾고 추가하고 지울 때의 비용과 특성을 비교한다. 직접 구현 학습과 실무 표준 라이브러리 활용을 함께 배운다.
4. **알고리즘·복잡도**: 탐색, 정렬, 재귀, 그래프 탐색, 시간·공간 복잡도. 자료가 늘 때 처리량이 어떻게 달라지는지 이해한다. 경로 탐색은 응용 예시로 짧게 보여준다.
5. **디버깅·검증**: 오류 재현, 중단점, 변수와 호출 흐름 확인, 정상/경계/실패 입력 검사. 원인을 좁혀 수정하고 다시 검증한다.
6. **게임 수학**: 좌표, 벡터, 거리·방향, 보간, 삼각함수. 3D 작업으로 확장하면 행렬·변환 등을 배운다. 서버 등 분야에 따라 수학과 네트워크·운영체제의 우선순위는 달라진다.

### 영상용 예시
상자를 열면 아이템이 인벤토리에 추가된다. “같은 아이템을 어떻게 찾지?”는 자료구조, “두 번 클릭하면 왜 두 개가 생기지?”는 상태와 디버깅, “아이템 수가 늘면 왜 느리지?”는 알고리즘과 측정으로 연결한다.

### 시작 연습
C++ 작은 콘솔 프로그램과 디버거 → 인벤토리 추가·검색·정렬 → 구조별 비용 비교 → 간단한 게임 기능에 적용. 기초를 완벽히 끝낼 때까지 엔진 사용을 금지하는 방식이 아니라, 작은 실습과 기초 복습을 함께 한다.

C++는 이번 영상의 대표 학습 경로다. 모든 게임 직무의 필수 언어라고 말하지 않는다. Unity의 C#, 웹의 JavaScript 등 환경에 맞는 언어를 쓰더라도 자료·흐름·검증의 기초는 이어진다.

근거: [Epic Career Paths](https://www.epicgames.com/site/earlycareers/career-paths)의 프로그래밍 전문 분야·C++·자료구조·알고리즘·수학 안내와 [Microsoft Modern C++](https://learn.microsoft.com/en-us/cpp/cpp/welcome-back-to-cpp-modern-cpp?view=msvc-170)의 수명·RAII·컨테이너·표준 알고리즘. 세부 공부 순서와 게임 예시는 채널 제안.

## 3. 2D 아트: 형태와 시각 정보로 세계를 설계하고 전달한다

### 실제 업무
콘셉트 아트는 캐릭터·배경·소품의 시각 방향을 탐색한다. 일러스트, 스프라이트, UI 등은 각기 다른 용도의 결과물을 만든다. 이 분야들을 모두 같은 업무로 묶지 않는다.

### 기본기와 공부 거리
1. **관찰과 드로잉**: 윤곽을 베끼는 데서 나아가 길이·각도·비율·빈 공간·실루엣을 비교한다.
2. **도형화·입체 이해**: 복잡한 대상에서 구·상자·원기둥 같은 큰 덩어리를 찾고 방향과 겹침을 이해한다. 사람도 머리·흉곽·골반과 팔다리의 큰 형태부터 본다.
3. **원근·비례**: 다른 방향에서도 형태가 유지되도록 공간과 축을 이해한다. 캐릭터 분야는 인체 구조·제스처, 배경은 공간·건축·환경 관찰로 심화한다.
4. **명암·색·재질**: 빛의 방향, 면의 밝기, 색 관계, 재질 차이. 세부 묘사 전에 큰 명암 덩어리를 읽는다.
5. **구도·시각적 전달**: 먼저 볼 곳, 실루엣의 차이, 작은 화면에서의 구분, 주변 요소와의 대비를 설계한다.

### 영상용 예시
보물상자를 상자+뚜껑의 단순 입체로 분해 → 원근과 비율 정리 → 빛과 명암 → 재질·장식 → 실제 게임 크기로 줄여 구분되는지 확인.

### 시작 연습
주변 사물을 큰 도형으로 관찰 → 여러 방향의 간단한 덩어리 → 흑백 명암 → 색과 구도 → 원하는 아트 분야에 적용. 캐릭터만 그리는 고정 코스로 제시하지 않는다.

근거: [Riot의 분야별 안내](https://www.riotgames.com/en/portfolio-and-reel-suggestions)의 비례·인체·색·빛·실루엣·구도와 [ScreenSkills 게임 콘셉트 아티스트 직무](https://www.screenskills.com/job-profiles/browse/games/art/concept-artist-games/)의 드로잉·구도·요구 해석. 도형화 시연과 학습 순서는 이 원리들을 설명하기 위한 채널 제안.

## 4. 3D 아트: 형태를 입체와 표면으로 만들고 게임 환경에 맞춘다

### 실제 업무
캐릭터, 소품, 배경 등의 모델과 표면을 만든다. 모델링·텍스처링·리깅·애니메이션·라이팅은 팀에 따라 나뉜다. 이번 입문 설명은 게임용 모델·소품 제작을 중심으로 한다.

### 기본기와 공부 거리
1. **형태·비례·공간 감각**: 앞에서만 괜찮은 모델이 아니라 여러 각도에서 자연스러운 덩어리를 이해한다. 2D와 관찰·조형의 기초를 공유한다.
2. **모델링·토폴로지**: 큰 형태를 먼저 만들고 면 구조를 정리한다. 움직임·변형·실루엣에 맞는 구조가 무엇인지 배운다.
3. **UV·텍스처·재질**: 표면을 펼치는 UV, 표면 정보를 담는 텍스처, 빛에 어떻게 반응할지 결정하는 재질을 구분한다.
4. **노멀·빛·표면 읽기**: 면 방향과 표면의 빛 반응을 이해하고 의도하지 않은 음영을 점검한다.
5. **게임에 넣는 기초**: 크기 단위, 축과 원점/피벗, 내보내기, 실제 엔진 카메라에서 확인. 목표 플랫폼에 맞춰 기하와 텍스처 비용을 조절한다.

### 영상용 예시
같은 상자를 단순 입체로 제작 → 뚜껑의 회전축 설정 → 와이어프레임·UV·재질 확인 → 게임 장면에서 열기. 장식보다 비례와 회전축이 어긋날 때 생기는 문제를 비교한다.

### 시작 연습
상자·통 같은 소품의 큰 비율 → 여러 각도 점검 → 면 구조와 UV → 재질·조명 → 엔진에서 확인. 캐릭터를 원하면 인체·변형, 배경을 원하면 공간·모듈 구성으로 심화한다.

모든 3D 아티스트에게 전문 일러스트레이터 수준의 손그림을 요구하지 않는다. 공유되는 핵심은 형태를 관찰하고 입체적으로 판단하는 기본기다. 폴리곤 수가 낮을수록 무조건 좋다는 식으로 설명하지 않는다.

근거: [Riot의 3D Character / Environment 안내](https://www.riotgames.com/en/portfolio-and-reel-suggestions), [Epic의 Art 전문 분야 안내](https://www.epicgames.com/site/earlycareers/career-paths). 소품 제작의 구체적인 과정과 비교 장면은 채널 제안.

## 영상 구성 제안 — 약 8~10분, 확정 전

1. 도입: 게임을 좋아하는데 무엇부터 공부해야 할까?
2. 보물상자 하나를 네 직무가 함께 만드는 장면.
3. 기획: 막연한 요구를 조건·결과·예외가 있는 문서로 바꾸기.
4. 프로그래밍: C++로 데이터와 실행 흐름 이해하기.
5. 프로그래밍: 자료구조·알고리즘·디버깅이 게임 문제에 쓰이는 이유.
6. 2D: 도형화에서 비례·원근·명암·가독성으로.
7. 3D: 큰 형태에서 면·표면·게임 내 동작으로.
8. 공통 기본기: 관찰, 질문, 피드백, 수정, 팀에 전달하기.
9. 결론: 오늘 작은 기능·한 페이지의 규칙·사물 한 점부터 연습하기.

프로그래밍에 씬을 두 개 배정하더라도 최종 시간 비중이 과도해지지 않게 조절한다. 각 분야는 실제 업무 → 기본기 → 화면 예시 → 첫 연습의 같은 흐름으로 설명한다.

## 결정할 내용

주제와 학습 범위 선택을 받은 뒤 녹음용 대본, 독립 씬, TTS 샘플을 작성한다. 현재 TTS·본편·자막은 생성하지 않았다. 기존 템플릿의 3개 씬과 길이는 제작 결과가 아닌 시작 파일이다.
