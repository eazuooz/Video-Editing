## 생성 결과를 게임용 데이터로 정리하기

<b>메시(mesh)</b>는 표면을 구성하는 점과 면입니다. 캐릭터 생성 원본에는 약 194만 개의 삼각형이 있었습니다. 이번에는 이를 목표 1만 면으로 정리해 실제 결과 9,968개의 사각형 면과 9,428개의 정점을 얻었습니다. 헤드폰은 약 191만 삼각형에서 2,000삼각형으로 정리했습니다. 캐릭터의 전후 숫자는 삼각형과 사각형이라는 단위가 다르므로 단순히 같은 종류의 면 수처럼 나누지 않습니다.

작은 방에서 카메라가 보는 실루엣이 유지되는지 확인하면서 필요한 복잡도를 정하는 것이 목적입니다. 면을 줄였다고 손이나 귀의 형태가 무너지면 사용할 수 없습니다. 반대로 소품이 작게 보이는데 원본의 수백만 면을 계속 유지하면 브라우저가 처리할 데이터만 커집니다.

<image source="file-upload://41b0b1ff-a61e-8108-b8e1-00b28e74d8a3">목표 10K와 실제 9,968개 사각형 면. 생성 원본과 게임용 메시를 구별한다. — 영상 02:50.25</image>

<b>텍스처(texture)</b>는 그 표면이 보이는 방식을 정하는 이미지입니다. 색과 데이터 맵도 역할이 다릅니다.

| 맵 | 쉬운 설명 | 확인할 점 |
|---|---|---|
| Base Color | 표면의 기본 색 | 밝은 조명이 이미 그려져 있지 않은가 |
| Normal | 작은 요철의 방향 | 채널 규격과 색 공간을 맞췄는가 |
| Roughness | 반사가 넓게 퍼지는 정도 | 매끈함 값과 거칠기 값을 혼동하지 않았는가 |
| Metallic | 금속인 영역 | 천이나 피부가 금속처럼 반사하지 않는가 |

이번에 연결한 색 원본은 4K입니다. 모든 맵이 무조건 같은 4K 규격이라는 뜻은 아닙니다. 노멀과 거칠기 같은 데이터 맵을 일반 색 그림처럼 처리하거나, Roughness를 Smoothness와 같은 값으로 넣으면 표면 느낌이 달라집니다.

### 상태 자료와 처리 순서

행동 상태에는 현재 단계, 목적 행동, 진입 기준점, 접촉 가중치가 필요합니다. 다음은 같은 구조를 구현할 때 사용할 수 있는 의사코드입니다. 실제 API 이름과 프로젝트 코드는 다를 수 있습니다.

```txt
requestAction(next):
  pending = next
  if phase is Seated or Reclined:
    phase = Exit        // 책/손 정리와 기존 일어나기 클립
  else if phase is Idle:
    phase = Walk

update():
  Walk  -> 목적지 앞에 도착하면 Align
  Align -> 방향이 맞으면 Enter
  Enter -> 기존 앉기/눕기 클립이 끝나면 Loop
  Loop  -> 생활 동작과 작은 접촉 보정
  Exit  -> 안전한 바닥 자세가 되면 pending으로 Walk
```

움직임 도중 또 버튼을 눌러도 몸을 즉시 다른 자리로 옮기지 않습니다. 다음 요청을 보관하고 Exit를 마친 뒤 전환합니다. 걷기 속도는 기존 클립의 Root Motion과 실제 이동 거리를 함께 보면서 맞춥니다. 다리 주기만 빠르게 돌리면 발이 바닥에서 미끄러집니다.

## 차분하게 앉는 동작은 속도만의 문제가 아니다

가구는 겉모양보다 접촉 기준을 먼저 정합니다. 아이맥 앞 의자의 낮은 등받이는 약 37cm이고 모니터도 낮게 배치했습니다. 의자 좌면, 골반, 발바닥이 놓일 바닥, 키보드에 닿을 손의 기준점을 따로 둡니다. 캐릭터를 기준으로 가구 크기를 맞춘 뒤 같은 기준점으로 접근·회전·착석을 연결해야 합니다.

아이맥 의자에 앉는 동작은 약 0.8초의 원본 앉기 클립을 상태 속도 0.36으로 재생해 약 2.22초 동안 앉게 했습니다. 의자에 방향을 맞추는 구간과 앉은 뒤 자세를 정리하는 구간도 이어 주었습니다. 골반 위치 보정이 한 프레임에 들어가지 않도록 가중치를 서서히 올리는 것이 핵심입니다.

진행 비율을 0에서 1 사이인 u라고 하면 보정 곡선은 다음과 같습니다.

```text
w = 6u⁵ − 15u⁴ + 10u³
```

w는 원래 동작과 의자 접촉 위치 사이를 섞는 비율입니다. 이 곡선은 시작과 끝에서 변화 속도가 0이 되므로, 보정을 켜고 끄는 순간이 덜 드러납니다. 실제 접촉은 옆과 앞 시점에서 확인해야 합니다. 수치가 매끄러워도 무릎이 책상을 뚫으면 완성된 동작은 아닙니다.



### 등과 다리를 받쳐 주는 소파 독서

독서용 소파와 테이블은 각각의 단독 입력 이미지를 만들어 Tripo H3.1로 생성했습니다. 밝은 목재 프레임과 크림색 라탄/코드 짜임을 맞추고, 소파는 Triangle 목표 20K에서 Tripo 표시 22,066삼각형, Unity 임포트 메시 22,062삼각형이며, 테이블은 목표 10K에서 9,375삼각형으로 정리했습니다. 두 가구의 생성·정리는 각각 90크레딧, 합계 180크레딧이며 캐릭터·헤드폰 175와 고양이 90은 별도입니다. 실제 출력 맵은 두 가구 모두 Base Color 4096×4096, Normal 2048×2048입니다. 소파는 폭 1.85m·높이 0.92m, 테이블은 폭 1.25m·높이 0.44m로 맞췄습니다.

몸은 PHILIPP 팩의 `Tourist_sit_03` 휴식 클립으로 기대고 다리를 편 자세를 유지합니다. 손을 머리 뒤에 둔 원래 팔은 그대로 독서에 쓰기 어려우므로, `Tourist_sit_02_Map`의 팔만 Avatar Mask로 섞습니다. Avatar Mask는 추가 애니메이션이 영향을 줄 인체 부위를 고르는 기능입니다. 왼팔·오른팔·손가락만 선택하고, 몸통과 다리는 기본 휴식 동작을 유지합니다.

접근 → 방향 맞춤 → KayKit 착석 → 휴식 자세 → 발 올리기 → 책 펼치기로 이어집니다. 약 1.8초 동안 발을 테이블 뒤에서 위로 들고, 상판 위로 뻗은 뒤 뒤꿈치를 내립니다. 일어날 때는 반대로 발을 먼저 거둡니다. 골반에서 발목까지의 실제 길이를 재어 목표점을 잡습니다. 이 장면에서는 다리 도달 범위를 벗어나던 소파 로컬 앞쪽 0.84m 대신 0.73m에 목표점을 두었습니다. 다른 행동을 누르면 책을 먼저 내리고 기존 기립 클립 뒤에 걷기를 연결합니다. 테이블을 통과하지 않도록 열린 옆쪽 통로로 접근합니다. 골반·등받이·테이블 상판·발바닥을 같은 가구 좌표에서 확인한 후 책과 손을 맞춥니다.

### 책과 손을 함께 배치하는 이유

책의 위치만 움직이면 손이 표지 안으로 들어가거나 팔이 페이지를 가로지를 수 있습니다. 책을 먼저 고정 각도로 놓기보다 가슴과 얼굴을 기준으로 책의 자세를 만들고, 그 자세에서 손목과 팔꿈치의 목표를 함께 계산합니다.

책의 가로축은 소파의 좌우 방향을 기준으로 안정시키고, 몸 위치 보정량을 책에도 함께 적용합니다. 몸의 기울기를 그대로 책 가로축에 쓰면 한쪽 손이 지나치게 위로 올라갈 수 있기 때문입니다. 페이지의 법선은 책 중심에서 얼굴로 향하는 방향을 가로축에 수직이 되게 정리합니다. 손목은 이 책 좌표계의 왼쪽과 오른쪽 표지 바깥에 둡니다. 팔꿈치는 몸 밖으로 유도해 팔뚝이 책을 관통하지 않도록 합니다.

현재 장면에서는 가슴의 기본 위치에 몸 보정량을 더한 뒤 소파 앞쪽 약 0.34m, 위쪽 약 0.07m에 책 중심을 잡고, 손목은 책 로컬 좌표의 좌우 약 0.20m에 둡니다. 캐릭터와 책 크기가 바뀌면 이 값도 다시 측정해야 합니다. 숫자만 복사하면 다른 체형에 같은 접촉이 나오지 않습니다.

손의 회전도 맞춰야 합니다. Unity Humanoid의 IK 목표 회전과 손목 뼈의 회전 기준은 그대로 같지 않을 수 있습니다. 현재 클립에서 측정한 손바닥 기준 프레임을 역으로 제거한 뒤 목표 프레임을 적용합니다.

```txt
goalRotation = targetPalmFrame * inverse(measuredPalmFrame) * currentIKGoalRotation
```

세 회전은 같은 월드 기준으로 계산하고 곱하는 순서를 유지합니다. 손바닥의 앞뒤와 손가락 방향이 뒤집히면 손이 닿더라도 잡는 모습이 어색합니다. 완성 여부는 정면·옆면·반대쪽에서 손목, 페이지, 팔꿈치의 간격을 보면서 판단합니다. 기존 전신 클립은 유지하고 책을 잡는 데 필요한 부분만 보정하는 이유입니다.

## 웹에서는 입력과 저장도 실제로 확인하기

PC 실행본의 메모는 로컬 UTF-8 JSON 파일에 자동 저장하고 이전 파일을 복구용으로 남깁니다. 웹 버전의 메모는 같은 주소와 브라우저의 localStorage에 저장합니다. 브라우저 데이터를 지우거나 주소가 달라지면 이전 메모가 보이지 않을 수 있습니다. 서버에 메모를 보내는 기능은 없습니다.

Unity가 키보드를 먼저 받아 가면 화면의 HTML 메모장에 한글을 입력하지 못할 수 있습니다. 입력창을 편집하는 동안 게임 단축키와 키보드 이벤트를 분리하고, 한글·줄바꿈·C/B/V 같은 단축키 문자를 실제로 입력해 확인했습니다. 저장 표시만 보지 않고 새로고침 후 내용이 같은지도 확인합니다.

집중 타이머는 매 프레임 1씩 줄이는 구조 대신 끝나는 시각을 저장합니다. 현재 남은 시간은 <b>종료 시각 − 현재 시각</b>으로 계산합니다. 브라우저가 뒤쪽 탭을 느리게 실행해도 표시가 원래 시간으로 돌아오게 하기 위한 방법입니다. 운영체제 시계를 바꾸면 시각 기준 타이머에도 영향이 있다는 한계는 남습니다.

### 따라 만들기 요청 · Unity Web + Codex / web-build

입력: 같은 에디터 버전의 Web Build Support와 현재 씬

```txt
현재 씬만 Unity WebGL 빌드로 묶어줘. 브라우저에서 시작 버튼을 누른 뒤 오디오를 켜고 로딩·재시도 UI를 넣어줘. 결과는 HTTP 서버로 실행하고 파일 캐시가 이전 빌드를 보여주지 않게 버전과 해시를 관리해줘. 독서·비·음악·메모·집중 타이머를 실제 브라우저에서 확인해줘.
```

받을 결과: 브라우저에서 실행하는 게임

확인할 점: WASM·데이터·압축 로딩, 클릭 입력, 오디오와 저장


웹 빌드는 WebGL 2와 WebAssembly로 실행됩니다. 로딩 진행·재시도 UI를 넣고, 브라우저의 자동재생 제한에 맞춰 시작 버튼 뒤에서 소리를 연결했습니다. 빌드 성공만으로 플레이 검수가 끝나는 것은 아닙니다. 실제 HTTP 주소에서 앉기·독서·일어나기, 음량, 메모 재실행을 확인해야 합니다. 현 검수는 이 컴퓨터의 데스크톱 브라우저 기준이며, 휴대폰 기기에서의 성능은 별도 확인 대상입니다.

## 실패를 빠르게 분리하는 검증 순서

| 보이는 문제 | 먼저 분리할 원인 | 직접 확인 |
| --- | --- | --- |
| 손과 책이 겹침 | 책 좌표와 IK 손목 기준 | 앞·옆·반대 시점, 전환 중간 |
| 걷는데 미끄러짐 | 보폭·실제 이동량·클립 속도 | 발 접촉점을 바닥 기준으로 관찰 |
| 털이 얼룩처럼 반복됨 | UV/무늬 좌표·거칠기 | 같은 조명에서 머리와 몸통 비교 |
| 비 버튼만 켜짐 | 입력 중복·활성 상태·레이어 | 한 클릭에 한 번 변화, 실제 창문 확인 |

최소 장면에서 시작해 한 동작씩 추가하고, 같은 카메라와 같은 입력으로 다시 확인합니다. AI에는 “자연스럽게”라는 평가와 함께 <b>어느 대상이 어디를 관통하는지, 어떤 상태에서 무엇이 남아야 하는지</b>를 전달하면 수정 범위가 구체적이 됩니다.

## 직접 바꿔 볼 세 가지

1. 의자 높이를 5cm 바꾸고 발·골반·손 중 무엇이 먼저 어긋나는지 확인합니다. 가구의 겉모양과 접촉 기준을 구별하는 연습입니다.
2. 앉기 클립 속도는 그대로 두고 위치 보정 곡선만 바꿔 비교합니다. 급하게 느껴지는 원인이 몸의 모션인지 접촉 보정인지 분리할 수 있습니다.
3. 메모를 쓰고 탭을 닫았다 다시 엽니다. 화면 반응과 실제 데이터 보존을 따로 확인하는 습관을 만듭니다.

디자인을 맞추고, 모델과 움직임을 다듬고, 조작과 저장을 연결합니다. 이번 방은 이 세 단계가 이어질 때 이미지가 플레이 가능한 공간이 되는 사례입니다.
