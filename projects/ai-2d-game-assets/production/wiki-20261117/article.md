## 1. 생성 → 정리 → 게임에서 검수하기

한 장의 캐릭터가 마음에 들어도, 옆모습에서 가방이 반대로 붙거나 걷는 동안 얼굴이 바뀌면 게임에 그대로 사용할 수 없다. 먼저 바뀌면 안 되는 특징을 정한다. 이번에는 노란 머리핀, 청록색 재킷, 갈색 가방과 같은 디자인을 기준으로 삼았다.

그다음 실제로 필요한 자세를 만든다. 걷기와 앉기, 지도 읽기와 필기는 각자 다른 실루엣과 접촉점을 가진다. 마지막에는 모든 자세의 픽셀 크기·색·발 기준점과 배경 사물의 크기를 맞춘다. 이 순서에서 이미지 생성 도구는 후보를 만들고, 후처리 도구는 규격을 정리하며, 게임 코드는 행동과 입력을 연결한다.

## 2. 캐릭터 설정화와 LoRA를 구별하기

**Turnaround Sheet(방향별 설정화)**는 정면·측면·후면에서 같은 디자인을 확인하는 그림이다. 머리핀의 좌우, 등에 이어지는 가방 끈, 소매와 신발, 몸의 비율을 나란히 본다. 방향만 바꾼다는 요청을 해도 이 검수는 필요하다.

다른 동작을 확장할 때는 기준 그림을 다시 참조하고, 바뀌면 안 되는 요소를 요청문에 남긴다. 다음은 이 작업에 응용할 수 있는 요청문이다.

```text
Use the attached character as the design reference.
Keep the same face, hairstyle, yellow hairpin, teal jacket,
brown bag, clothing details, palette and body proportions.
Show the requested action clearly on a plain background.
Preserve the character design and keep both feet visible.
```

**LoRA(Low-Rank Adaptation)**는 이미지 폴더가 아니라 기본 모델에 더할 변화량을 적은 학습 파라미터로 표현하는 어댑터다. 이미지와 캡션은 학습 재료이고, 학습한 LoRA 파일이 결과다. 캐릭터 LoRA는 누구를 그릴지, 스타일 LoRA는 어떤 표현으로 그릴지를 나누어 다룰 수 있다.

학습을 선택한다면 생성에 쓸 기본 모델과 맞는 구성을 고르고, 방향과 자세가 다양한 정확한 디자인을 모은다. 정면만 많거나 잘못된 가방이 섞인 자료는 장수가 많아도 도움이 되지 않는다. 검수한 20~50장은 첫 실험을 위한 제안 범위이며 보장된 필요 수량이 아니다. 이번 완성 방의 동작 확장은 기준 이미지 참조로 진행했고, 캐릭터 전용 LoRA를 새로 학습한 결과로 소개하지 않았다.

## 3. ComfyUI에서 입력과 결과를 나누기

Checkpoint(체크포인트)는 기본 이미지 모델이다. 해당 계열과 맞는 픽셀 스타일 LoRA를 연결하고, 준비된 캐릭터 LoRA가 있다면 다음 LoRA 노드로 이어 붙인다. LoRA 노드의 모델 경로와 CLIP 경로를 함께 연결해야 모델과 문장 해석에 설정이 전달된다.

```text
Checkpoint
  → Style LoRA
  → Character LoRA (학습 파일이 준비된 경우)
  → Text conditioning + latent image
  → Sampler
  → VAE Decode
  → Pixel-size / palette / alpha processing
  → Save
```

비교할 때는 프롬프트·해상도·시드를 유지하고 LoRA 강도 하나부터 바꾼다. Seed(시드)는 무작위 값의 출발점을 정하지만 캐릭터의 모든 장식을 고정하는 장치는 아니다. 스타일을 강하게 적용하면 도트 느낌이 살아나도 얼굴이나 작은 장식은 뭉개질 수 있다. 지켜야 할 디자인을 보며 강도를 고른다.

## 4. 도트처럼 보이는 그림을 실제 픽셀 규격으로 정리하기

픽셀아트에서는 작은 논리 해상도의 한 칸이 윤곽을 결정한다. 생성 그림을 확대했을 때 칸의 폭이 불규칙하거나 경계에 흐린 색이 끼어 있다면, 먼저 게임에서 쓸 논리 해상도를 정해야 한다.

PixelArt SakuLike ILXL의 8배 표현을 다루는 예에서는 768×1344를 96×168로 축소하는 방법을 비교했다. **이 규격과 완성 게임 캐릭터의 96×132 규격은 서로 다른 입력의 처리 결과**다. 모든 그림에 8배 축소나 같은 세로 크기를 강제하는 규칙이 아니다.

완성 게임에서는 PixelOE로 윤곽을 정리한 뒤 같은 캐릭터의 자세들에 공통 32색 팔레트를 적용하고, 반투명한 가장자리를 정리했다. 프레임마다 색을 따로 줄이면 옷의 색이 깜빡일 수 있으므로 공통 팔레트를 먼저 비교한다. 후단의 색상 맞춤에서 색 수가 늘어날 수 있으니 필요한 최종 제한은 마지막 출력에서도 확인한다.

{{frame:pixels}}

### 알파와 확대 방식

투명 배경은 실제 알파 값이 비어 있어야 한다. 그림 속에 체크무늬가 그려진 것과 구분하고, 밝고 어두운 배경 위에서 흰 테두리와 남은 픽셀을 찾는다. 전체 화면을 키울 때는 Nearest Neighbor(최근접 보간)로 이웃 색을 섞지 않게 한다. 다만 최근접 보간만으로 원래 그림의 불규칙한 격자가 고쳐지지는 않는다.

Unity로 옮긴다면 Sprite 임포트의 Point 필터, 같은 Pixels Per Unit(게임 한 단위의 픽셀 수), 공통 Pivot(배치·회전 기준점)을 확인한다. 이번 완성본은 브라우저 Canvas에서 논리 픽셀과 발 기준점을 유지하도록 구현했다.

## 5. 같은 방으로 배경과 캐릭터의 크기 맞추기

배경과 캐릭터를 따로 생성하면 색과 사물의 크기가 어긋나기 쉽다. 캐릭터가 들어 있는 장면을 기준으로 Outpainting(바깥 영역 확장)을 하고, 배경 레이어에서는 캐릭터를 제거해 움직일 자리를 확보한다. 그 뒤 창틀·책장·바닥의 격자와 의자의 높이를 다시 본다.

앉은 모습을 맞출 때는 키만 비교하면 부족하다. 좌판에 닿는 것은 엉덩이 아래 윤곽이고, 발은 바닥에 닿아야 한다. 서 있는 자세와 앉은 자세에 같은 배율을 적용한 채 접촉점을 맞춘다. 자세마다 그림을 따로 확대하면 앉는 순간 몸집이 바뀐다.

## 6. 걷기와 중간 동작을 조립하기

다리 모양이 비슷한 두 그림을 번갈아 보여 주는 것만으로는 걷기가 읽히지 않았다. 발이 닿는 자세, 체중을 싣는 자세, 반대 발이 지나가는 자세를 양쪽 다리에 나누어 여덟 단계로 다시 준비했다.

발이 바닥을 지지하는 동안 몸이 앞으로 간 만큼 그 발은 몸의 뒤쪽으로 이동해야 한다. 한 주기의 이동 거리를 약 83픽셀로 맞췄고, 이전의 38픽셀 설정에서 과하게 반복되던 걸음 수를 줄였다. 이 수치는 이번 리소스에서 확인한 값이다.

거리를 기준으로 재생하려면 다음 관계를 사용할 수 있다.

$$
\phi = \operatorname{frac}\!\left(\frac{d}{s}\right), \qquad i=\lfloor N\phi\rfloor
$$

$d$는 누적 이동 거리, $s$는 같은 단위로 나타낸 한 보행 주기의 이동 거리, $N$은 프레임 수, $\phi$는 한 주기 안의 위치, $i$는 재생할 프레임 번호다. 화면을 그린 횟수 대신 실제 이동량으로 다음 자세를 고르므로 멈추면 걸음도 멈춘다.

### 행동이 바뀔 때도 그림 사이를 연결하기

게임의 행동 순서는 `이동 → 도착 자세 → 행동 반복 → 정리 → 다시 이동`이다. 의자에서는 몸을 낮추고, 책을 읽기 전에는 꺼내 펼치며, 이동하기 전에는 책을 정리한다. 2dimg2motion의 지도 읽기는 받치기·경로 짚기·다시 잡기의 주요 자세를 먼저 정하고 사이 프레임을 준비했다. 14장이 있다는 사실 외에도 발 기준선, 주요 자세, 처음과 끝의 반복 연결을 확인했다.

sprite-gen으로 시트를 분리할 때는 각 프레임의 외곽선 상자 가운데를 새 피벗으로 잡지 않는다. 팔을 뻗을 때 외곽 상자가 커지면 몸통까지 밀릴 수 있기 때문이다. 원래 셀의 공통 기준점으로 맞춘다. Agent Sprite Forge에서는 이 프레임들의 순서와 머무는 시간을 함께 보관해 다른 재생 환경에서도 같은 동작을 구성하게 했다.

## 7. 효과·부분 움직임·팔레트에 맞는 도구 쓰기

**pixelfx**의 불꽃·비·눈은 시간에 따라 코드가 픽셀을 그리는 효과다. 투명한 프레임뿐 아니라 재생 시간과 위치 정보도 함께 다룬다. 비와 눈은 창문 영역 안에서 그리고 창틀을 다시 앞에 그린다. 같은 효과라도 레이어와 범위가 맞아야 방 안을 뚫고 내리지 않는다.

밤의 불꽃은 랜턴 안 심지와 촛불의 기준점에 놓고, 같은 위치에서 따뜻한 빛을 더했다. 배경색을 어둡게 만드는 것과 실제 광원이 있어 보이게 만드는 일을 나누어 확인했다.

{{frame:weather}}

**Codixel**에서는 같은 그림의 목 기준점과 머리에 속하는 픽셀을 정해 머리만 작은 각도로 움직였다. 책과 발까지 흔드는 대신, 움직여야 할 부분을 골랐다. 그림에 없는 뒷면이 필요하다면 별도 이미지가 필요하다.

**Pixelbolt**에서는 JSON 레시피의 색과 프레임을 제어했다. 정령은 같은 모양에서 비·눈·밤에 맞는 팔레트로 바뀌고, 원래의 깜빡임과 프레임 머무는 시간은 유지한다. 작은 소품이나 아이콘처럼 수정 범위가 명확한 자산에 유용하다.

{{frame:rig}}

Sprite Sheet Diffusion은 참조 그림과 포즈 순서를 조건으로 사용하는 연구다. 이번 설치에서는 공개 모델 세 개를 확보했지만 실행에 필요한 포즈 가이더와 이미지 인코더 경로를 완성하지 못해 생성 결과를 방에 넣지 않았다. 설치 파일을 받은 상태와 실제 추론에 성공한 상태를 작업 기록에서 구분했다.

## 8. 필기·레이어·메모·라디오를 게임으로 연결하기

작업대는 화면 앞쪽 가운데로 옮기고 방 전체의 화면비와 캐릭터 크기를 유지했다. 접근해서 몸을 낮추고, 장부에 손을 짚고, 펜을 내리는 순서로 연결했다. 필기 반복에서는 몸 전체보다 팔과 펜의 작은 움직임을 사용한다.

그리기 순서는 의미에 맞게 나눈다. 의자 뒤쪽과 캐릭터 다리, 책상 앞부분, 책상 위의 손·펜·장부를 필요한 순서로 그려야 실제로 앉아 쓰는 관계가 보인다. 단순히 캐릭터 전체를 책상 앞이나 뒤로 보내면 어느 한쪽이 어긋난다.

{{frame:writing}}

기록하기에서는 화면 안 메모에 500자까지 적고 저장할 수 있다. 기록은 같은 주소와 브라우저의 저장소에 남으며 다른 기기로 자동 전송되지 않는다. 작업실 라디오에는 HoliznaCC0가 CC0로 배포한 로파이 20곡을 넣어 다음 곡·섞기·음량과 반복 재생을 연결했다.

- 논리 픽셀 크기·팔레트·알파·발 기준점이 동작마다 유지되는가?
- 의자·책상과 몸의 접촉점, 앞뒤 레이어가 맞는가?
- 정상 속도와 프레임 관찰에서 발 미끄러짐·크기 변화·반복 이음새가 보이지 않는가?
- 클릭 후 이동·중간 자세·행동·정리 순서와 메모 저장을 실제 브라우저에서 확인했는가?

응용 과제로는 같은 캐릭터의 행동 하나를 정해 주요 자세를 만들고, 공통 피벗·팔레트·알파를 유지한 채 전환을 연결해 보면 좋다. 입력 이미지, 생성 설정, 최종 프레임과 재생 메타데이터를 함께 보관하면 어긋난 단계를 다시 고치기 쉽다.

이미지와 모델·학습 데이터·출력물, 공개 코드와 연결된 생성 서비스는 이용 조건과 비용이 각각 다르다. 프로젝트 기록에는 실제 사용한 버전과 출처를 남기고, 코드의 공개 라이선스로 다른 사람의 캐릭터나 별도 서비스의 조건까지 해결됐다고 보지 않는다.
