# DX12 프레임 동기화와 ImGui 렌더링

전체 한국어 대본 초안입니다. 예상 10~14분이며 실제 음성 길이는 아직 측정하지 않았습니다. 이 문서는 대사를 전부 읽으면서 실제 화면과 흰색 2.5D 설명의 연결을 검토하는 용도입니다.

이 편에서 기억할 내용은 다음과 같습니다. **재사용할 공간의 이전 GPU 사용이 끝났는지 먼저 확인한다.** [해당 노션 강의](https://www.notion.so/3400b1ffa61e8054a80bc1d4b575b515)와 현재 소스의 구현을 대조했습니다. 대본·목소리·음악 승인은 각각 대기 상태입니다.

장면 시간과 실제 개발 화면 60%·설명 40%는 계획값입니다. 촬영과 승인 음성 이후 다시 맞추며, 시간에 맞추려고 반복·저속 재생·정지 화면을 늘리지 않습니다. 각 장면은 실제 예시 뒤 원리 설명으로 이어지는 독립 Motion Canvas 씬을 계획합니다.

### 전체 내레이션

게임 엔진에서 화면이 한 번 잘 나왔다고 해서, 렌더링이 끝난 건 아닙니다.

똑같은 코드인데 어떤 때는 정상이고, 어떤 때는 화면이 깨진다면 무엇부터 확인해야 할까요?

오늘은 얌얌엔진의 디엑스 십이 코드로, 시피유와 지피유가 같은 메모리를 안전하게 사용하는 방법을 살펴보겠습니다.

먼저 기억할 문장은 하나입니다. 시피유가 일을 보냈다는 것과, 지피유가 그 일을 끝냈다는 것은 다릅니다.

우리는 명령을 적는 공간을 두 개 준비하고, 다시 쓸 공간의 이전 작업이 끝났는지 확인할 겁니다.

그다음 게임 화면 위에 에디터를 그리고, 탭을 별도 창으로 꺼냈을 때까지 완료 확인이 이어지게 만들겠습니다.

함수 이름을 외우기 전에, 화면 뒤에서 어떤 순서가 지켜져야 하는지부터 보죠.

### 실제 예시와 촬영 지시

### 흰색 2.5D 설명 연출

흰 바닥 위에 두께가 있는 CPU 작업판과 GPU 작업판을 비스듬히 배치한다. CPU의 제출 도장이 먼저 찍히지만 GPU의 실행 막대는 아직 이동 중이다. '보냄'과 '끝남'의 간격을 카메라가 옆으로 이동하며 보여준다.

화면 핵심 문구는 **제출 ≠ 완료**입니다.

- 1~3행: 실제 코드와 엔진 참고 화면
- 4~7행: CPU/GPU 판의 시간 차이를 애니메이션으로 보여준다

## 장면 02 명령의 기록과 제출과 완료

계획 구간 0:47~1:47. 실제 개발 자료 30초, 자체 설명 30초. 확정 타임코드가 아닙니다.

### 전체 내레이션

시피유는 게임 속 물체의 위치를 계산하고, 무엇을 어떻게 그릴지 명령을 준비합니다.

여기서 드로우 함수를 호출해도 지피유가 그 자리에서 그림을 다 그리는 건 아닙니다.

먼저 커맨드 리스트에 그릴 일을 기록합니다. 작업 지시서를 작성하는 단계라고 생각하면 됩니다.

기록을 끝낸 리스트를 커맨드 큐에 제출하면, 지피유가 앞선 작업과 필요한 의존성을 처리하며 실행합니다.

시피유는 제출 함수에서 돌아온 뒤에도 다음 일을 할 수 있습니다. 그동안 지피유는 이전 그림을 그리고 있을 수 있죠.

그래서 기록, 제출, 완료라는 세 시점을 구분해야 합니다.

얌얌엔진에서도 드로우 호출과 리스트 제출은 다른 함수에 있습니다. 코드의 호출 순서를 따라가면 이 구분이 보입니다.

드로우 호출 옆에 완료 표시를 붙이면 너무 이릅니다. 제출 직후에도 완료를 확인할 근거가 따로 필요합니다.

그리고 명령을 적어 둔 메모리에는 수명이 있습니다. 지피유가 그 명령을 모두 사용하기 전까지 내용이 유지되어야 합니다.

### 실제 예시와 촬영 지시

DrawIndexedInstanced에서 ExcuteCommandList로 실제 정의 이동. 각 호출이 기록인지 제출인지 한 줄씩 강조한다. 실행 녹화 때는 실제 호출 스택/브레이크포인트만 사용하고 GPU 실행 중이라는 가짜 debugger 값은 만들지 않는다.

### 흰색 2.5D 설명 연출

명령 카드가 공중의 '기록' 층에서 'Queue 제출' 레일로 내려가고 GPU 실행 기계로 이동한다. 각 단계의 수직 높이를 달리한다. CPU 커서는 다음 카드로 먼저 이동하고 GPU는 앞 카드를 처리해 시간 차이를 보여준다.

화면 핵심 문구는 **기록 → 제출 → 실행 완료**입니다.

- 1~5행: 실제 함수 추적→명령 카드 이동
- 6~9행: 제출 후 GPU 사용이 남는 도식

## 장면 03 Allocator를 다시 쓰는 순간

계획 구간 1:47~2:47. 실제 개발 자료 33초, 자체 설명 27초. 확정 타임코드가 아닙니다.

### 전체 내레이션

커맨드 리스트가 작업 지시서라면, 커맨드 얼로케이터는 그 명령을 기록할 메모리를 관리하는 공간입니다.

다음 프레임을 준비할 때 이 공간을 리셋해서 다시 사용합니다.

그런데 지피유가 이전 명령을 처리하는 중이라면, 아직 읽는 지시서의 공간을 다른 내용에 쓰게 됩니다.

문제가 생긴 뒤에 기다려 봐야 이미 순서가 늦었습니다. 리셋하기 전에 이전 사용이 끝났는지 확인해야 합니다.

얌얌엔진의 에디터 루프에서는 프레임 자원을 기다리는 함수가 애플리케이션 실행보다 먼저 호출됩니다.

애플리케이션의 렌더 함수는 그 뒤에 얼로케이터와 리스트를 리셋합니다. 이 앞뒤 관계가 핵심입니다.

리스트를 닫는 것도 별개의 일입니다. 클로즈는 기록을 끝낸다는 뜻이고, 지피유의 실행 완료를 기다리는 기능은 아닙니다.

이름에 리셋이나 클로즈가 있다고 해서 모든 객체의 사용 조건이 같은 것은 아닙니다.

여기서 우리가 지키려는 조건은 정확합니다. 얼로케이터의 이전 명령 실행이 끝난 다음, 그 메모리를 재사용합니다.

### 실제 예시와 촬영 지시

main→Run→Render→ResetCommandAllocator의 정의를 순서대로 탐색하고 CloseCommandList도 별도 탭으로 확인. 수정 전 Reset→Wait 도식은 역사적 설명용으로만 표시한다.

### 흰색 2.5D 설명 연출

Allocator 명령 공간을 두께가 있는 종이 블록으로 만들고 GPU 독서 바늘이 지나간다. 왼쪽은 독서 중 덮어쓰기 붉은 충돌, 오른쪽은 완료 잠금 해제 후 새 명령 기록. Close는 종이 끝에 기록 종료 탭만 붙이고 완료 체크는 만들지 않는다.

화면 핵심 문구는 **Wait 성공 → Allocator Reset**입니다.

- 1~4행: 읽는 명령 공간과 잘못된 덮어쓰기
- 5~9행: 실제 Wait→Reset 경로와 Close의 별도 의미

## 장면 04 Fence로 완료 지점을 표시하기

계획 구간 2:47~3:52. 실제 개발 자료 28초, 자체 설명 37초. 확정 타임코드가 아닙니다.

### 전체 내레이션

그럼 지피유가 어디까지 처리했는지 어떻게 알까요? 펜스라는 완료 표식을 사용합니다.

작업 뒤에 십 번이라는 번호를 붙여 큐에 신호를 넣었다고 해 봅시다.

이 호출은 시피유가 지금 십 번 작업을 완료했다는 선언이 아닙니다.

지피유가 큐의 그 지점에 도달했을 때, 펜스 값을 십으로 만들어 달라는 예약입니다.

시피유는 나중에 완료 값을 읽고, 필요한 번호에 도달했는지 확인합니다.

얌얌엔진은 새 신호를 보낼 때마다 번호를 하나씩 늘립니다. 십, 십일, 십이처럼 앞으로 가는 완료 기록을 만드는 겁니다.

이 번호는 프레임 번호와 꼭 같을 필요가 없습니다. 중간의 텍스처 업로드도 같은 큐에 신호를 넣을 수 있기 때문입니다.

기다려야 한다면 값을 계속 확인하는 무한 반복 대신, 해당 값에 도달했을 때 이벤트가 깨어나도록 연결합니다.

이미 필요한 번호까지 완료됐다면 오래 기다릴 이유가 없습니다. 아직이면 그 번호가 완료될 때까지 기다립니다.

펜스를 쓴다는 것은 매번 모든 작업을 멈춘다는 뜻이 아닙니다. 지금 필요한 완료 지점이 무엇인지 정하는 것입니다.

### 실제 예시와 촬영 지시

Signal 호출과 SetEventOnCompletion을 서로 다른 색으로 추적. mFenceLastSignalValue+1과 완료 조회 위치를 찾는다. 숫자 10/11/12는 설명용 예시이며 실측 로그처럼 합성하지 않는다.

### 흰색 2.5D 설명 연출

Queue 레일의 작업 뒤에 '10' 완료 표식을 세운다. CPU Signal 순간에는 회색 예약 상태이고 GPU 바늘이 그 지점을 통과해야 파란 완료 상태로 변한다. 다른 높이의 CPU 조회창에 completed=10이 나타난다.

화면 핵심 문구는 **Signal은 완료 지점 예약**입니다.

- 1~6행: 예약 표식과 실제 완료를 단계적으로 비교
- 7~10행: 단조 증가 숫자와 이벤트 대기

## 장면 05 두 슬롯을 돌려 쓰는 방법

계획 구간 3:52~5:07. 실제 개발 자료 33초, 자체 설명 42초. 확정 타임코드가 아닙니다.

### 전체 내레이션

얌얌엔진은 프레임 컨텍스트를 두 개 둡니다. 각 슬롯에는 자기 얼로케이터와 마지막 제출의 펜스 번호가 있습니다.

영 번 슬롯을 사용하고 완료 기준으로 십을 저장합니다. 다음에는 일 번 슬롯을 사용하고 십일을 저장합니다.

다시 영 번 슬롯이 필요해졌는데, 지피유 완료 값이 구라면 어떻게 해야 할까요?

영 번 슬롯의 기준인 십까지 기다려야 합니다. 아직 그 슬롯의 이전 사용이 끝나지 않았기 때문입니다.

완료 값이 십이 되었다면 영 번 슬롯을 다시 쓸 수 있습니다. 일 번 슬롯의 십일이 끝날 때까지 기다릴 필요는 없습니다.

이렇게 각 공간의 이전 사용을 따로 추적해야 시피유가 다음 명령을 준비하는 동안 지피유가 앞선 명령을 실행할 여유가 생깁니다.

슬롯이 두 개라는 이유만으로 기다림이 사라지지는 않습니다. 지피유가 두 슬롯 모두를 아직 사용한다면 결국 기다립니다.

백버퍼도 두 개지만 역할은 다릅니다. 백버퍼는 그림을 저장하고, 얼로케이터는 명령 기록용 메모리를 관리합니다.

현재 엔진은 같은 인덱스로 이 둘을 연결합니다. 따라서 지금 그리는 백버퍼와 지금 사용하는 프레임 슬롯이 끝까지 맞아야 합니다.

그리고 슬롯에 저장된 번호는 완료 값 자체가 아닙니다. 다시 사용하기 전에 도달해야 할 기준값입니다.

### 실제 예시와 촬영 지시

FrameContext 선언과 슬롯 FenceValue 저장/조회 정의를 번갈아 보여준다. 녹화 시 브레이크포인트가 GPU 진행을 바꾸므로 시간 측정 결과로 사용하지 않는다.

### 흰색 2.5D 설명 연출

프레임 슬롯0/1을 두께가 있는 서랍으로, 백버퍼0/1을 별도의 이미지 판으로 배치한다. 슬롯0 기준10, 슬롯1 기준11, 완료9에서 슬롯0 잠김. 완료10으로 이동하면 슬롯0만 열리고 슬롯1은 잠긴 채다. CPU/GPU 시간 막대가 다른 높이에서 겹친다.

화면 핵심 문구는 **지금 재사용할 슬롯의 이전 Fence만 확인**입니다.

- 1~5행: 슬롯별 기준과 9→10의 변화
- 6~10행: 명령 서랍/이미지 판 차이 및 작업 겹침

## 채널 인트로와 회원 감사 엔딩

처음에는 원본 고양이 로고의 기존 인트로를 사용합니다. 마지막에는 원본 회원 프로필·표시 이름·배지가 함께 보이는 10초 감사 씬을 한 번 추가하고 제목은 정확히 멤버쉽가입 감사드립니다.로 유지합니다. 이 장면은 별도 내레이션이나 자막이 없습니다. 원본 명단·이미지 확인 및 엔딩 적용은 렌더 단계에서 진행합니다.
