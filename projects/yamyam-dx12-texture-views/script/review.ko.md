여러 게임 카메라는 게임용 타깃에 순서대로 렌더링합니다. 씬 패널은 별도의 편집용 카메라와 타깃을 사용합니다.

처음에는 그림의 저장 장소가 두 개라는 것부터 잡으면 됩니다. 각 카메라가 어디에 쓰고, 에디터가 무엇을 읽는지 따라가 보세요.

## 장면 03 파일 이미지가 GPU에 도착하기까지

계획 구간 1:52~3:02. 실제 개발 자료 47초, 자체 설명 23초. 확정 타임코드가 아닙니다.

### 전체 내레이션

스프라이트를 그리려면 먼저 이미지 파일의 픽셀을 지피유가 읽을 수 있게 준비해야 합니다.

얌얌엔진은 다이렉트엑스텍스로 파일을 읽습니다. 이 단계에서 얻은 픽셀은 아직 시피유 메모리에 있습니다.

파일을 읽었다는 것만으로 지피유 텍스처가 생긴 것은 아닙니다.

현재 로더는 이차원 이미지의 첫 번째 밉을 알지비에이 팔 비트 채널 형식으로 준비하고, 실제 텍스처를 생성합니다.

그다음 시피유가 쓸 수 있는 업로드 버퍼를 경유해, 디폴트 힙의 텍스처로 픽셀을 복사합니다.

원본 이미지의 한 줄 간격과 지피유 복사용 버퍼의 한 줄 간격은 다를 수 있습니다. 가로 길이에 네 바이트를 곱하면 끝이라고 가정하면 안 됩니다.

현재 코드는 복사 공간의 크기와 배치를 계산하는 헬퍼를 사용합니다.

복사할 때는 텍스처를 복사 목적지 상태로 바꾸고, 끝나면 픽셀 셰이더가 읽는 상태로 되돌립니다.

업로드에는 별도의 얼로케이터와 리스트를 사용하고, 복사 완료를 기다립니다. 프레임의 기록 공간을 중간에 리셋하지 않기 위한 구조입니다.

따라서 현재 구현은 동기식 업로드 경로입니다. 파일을 받아 오면서 계속 이어 그리는 비동기 스트리밍까지 완성된 단계는 아닙니다.

### 실제 예시와 촬영 지시

Load의 파일 분기→mip0→RGBA8→UploadTexture와 UpdateSubresources를 탐색. 새 자료는 직접 만든 단색/체커 이미지를 로드하는 경로를 사용하고 기존 타사 스프라이트는 권리 확인 전 게시 컷에서 제외한다.

### 흰색 2.5D 설명 연출

파일 카드→CPU 픽셀 타일→패딩이 있는 Upload 행→Default 텍스처 판을 서로 다른 깊이로 이동시킨다. 한 행 끝에 패딩 블록을 덧붙여 원본 rowPitch와 복사용 행 간격 차이를 시각화한다. COPY_DEST 표지가 읽기 상태 표지로 바뀐다.

화면 핵심 문구는 **파일을 읽는 것과 GPU 텍스처 업로드는 다르다**입니다.

- 1~5행: 파일에서 GPU 텍스처까지 이동
- 6~10행: 행 간격/상태 전환/동기식 완료

## 장면 04 픽셀 저장소와 읽고 쓰는 방법

계획 구간 3:02~4:07. 실제 개발 자료 29초, 자체 설명 36초. 확정 타임코드가 아닙니다.

### 전체 내레이션

텍스처가 픽셀을 담는 저장소라면, 디스크립터는 그 저장소를 어떤 방식으로 사용할지 알려 주는 정보입니다.

같은 컬러 텍스처라도 그림을 써 넣을 때는 렌더 타깃 뷰를 연결합니다. 화면에는 알티브이라고 표시하겠습니다.

그 그림을 셰이더에서 읽을 때는 셰이더 리소스 뷰, 에스알브이를 연결합니다.

깊이를 기록하고 비교할 때는 깊이 스텐실 뷰를 사용합니다.

이것들이 모두 이미지 복사본인 것은 아닙니다. 하나의 저장소를 출력용으로 보거나 읽기용으로 보는 연결입니다.

디스크립터 힙은 이런 정보를 보관하는 슬롯들의 모음입니다. 엔진은 빈 슬롯을 배정하고, 안전하게 반납한 슬롯을 다시 사용합니다.

시피유 핸들은 디스크립터를 작성하거나 출력 뷰를 바인딩할 때 사용합니다. 지피유 핸들은 셰이더가 참조할 슬롯을 연결합니다.

임구이의 이미지 함수에 필요한 것도 지피유가 읽을 에스알브이 핸들입니다. 시피유의 픽셀 주소나 출력용 핸들을 넣는 자리가 아닙니다.

얌얌엔진에서는 엔진과 임구이가 같은 셰이더 가시 디스크립터 힙을 사용합니다. 이미지가 들어 있는 슬롯을 같은 기준으로 참조하기 위해서입니다.

## 장면 05 셰이더의 입력 자리 연결하기

계획 구간 4:07~5:22. 실제 개발 자료 53초, 자체 설명 22초. 확정 타임코드가 아닙니다.

### 전체 내레이션

읽기용 디스크립터를 만들었다면, 이번 드로우가 어떤 슬롯을 읽을지도 알려 줘야 합니다.

현재 스프라이트 셰이더에서 비 영에는 변환 행렬, 티 영에는 텍스처, 에스 영에는 샘플러를 연결합니다.

샘플러는 텍스처에서 어느 픽셀을 어떤 규칙으로 고를지 정합니다. 텍스처 좌표와 함께 실제 색을 읽는 데 사용합니다.

루트 시그니처는 이런 입력의 연결 구조를 미리 정합니다.

여기서 주의할 점이 있습니다. 루트 파라미터 번호와 셰이더의 레지스터 번호는 서로 다른 번호입니다.

얌얌엔진의 루트 파라미터 영 번은 비 영을 담당하고, 일 번은 티 영 텍스처 테이블을 담당합니다.

텍스처를 바인딩하는 함수는 먼저 사용할 힙을 고르고, 그 힙 안에서 이번 텍스처의 지피유 핸들을 테이블에 연결합니다.

책장을 골랐다고 책 한 권까지 고른 것은 아니죠. 힙을 선택하는 일과 그 안의 슬롯을 지정하는 일을 둘 다 해야 합니다.

현재 텍스처 바인딩 함수의 단계와 슬롯 인자는 여러 위치를 선택하는 기능으로 연결되어 있지 않습니다. 이 스프라이트 경로의 한 입력 자리에 고정되어 있습니다.

비슷한 기능을 확장할 때는 인자가 있다는 이유만으로 다중 텍스처 입력까지 구현됐다고 생각하지 말고, 실제 테이블 설정을 확인해야 합니다.

### 실제 예시와 촬영 지시

루트 시그니처의 root0/b0와 root1/t0를 실제 줄로 연결하고, Bind와 HLSL Sample을 번갈아 추적한다. stage/slot 인자가 실제로 사용되지 않는 것도 확인한다.

### 흰색 2.5D 설명 연출

현재 엔진은 이런 렌더링 연결을 갖추고 있지만, 오브젝트 아이디를 읽는 선택 기능이나 비동기 스트리밍은 별도 구현이 필요합니다.

씬과 게임의 차이는 창 이름에 있지 않습니다. 같은 장면을 누가 보고, 어디에 그리고, 어떤 핸들로 읽는지에 있습니다.

다음 영상에서는 이렇게 만든 그림의 불투명과 반투명 규칙을 맞추고, 에디터에 올릴 때 색이 다시 섞이는 문제를 해결하겠습니다.

### 실제 예시와 촬영 지시

직접 만든 색 도형으로 Scene 카메라 이동→공유 Transform 수정→패널 리사이즈를 새로 녹화할 계획. ReadPixel=0 구현과 실제 test의 카메라 검사도 보여준다. 동작 확인 전 테스트 통과 캡션을 넣지 않는다.

### 흰색 2.5D 설명 연출

동일 물체를 사이에 둔 두 카메라와 두 그림판을 돌아가며 보여준다. Scene 카메라 이동은 한 결과만 바꾸고 Transform 이동은 두 결과를 바꾸는 대조. 마지막에는 입력 gate 세 표찰과 다음 편의 opaque/cutout/transparent 세 재질판이 등장한다.

화면 핵심 문구는 **카메라·RT·CB 주소·SRV를 연결해 점검**입니다.

- 1~6행: 비슷한 기능의 구현/확인 순서
- 7~10행: 입력 조건과 미완 기능 및 다음 편
