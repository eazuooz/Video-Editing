# 반복 가능한 영상 제작 워크플로

## Git 보관 정책 — 2026-09-29

영상·음성·BGM·압축/분할 미디어는 로컬/외부 저장소에만 보관합니다. Git에는 대본·편집 코드·스타일·자막·출처·프로젝트별 `rebuild.json`을 올립니다. 최신 파일과 과거 이력 모두에 적용합니다. 파일명 변경이나 압축으로 제한을 우회하지 않습니다.

제작/수정 후 `node scripts/build-rebuild-manifests.cjs <slug>`로 원본 위치, 씬 수, 컷/타이밍 자료, 믹스 설정, 재제작 스크립트 목록을 갱신하고 커밋 전 `npm run media:check`와 `npm run rebuild:check`를 실행합니다. 새 프로젝트 생성과 납품 수집에서도 JSON을 자동 갱신합니다. 원본 파일은 별도 보관해야 하며 JSON만으로 소실된 미디어를 복구할 수 없습니다. 상세는 [미디어 보관과 재제작](MEDIA_STORAGE.md)을 따릅니다.

이 저장소는 영상 한 편을 `기획 → 대본 승인 → TTS 샘플 승인 → 1.7B 장면 단위 TTS·SRT·받아쓰기 검수 → 독립 씬 제작 → 실제 예시·자체 설명 페어 → 음악 승인 → 게임 원음·BGM 믹스 → 최종 검수 → 게시` 순서로 제작합니다. 각 단계의 기준 파일과 승인 상태를 분리해, 수정할 때 무엇을 다시 생성해야 하는지 명확하게 유지합니다.

내레이션과 오디오의 상세 수치·완료 조건은
[내레이션·자막·오디오 제작 기준](NARRATION_AUDIO_STANDARD.md)을 단일 기준으로
사용합니다.

화면 디자인은 [흰색 연구 발표형 디자인 기준](VIDEO_VISUAL_STYLE.md)을 기본으로 합니다.
2026-09-07 사용자 지정 PDF 분석 기준이며, 공통 테마와 신규 프로젝트 템플릿에도 적용합니다.

내레이션 자막은 2026-09-19 승인한 [흰 박스·초록 그림자 스타일](CAPTION_STYLE.md)을
새 영상의 기본값으로 사용합니다. 무자막 마스터·한국어 자막판·KO/EN SRT를 함께 보관합니다.

## 제작 전 주제 중복 확인 — 2026-10-01

새 대본·음성·씬을 만들기 전에 기존 프로젝트와 실제 채널 업로드를 확인합니다. 원본 영상 ID·파일명·앞 6편 제외 목록만 대조하지 않고, 시청자에게 답하는 질문과 장면별 설명·대본 내용이 이미 제작된 주제인지 비교합니다. 같은 키워드가 나와도 다루는 질문이 다를 수 있으므로 자동 문자열 점수만으로 통과시키지 않습니다.

배치 항목은 `node scripts/review-video-duplicates.cjs <slug>`로 전체 프로젝트 목록과 입력 해시를 저장합니다. 겹칠 가능성이 있는 기존 대본을 읽고 Studio에서 관련 한국어·영어 제목으로 현재 업로드를 검색한 실제 근거를 확보한 뒤 `--decision distinct --reason "내용 비교 근거" --studio-evidence "실제 Studio 확인 기록"`으로 판단을 기록합니다. 생성 스크립트는 `--check`를 통과해야 실행되며, 기존 자료가 바뀌면 다시 검토합니다. 이 검사는 주제 비교를 대신하지 않습니다.

중복이면 기존 프로젝트·영상 ID와 이유를 대기열에 남기고 건너뜁니다. 사용자의 `이미 만든건 어쩔수없고` 지시에 따라 이미 만든 완성본은 유지합니다. 새 GPU 작업이나 업로드는 이 확인 전 시작하지 않습니다.

## 1. 새 프로젝트 생성

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/new-video-project.ps1 `
  -Slug "camera-shake" `
  -TitleKo "카메라 흔들림은 어떻게 손맛을 만들까?" `
  -TitleEn "How Does Camera Shake Create Impact?"
```

생성되는 위치:

```text
projects/camera-shake/                    # 기획·대본·출처·게시 정보
motion-canvas/src/projects/camera-shake/  # Motion Canvas 시작 프로젝트
manim/projects/camera-shake/              # Manim 시작 프로젝트
```

Motion Canvas 프로젝트는 `motion-canvas/projects.json`에 자동 등록됩니다.
기본 대본의 도입·본론·결론에 대응하는 독립 씬 3개와, 첫 TTS 전에도 편집기를
열 수 있는 짧은 무음 내레이션 파일이 함께 생성됩니다.

## 2. 기획

먼저 `projects/<slug>/planning/outline.md`를 작성합니다.

- 이 영상이 답할 질문은 무엇인가?
- 시청자가 끝까지 보고 기억할 한 문장은 무엇인가?
- 설명만 할 부분과 실제 화면으로 보여 줄 부분은 어디인가?
- 도입 30~45초 안에 영상의 약속이 드러나는가?
- 결론에서 시청자가 직접 적용할 방법을 제시하는가?

게임 영상이나 외부 이미지를 사용할 예정이라면 이 단계부터 `sources/SOURCES.md`에 후보 링크와 허용 근거를 기록합니다.

## 3. 대본

`projects/<slug>/script/narration.ko.json`을 장면 단위로 작성합니다.

권장 규칙:

- 한 줄에는 한 가지 정보만 둡니다.
- 화면 전환이 필요한 지점에서 장면을 나눕니다.
- `scenes[].id` 하나는 Motion Canvas 씬 하나에 대응시킵니다.
- 숫자와 고유명사는 TTS가 자연스럽게 읽는 표기로 씁니다.
- 도입, 기본 원리, 사례, 결론의 순서를 유지합니다.
- 최종 생성 전에 대본을 직접 소리 내어 읽습니다.

대본은 TTS, SRT, 장면 타이밍의 기준 파일입니다. 대본이 바뀌면 음성부터 다시 생성합니다.

## 4. TTS 샘플 승인과 전체 TTS·SRT

기본 모델은 `Qwen3-TTS-12Hz-1.7B-Base`입니다. 기준 음성과 정확히 일치하는
발화문을 함께 사용하고, 같은 장면의 문장을 한 번에 읽게 합니다. 문장별 개별 합성은
종결 어미가 반복적으로 끊겨 들릴 수 있으므로 기본값으로 사용하지 않습니다.

전체 생성 전에 20~40초 정도의 비교 샘플로 목소리, 속도와 톤을 승인받습니다.
승인된 뒤 다음 통합 명령을 실행합니다.

```powershell
qwen3-tts/.venv/Scripts/python.exe qwen3-tts/generate_sample.py `
  --project <slug> --scene 01
```

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File scripts/build-project-narration.ps1 -Project <slug>
```

이 명령은 장면별 TTS와 한국어 SRT, 번역 대본이 있을 때 영어 SRT, Motion Canvas
타이밍, 전체 Whisper 받아쓰기 검토 파일을 생성합니다. 중단 후 다시 실행하면 품질
검사를 통과한 장면 WAV는 재사용합니다.

생성 후 확인할 항목:

- 문장 끝이 잘리지 않았는가?
- 고유명사 발음이 자연스러운가?
- 문장 사이 휴지가 너무 짧거나 길지 않은가?
- 전체 속도가 영상 톤과 맞는가?
- 전체 받아쓰기에 누락·반복·잘못 읽힌 숫자나 고유명사가 없는가?
- SRT 번호와 타임코드가 음성과 일치하는가?

번역 자막은 한국어 SRT의 타임코드를 유지하고 텍스트만 번역합니다.

## 5. Motion Canvas와 Manim 분담

2026-10-01 프레임 세기 수정 피드백: 단순한 자체 테스트 화면도 길게 이어지면 PPT처럼 보일 수 있습니다. 실제 상용 게임, 실행 가능한 자체 테스트, 흰 2.5D 설명의 시간을 따로 기록하고, 실제 게임을 도입부에만 몰지 말고 해당 개념을 말하는 본론 사이에도 넣습니다. 프레임·준비·판정·회복·타격 정지에는 실제 격투게임 동작을 우선 검토합니다. 자체 테스트의 숫자를 다른 게임의 기술 수치로 보이게 하지 않으며 원본 전환·암전·광고 화면을 제외합니다.

대본의 각 장면은 별도 Motion Canvas 씬으로 유지합니다. 모든 내용을 하나의
`main` 씬에 넣지 않습니다. `build_project_timing.py`가 실제 음성 길이를 씬별로
동기화하므로 장면 코드는 생성된 `timing.ts` 값을 사용합니다.

### Motion Canvas가 적합한 부분

- 텍스트, 제목, 강조 표시
- UI, 다이어그램, 장면 전환
- 내레이션에 맞춘 전체 타임라인
- 게임 영상 B-roll 합성

### Manim이 적합한 부분

- 좌표축, 수식, 그래프
- 물리 궤적 비교
- 값을 바꿨을 때의 수학적 변화
- 독립적인 설명용 클립

Manim 클립을 먼저 렌더한 뒤 Motion Canvas의 영상 에셋으로 넣거나, 최종 단계에서 `scripts/combine.ps1`로 이어 붙일 수 있습니다.

```powershell
# Motion Canvas
npm start

# 특정 Manim 프로젝트
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/render-manim.ps1 -Project camera-shake -Quality qh
```

## 6. 실제 예시와 자체 설명 화면

2026-10-01 사용자 요청: **매 영상마다 게임 후보를 새로 검토하고 최근 사용 이력과 대조한다.** 같은 예시 게임·구간을 고정 템플릿처럼 반복하지 않는다. 주제에 맞는 새 타이틀과 새 플레이 구간을 우선하며 프로젝트 `sources/`에 후보·선정/제외 이유·이전 사용 여부·이용 조건을 기록한다. 파일이 이미 있다는 이유만으로 쓰지 않는다. 기존 완료본은 자동 변경하지 않는다.

2026-09-30 화면 구성: [채널 화면 구성](VIDEO_SCREEN_LAYOUT.md)을 우선한다.
채널 고양이 인트로 → 전체 화면 게임 영상과 그 위 자막 → 모든 설명 장면의 흰색 2.5D → 원본 회원 이미지와 로고가 있는 10초 엔딩 순서다.
게임 영상을 흰 PPT 액자에 작게 넣지 않는다. 넓은 게임 디자인 주제는 서로 다른 타이틀로 예시를 확장한다.

### 화면 시간 비율 — 2026-09-29 승인

앞으로 만드는 영상은 **실제 게임·개발 영상 60% / 자체 설명 40%**를 기본으로 설계합니다.
장면 흐름상 필요하면 **62% / 38%까지** 조정합니다. 채널 인트로와 멤버십 감사 엔딩을
제외한 본편 시간 기준이며, 모든 씬에 같은 비율을 강제하지 않습니다. 설명은 정적인
PPT 글보다 2.5D 비교·화살표·강조 애니메이션을 우선합니다.

`editing.targetGameplayShare=0.6`, `targetExplanationShare=0.4`,
`gameplayShareRange=[0.6,0.62]`를 새 프로젝트에 기록합니다. 편집이 끝나면
실측 `actualGameplaySeconds`, `actualExplanationSeconds`, `actualGameplayShare`와
씬별 인·아웃점을 기록하고 `rebuild.json`도 갱신합니다. 실제 영상 위의 자막/화살표는
별도 설명 시간으로 중복 합산하지 않습니다. 명시적인 사용자 예외가 있으면 프로젝트에 남깁니다.
기존 완성 영상은 이 기준만으로 바꾸거나 재렌더하지 않습니다.

2026-09-12 음성 구성 변경: 실제 예시와 자체 설명은 **화면의 페어**이며, 대사를 비워 두는 구분이 아닙니다.
자료화면에서 무엇을 봐야 하는지 우리 대사로 설명하고, 자체 화면에서도 이어 갑니다.
새 대본의 예시 내레이션을 승인받은 뒤 TTS·KO/EN SRT·씬 타이밍·연속 BGM 믹스를 함께 만듭니다.
AI 컴공 v6의 제안 원음 크기는 -31 LUFS이며, 선택곡 Blue Dream은 처음부터 끝까지 이어 사용합니다.
기존 v5·게시된 과거 영상은 보존하고 새 버전에만 적용합니다.

2026-09-07 채널 소재 기준: **게임개발 채널의 상황 자료도 실제 개발 화면을 우선**합니다.
코드 작성, 게임 엔진 편집기, 디버거, 성능 측정, 빌드·플레이 테스트 등 설명과 연결되는
행동이 보여야 합니다. 사용 허용이 확인된 외국 게임개발 튜토리얼·개발 로그도 활용합니다.
일반 사무실·회의·스마트폰·현금·키보드 손만 나오는 스톡은 별도 요청이 없으면 사용하지 않습니다.
챕터마다 가능한 한 다른 원본·구간을 선택하고, 강연이라도 사람 얼굴보다 실제 코드·도표를 우선합니다.
예시의 역할을 명시합니다. 최적화 화면은 AI 요금의 증거가 아니며, 개발 영상 출연자가
대본 속 가상 상사나 면접 사례의 당사자인 것처럼 연결하지 않습니다.

기본 장면 구조는 `실제 게임·공식 기술 예시 영상 1개 → 같은 개념의 채널 제작
그래픽 1개`입니다. **19.5초는 종전 기획 참고값**이며 새 영상에서는 위의 본편 60:40 목표에
맞춰 실제 컷 길이를 정합니다. 한 원본이 짧으면 관련 컷을 연결하되 원본별 출처와
인·아웃점을 기록합니다. 반복 재생·정지 화면·부자연스러운 저속 재생으로 분량만 채우지 않습니다.
숫자만 맞추려고 필요한 설명을 잘라내지 않습니다. 대본과 예시를 함께 설계하고 전체 흐름을 확인합니다.
과거 AI 컴공 초안의 예시78초/695.03초 → 234초/851.03초는 당시 변경 기록이며 새 비율의 기준이 아닙니다.
새 프로젝트는 `project.json.editing`의 목표와 확정된 씬별 타임라인을 미디어 편집·씬 코드·오디오·SRT의 공통 기준으로 읽습니다.
타이밍 변경 시 전체 믹스와 KO/EN SRT를 함께 재생성하며 과거 SRT를 새 타임라인에 사용하지 않습니다.

- 영상의 중요한 동작이 자막이나 그래픽에 가리지 않는지 확인합니다.
- 게임 예시에는 효과음·환경음 중심의 원음을 보존하고 내레이션보다 작게 둡니다.
- 원본 음악의 권리가 불명확하면 음악이 적은 구간을 고르거나 그 부분만 제거합니다.
- 실제 사용 파일, 원본 링크, 구간, 화면·원음 사용 여부를 출처 문서에 남깁니다.
- 라이선스나 사용 허용을 확인하지 못한 파일은 게시본에서 제외합니다.

## 7. BGM 후보 승인과 오디오 믹스

잔잔한 BGM은 영상 처음부터 끝까지 이어 깔고, 게임 원음은 그 위에 함께 재생합니다. 음악을
선택하기 전에 곡명, 원본 미리듣기 링크, 라이선스, 출처 표기와 영상 적합성을 먼저
제시합니다. 사용자가 곡을 선택하기 전에는 다운로드·믹스·최종 렌더를 진행하지
않습니다.

승인 뒤 `project.json`의 `audio.backgroundMusic`과 실제 믹서 입력값을 갱신합니다.
2026-09-06 승인한 기본값은 **내레이션 -16 / 게임 원음 -23 / BGM -28 LUFS**이며,
가벼운 사이드체인 덕킹을 적용합니다. 예전의 더 작은 배경음 기준은 사용하지 않습니다.
정확한 수치·페이드·검사 방법은 [오디오 제작 기준](NARRATION_AUDIO_STANDARD.md)의
기본 믹스 기준을 따릅니다. 배경음만 조정할 때 내레이션과 SRT는 유지합니다.
게임 원음이 나오는 동안에도 BGM을 끄지 않고 3dB만 낮춥니다. 씬 전환에서 음악을
자르거나 다시 시작하지 않으며, 곡이 끝나면 1초 크로스페이드로 반복 연결합니다.

전체 믹스 완료에는 다음 작업까지 포함됩니다.

1. 원본 TTS·게임 원음·승인곡을 합쳐 최종 MP4와 편집기용 `assets/final-mix.m4a`를 생성합니다.
2. `paths.audioMix`를 기록하고 `project.ts`의 `audio`를 전체 믹스로 연결합니다.
   나레이션 전용 연결은 초안 단계에서만 사용합니다.
3. 개별 Video 재생만 음소거해 원음의 이중 재생을 방지합니다. 원본 파일의 소리는 보존합니다.
4. 배경 합산의 `amix normalize=0`, 동일 타이밍, 음량 측정과 편집기 재생을 검사합니다.
5. 설정·측정값·대체 음악 씬을 `projects/<slug>/audio/mix-report.md`에 남깁니다.

FPS의 `scripts/mix-frame-rate-audio.ps1`는 20개 씬·6.5초 예시 구간용 구현입니다.
새 영상에서는 씬 수와 예시 구간을 맞춘 뒤 재사용합니다. 현재 명령을 임의의
새 프로젝트에 그대로 실행하면 안 됩니다.

## 8. 렌더와 검수

### 필수 마지막 장면: 멤버십 감사 엔딩

2026-09-25 사용자 요청으로 **새 최종 영상마다 결론 뒤에 10초의 회원 감사 화면**을 한 번만 추가합니다. 상세 규칙은 [멤버십 엔딩](MEMBERSHIP_OUTRO.md)을 따릅니다. 문구는 요청 그대로 `멤버쉽가입 감사드립니다.`입니다. 공유 명단의 잘린 아이디는 추측하지 말고 게시 전에 확인합니다. 완성된 과거 영상은 자동 변경하지 않습니다.

본편 시간에 10초를 더하고 Motion Canvas 마지막 씬·최종 믹스 길이·게시 길이를 함께 반영합니다. 기존 본편 KO/EN SRT 타임코드는 밀지 않습니다. BGM을 쓰지 않기로 한 영상은 엔딩에도 음악을 새로 넣지 않습니다. 음성/디자인만 확인하는 부분 프리뷰에는 엔딩을 억지로 붙이지 않아도 됩니다.

최종 렌더 권장값:

- 1920×1080
- 60fps
- H.264 영상 + AAC 오디오
- 무자막 본편을 기준 파일로 보관
- 기본 한국어 자막판도 별도 생성: `boxed-white-forest-v1` ([수치·검수 기준](CAPTION_STYLE.md))

게시 전에는 처음부터 끝까지 한 번 재생하며 다음을 확인합니다.

- 음성과 장면 전환이 맞는가?
- 검은 화면, 프레임 멈춤, 영상 반복 오류가 없는가?
- B-roll 출처와 파일명이 일치하는가?
- 자막 오탈자와 줄바꿈이 자연스러운가?
- 모든 자막이 최대 두 줄이며 박스·그림자 잘림이나 게임 UI·하단 요약과의 겹침이 없는가?
- 음량이 장면마다 갑자기 달라지지 않는가?
- 게임 예시에는 작은 원음과 BGM이 동시에, 설명 구간에는 같은 BGM이 연속해서 들리는가?
- 내레이션, 원본 음악과 BGM이 서로 경쟁하지 않는가?
- 배경 단독 트랙에도 각 씬의 원음·BGM이 있고 편집기와 MP4에서 같은 믹스가 나오는가?
- 편집기 `include audio`가 켜져 있고 개별 게임 Video의 소리가 중복되지 않는가?

프로젝트 매니페스트에 최종 경로를 기록한 뒤 검사합니다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File scripts/check-video-project.ps1 -Project <slug> -Stage publish
```

음성 생성 직후에는 `-Stage narration`, 최종 MP4가 준비된 뒤에는 `-Stage publish`를
사용합니다. 음악 승인이 `pending`인 프로젝트는 게시 검사를 통과하면 안 됩니다.

## 9. YouTube 게시

### 고정 납품 폴더 — 2026-09-26 사용자 지정

앞으로 렌더·자막 수정이 끝날 때마다 저장소 루트 `output/<프로젝트명>/`에 최신 결과물 네 개를 모읍니다.
`shared/output/`은 작업 산출 경로이며 사용자가 여는 최종 모음은 **루트 `output/`**입니다.

- `<slug>.captioned.mp4`: 한국어 자막이 입혀진 영상
- `<slug>.clean.mp4`: 내레이션/승인된 오디오가 있는 무자막 영상
- `<slug>.ko.srt`: 한국어 SRT
- `<slug>.en.srt`: 같은 타임라인의 영어 SRT
- `index.html`: 두 영상 재생·다운로드와 검수 상태 안내

```powershell
node scripts/collect-video-output.cjs <slug>
```

프로젝트 매니페스트의 경로로만 파일을 고릅니다. 수정 시각이나 파일명 추측으로 버전을 섞지 않습니다.
네 파일이 모두 준비되고 영상 길이·해상도·오디오 존재·한영 SRT 타임코드 검사가 통과한 뒤 복사하며 SHA-256을 대조합니다.
원본은 이동/삭제하지 않습니다. 이전 납품 폴더는 `projects/<slug>/production/delivery-history/`로 보존하고,
작업 중간 WAV·PNG·로그는 `output/`에 넣지 않습니다. 수집 기록은 `production/delivery-output.json`에 남깁니다.
새 프로젝트에도 `delivery` 설정을 포함하며, 결과 안내에는 `output/index.html` 또는 프로젝트 폴더를 링크합니다.
이 폴더는 정리 위치일 뿐 게시 승인 증명이 아닙니다. 미완료 엔딩·청취·권리 검수 상태는 그대로 표시합니다.
과거 영상을 이 규칙만으로 재렌더하지 않습니다. `output/`은 중복 복사본이므로 Git에서는 제외하고,
다른 컴퓨터에서는 원본 미디어 복원 후 같은 명령으로 다시 모읍니다.

`projects/<slug>/publishing/`에서 언어별 제목, 설명, 챕터를 관리합니다.

2026-10-01 사용자 지정 업로드 절차는 [YouTube 썸네일·언어·링크 기본값](YOUTUBE_PUBLISHING.md)을 따른다. 한영 SRT 수동 등록과 영어 제목·설명, 기존 채널 소개 위의 새 설명, 00:00 과외 링크 카드, 회원 엔딩의 재생목록·구독 버튼을 각각 검증한다.

권장 구성:

- 기본 제작물: 무자막 마스터 + 승인된 박스 스타일 한국어 자막판 + 언어별 SRT
- 업로드: 디자인 고정이 목적이면 자막판, 언어별 자막 선택이 우선이면 무자막판 + SRT
- 영상 내부: 핵심 단어·모션 그래픽과 내레이션 자막이 겹치지 않게 배치
- 쇼츠·SNS: 같은 자막 스타일을 해당 화면 비율에 맞춰 재배치·검수
- 설명란: 핵심 검색어를 첫 두 줄에 자연스럽게 포함
- 챕터: 반드시 `00:00`부터 시작

업로드 후에는 실제 모바일 화면에서 제목 잘림, 썸네일 가독성, 자막 위치를 확인합니다.
SRT에는 박스·서체 디자인이 저장되지 않습니다. 고정 자막판에서 플레이어 자막까지 켜져
이중으로 표시되지 않는지도 확인합니다. 기존 완성 영상은 이번 기본값 변경만으로 재렌더하지 않습니다.
