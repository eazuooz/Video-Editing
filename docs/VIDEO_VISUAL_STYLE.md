# 화면·설명 렌더링 제작 규격

운영·승인·재검수 범위는 [통합 제작 규칙](VIDEO_WORKFLOW.md)만 따른다. 이 문서는 장면 설계 때 적용하는 화면 규격이다.

## 설명에 따른 렌더러 선택

2026-10-14 사용자 지시를 반영해 **Three.js·Motion Canvas·Manim·Unity를 영상 제작 도구로 사용**한다. 2.5D를 기본 해법으로 강제하지 않고 시연과 설명에 맞춰 도구를 선택한다. 현재 `game-lighting-history-01` 수정본은 공간·조명·그림자를 Three.js로 구현하고, 각 설명에 더 명료한 도구가 있으면 에이전트가 판단해 채택한다. 나머지 편의 자동 재제작은 하지 않는다.

| 도구 | 적합한 설명 | 구현 기준 |
|---|---|---|
| Manim | 수식 전개, 벡터·좌표·기하·행렬 변환 | 기호와 공간 대상의 대응을 유지하고 계산 순서를 발화에 맞춰 표시. 3D 기능도 필요에 따라 사용 |
| Three.js | 실제3D 모델, 카메라 투영, 법선·광원·가림·그림자, 렌더링 중간 결과 | 실제 메시/카메라/깊이 검사를 사용. 같은 장면·시점에서 한 조건을 바꿔 비교하고, 깊이/법선 버퍼 등은 실제 구현 출력인지 교육용 모형인지 명시 |
| Motion Canvas | 2D 흐름도·타임라인·라벨·자막·화면 합성, 공간 오해가 없는 간단한2.5D | 억지 입체 장식 대신 정보의 등장 순서와 읽기 쉬운 구성을 우선 |
| Unity | 실제 엔진의 렌더링·셰이더·조명/그림자·물리·애니메이션·상호작용 시연 | 실제 씬과 컴포넌트의 동작을 촬영. 에디터/렌더 파이프라인 버전·조건을 기록하고, 실제 측정값과 교육용 표식을 구분 |
| Blender / 적합한 게임엔진 | 상세 자산·반사·굴절·간접광·볼륨 등 또는 해당 엔진의 실제 기능 | 장면과 설정을 재현 가능하게 기록. 영상미만으로 구현 원리나 성능을 증명하지 않음 |

씬의 기존 설계표에 `renderer`, `rendererReason`, `implementationKind`, 전 상태→조작→결과, 사용할 실제 출력/교육용 표식과 자막 여백을 기록한다. `implementationKind`는 `actual-implementation` 또는 `conceptual-illustration` 등으로 구분하고 같은 화면에 혼합되면 요소별로 적는다. 라이브러리 이름만 바꾸고 기존 평면 도형을 그대로 출력한 것을 실제3D 전환이라 하지 않는다. 하나의 설명에 도구를 섞을 때에도 좌표계·같은 대상·색·라벨·카메라 연결과 타이밍을 유지한다. 필요 없는 도구/의존성은 추가하지 않는다.

추가한 Unity 프로젝트는 `unity/VideoEditing`이며 기존 `unity/` 프로젝트는 보존한다. 선택된 영상의 설명에 적합하면 에이전트가 Unity 씬을 제작·촬영할 수 있고 씬마다 별도 승인을 요구하지 않는다. 프로젝트·씬 경로, 에디터와 렌더 파이프라인/패키지 버전, 결과에 영향을 주는 광원·카메라·물리 조건, 캡처 해상도/fps와 프레임/내레이션 대응을 기존 설계표에 기록한다. 씬·프리팹·스크립트로 독립 편집 가능하게 구성하고 실제 최종 자막 공간을 확보한다. 자체 제작 Unity 화면은 실제 엔진 구현이어도 **설명 분량**이며 독립 확보한 상용 게임 플레이로 계산하지 않는다. 소스와 `.meta`·패키지 잠금·프로젝트 설정은 [미디어/Git 규격](MEDIA_STORAGE.md)에 따라 보존하고 캐시·빌드·녹화 결과는 Git에서 제외한다.

같은 3D 장면에서 전체 공간→관찰할 면/픽셀→변경할 한 조건→계산 중간값→화면 결과의 순서로 설계한다. 광원 시점과 관찰자 시점은 이름과 위치를 구분한다. 카메라를 계속 회전시켜 정보를 늘리지 말고 관계를 보여 준 뒤 고정한다. 임의의 광선이나 색칠한 칸은 교육용 표식이며 실제 깊이 버퍼/측정 결과로 부르지 않는다. 짧은 대표 동작으로 공간·가림·글씨·실제 자막을 먼저 확인한 뒤 같은 체계를 전체 장면에 적용한다.

## 팔레트와 글자

신규 설명은 `research-black-v1` / `motion-canvas/src/styles/research-dark.ts`를 사용한다. 이미 승인된 흰 프로젝트는 `research-paper.ts`를 보존한다. 명시 수정된 `game-lighting-history-01`~`04`는 검정이다. 실제 게임·브랜딩·회원 엔딩·썸네일을 함께 검게 바꾸지 않는다.

| 역할 | 색 |
|---|---|
| 배경 | #000000 |
| 본문·수식·라벨 | #f5f5f5 |
| 보조·축 | #b8b8b8 |
| 제목·강조 | #e8cf83 |
| 벡터·곡선 | #73c7c2 |
| 초점 | #f39a4b |

빨강·초록 등 추가 색은 역할·라벨을 정해 사용한다. 색만으로 의미를 구분하지 않는다. 1920×1080 좌우 안전 여백96px, 제목48–56px, 핵심 라벨32–40px, 보조26–30px가 시작값이다. 영어Segoe UI, 한글Malgun Gothic, 수식Cambria Math, 코드Consolas 또는 승인 폰트를 사용한다. 실제 폰트로 폭을 측정한다. 하단 고정 자막의 박스와 그림자 공간을 먼저 예약하고 요약 띠·수식은 그 위에 놓는다. 이전 흰 레이아웃의 y405 요약 띠를 그대로 복사하지 않는다.

## 상세 대상과 실제 공간 표현

- 사람: 머리·얼굴 또는 장비, 몸통·의복, 어깨/팔꿈치/무릎 등 관절, 손발, 대사와 맞는 자세·행동을 알아볼 수 있게 제작한다.
- 물건: 비례·윤곽과 특징적 구조/작동부를 그린다. 자전거의 프레임/바퀴/핸들/페달, 항공기의 동체/조종석/주익/꼬리처럼 동작을 이해하는 세부를 포함한다.
- 같은 대상을 연결되는 씬에서 재사용하고 투영·앞뒤 가림·면·높이·관절 동작을 일관되게 유지한다. 사람/탈것이라는 이름만 붙인 큐브·막대 아이콘은 대체물이 아니다. 큐브/경계상자/행렬칸 자체를 설명할 때는 추상 도형이 적합하다.
- 카드에 그림자만 준 장식을 공간 설명으로 대체하지 않는다. 필요한 투영·공간 관계·가림과 내레이션에 맞는 이동/회전/비교가 보여야 한다. 2D가 더 명료하면2D를 쓰고 실제 깊이가 필요하면3D를 쓴다. 과도한 장식·네온·빛번짐보다 대상과 수식의 대비를 우선한다.
- 장면별 실제 대상/식별 세부/관절·작동부/시작·끝 상태/대사별 움직임/같은 대상의 연결/자막 공간을 제작 전에 적는다. 선택한 도구에서 독립 편집 가능한 씬과 자산을 사용한다. Three.js·Motion Canvas·Manim·Unity·Blender 출력을 합성할 때도 동일 팔레트·타이밍과 실제 자막을 따른다.

## 실제 게임 위의 해설

게임은 전체 화면, 원래 색과 동작을 유지한다. 핵심 빨간선, 구별되는 축·벡터·각도·궤적·영역/라벨을 대사 순서로 등장시킨다. 실제 대상과 카메라를 추적하고 컷이 바뀌면 이전 표식을 제거한다. 게임 디자인에는 상태·윤곽·선택을 표시하고 무관한 수식을 넣지 않는다. 화면상의 투영 길이/각도를 확인되지 않은 게임 월드 값으로 주장하지 않는다.

실제 자막을 합성한 대표 동작과 까다로운 UI 구간을 먼저 확인한다. 최종에는 모든 관련 움직임·큐/컷을 한 번 통합 검수하고 해시/구간을 기록한다. 정지판이나 코드 이름은 움직임 승인 근거가 아니다. 변경 없는 승인 구간은 통합 규칙의 재사용 조건으로 유지한다. 썸네일은 [별도 채널 삽화 규격](VIDEO_25D_THUMBNAIL_REVIEW.md)을 따른다.
