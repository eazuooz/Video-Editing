# 화면·설명 렌더링 제작 규격

운영·승인·재검수 범위는 [통합 제작 규칙](VIDEO_WORKFLOW.md)만 따른다. 이 문서는 장면 설계 때 적용하는 화면 규격이다.

## 설명에 따른 렌더러 선택

2026-10-14 사용자 승인에 따라 **Unity를 게임 시연과 대부분의3D 원리 설명의 주력 도구**로 사용한다. **Unity는 적합한2D 설명에도 사용**하고 **Motion Canvas는2D 도식·합성, Manim은 수학, Three.js는 필요한 경우의 선택 도구**로 둔다. 2D라는 이유로 도구를 고정하지 않으며 도트/스프라이트 애니메이션·게임 상태·기존 씬 재사용이 설명에 유리하면 Unity를 선택한다. 게임 동작과 조명·그림자·투영·깊이 등 원리 설명을 도구별로 강제 분리하지 않고 같은 Unity 씬·자산·촬영 구성을 재사용한다. Three.js는 브라우저 상호작용이나 기존 씬 재사용 등 장면별 이점이 명확할 때 선택하고 `rendererReason`에 적는다. 동일 장면을 두 도구로 중복 제작하지 않는다. 2.5D를 기본 해법으로 강제하지 않고 나머지 설명은 목적에 맞춰 도구를 선택한다. 사용자가 특정 렌더러를 지정한 장면은 그 지시를 우선한다. 현재 `game-lighting-history-01` 수정본은 공간·조명·그림자를 Three.js로 구현하고, 각 설명에 더 명료한 도구가 있으면 에이전트가 판단해 채택한다. 나머지 편의 자동 재제작은 하지 않는다. 같은 날 사용자 지시로 Blender는 제작 도구에서 제외한다.

| 도구 | 적합한 설명 | 구현 기준 |
|---|---|---|
| Unity | **자체 제작 게임 시연과 대부분의3D 원리 설명의 주력 도구이며2D 설명에도 선택 가능**. 도트 캐릭터·아이템·타일맵·스프라이트 애니메이션·상태 변화, 3D 구조·좌표계·카메라 투영·법선·깊이/가림·렌더링 원리, 캐릭터 이동·점프·공격·애니메이션, 상점/인벤토리·상호작용, 물리/충돌, 카메라 추적·레벨 이동, 실제 엔진의 셰이더·조명/그림자 동작 | 실제 씬·컴포넌트·게임 규칙을 실행해 전 상태→행동→결과를 촬영. 예: 100골드에서 30골드 구매 성공, 20골드에서 구매 거절. 에디터/렌더 파이프라인 버전·조건을 기록하고 실행값과 교육용 표식을 구분 |
| Motion Canvas | 2D 흐름도·움직이는 화살표·분기/합류·상태 라벨·타임라인·자막·화면 합성 | 예: Unity 구매 동작 위에 조건→처리→결과 화살표와 잔액 표시. 실제 값 표시는 Unity 실행 데이터에 연결. 순수 관계 도식은 단독 제작하고 정보 등장 순서·가독성을 우선 |
| Three.js — 선택 | 브라우저에서 직접 조작하는3D 설명, 기존 Three.js 씬 재사용 등 채택 이점이 분명한 장면 | 예: 웹에서 카메라/광원을 직접 바꾸는 설명. 원리 설명이라는 이유만으로 Unity에서 전환하지 않음. 선택 이유를 기록하고 실제 구현 출력과 교육용 모형을 구분 |
| Manim | 수식 유도·계산, 벡터·기하·행렬 변환, 그래프와 수학적 변화 | 예: 내적 계산→밝기 값, 변환 행렬→좌표 변화. 기호와 공간 대상의 대응을 유지하고 계산 순서를 발화에 맞춰 표시. 필요한 경우 3D 기능 사용 |

씬의 기존 설계표에 `renderer`, `rendererReason`, `implementationKind`, 전 상태→조작→결과, 사용할 실제 출력/교육용 표식과 자막 여백을 기록한다. `implementationKind`는 `actual-implementation` 또는 `conceptual-illustration` 등으로 구분하고 같은 화면에 혼합되면 요소별로 적는다. 라이브러리 이름만 바꾸고 기존 평면 도형을 그대로 출력한 것을 실제3D 전환이라 하지 않는다. 하나의 설명에 도구를 섞을 때에도 좌표계·같은 대상·색·라벨·카메라 연결과 타이밍을 유지한다. 필요 없는 도구/의존성은 추가하지 않는다.

추가한 Unity 프로젝트는 `unity/VideoEditing`이며 기존 `unity/` 프로젝트는 보존한다. 선택된 영상의 설명에 적합하면 에이전트가 Unity 씬을 제작·촬영할 수 있고 씬마다 별도 승인을 요구하지 않는다. 적합한 **권리 확인 무료 도트/스프라이트·모델·리그·애니메이션을 우선 재사용**하고 원본 URL·제작자·버전·라이선스와 필요한 표시 조건을 기록한다. 기존 자산이 설명에 맞지 않을 때 필요한 부분을 수정하거나 제작한다. 프로젝트·씬 경로, 에디터와 렌더 파이프라인/패키지 버전, 결과에 영향을 주는 광원·카메라·물리 조건, 캡처 해상도/fps와 프레임/내레이션 대응을 기존 설계표에 기록한다. 씬·프리팹·스크립트로 독립 편집 가능하게 구성하고 실제 최종 자막 공간을 확보한다. 자체 제작 Unity 화면은 실제 엔진 구현이어도 **설명 분량**이며 독립 확보한 상용 게임 플레이로 계산하지 않는다. 소스와 `.meta`·패키지 잠금·프로젝트 설정은 [미디어/Git 규격](MEDIA_STORAGE.md)에 따라 보존하고 캐시·빌드·녹화 결과는 Git에서 제외한다.

**Unity2D 자산과 씬 저장.** 필요한 설명에 맞는 도트 자산을 찾아 캐릭터 동작·아이템 식별·그림체·색 의미·자막 대비를 확인한다. 이미 보유한 적합한 자산은 재사용하며 모든 설명에 도트 스타일을 강제하지 않는다. 원본 URL·제작자·버전/리비전·라이선스·출처 표시 조건·원본 해시와 원본 자산의 Git 재배포 가능 여부를 기록한다. 픽셀 밀도·스케일·카메라 크기를 맞추고 필요하면 Point 필터와 정수 배율을 사용해 의도하지 않은 번짐/떨림을 방지한다. 적용한 PPU·필터·압축·카메라/Pixel Perfect 설정은 결과에 관련된 것만 설계표에 남기며 모든 씬에 특정 설정을 강제하지 않는다.

Unity로 제작한 대본 씬마다 독립 편집 가능한 `.unity` 파일을 저장한다. 새 구성의 권장 위치는 `Assets/VideoScenes/<slug>/<scene-id>.unity`이며 기존 샘플·승인 씬을 이름만 맞추려고 옮기지 않는다. 같은 캐릭터·타일셋·프리팹·AnimationClip/Animator·스크립트·머티리얼은 공유 참조로 재사용하고 씬별로 필요한 시작 상태·동작·끝 상태·촬영 설정을 저장한다. 스프라이트 시트·분할/import 설정과 대응 `.meta`도 보존하되 이미지 등록과 라이선스는 미디어 규격을 따른다. 기존 설계표에 `assetRecords`, `sharedAssetPaths`, `sceneSaveStatus`와 실제 `scenePath`를 연결해 계획/저장을 구분한다. 장면별 파일 분리는 편집과 재사용을 위한 것이며 챕터마다 연출을 끊는 기준이 아니다.

같은 3D 장면에서 전체 공간→관찰할 면/픽셀→변경할 한 조건→계산 중간값→화면 결과의 순서로 설계한다. 광원 시점과 관찰자 시점은 이름과 위치를 구분한다. 카메라를 계속 회전시켜 정보를 늘리지 말고 관계를 보여 준 뒤 고정한다. 임의의 광선이나 색칠한 칸은 교육용 표식이며 실제 깊이 버퍼/측정 결과로 부르지 않는다. 짧은 대표 동작으로 공간·가림·글씨·실제 자막을 먼저 확인한 뒤 같은 체계를 전체 장면에 적용한다.

## 팔레트와 글자

신규 설명은 `research-black-v1` / `motion-canvas/src/styles/research-dark.ts`를 사용한다. 이미 승인된 흰 프로젝트는 `research-paper.ts`를 보존한다. 명시 수정된 `game-lighting-history-01`~`04`는 검정이다. 실제 게임·브랜딩·회원 엔딩·썸네일을 함께 검게 바꾸지 않는다.

빨강·초록 등 추가 색은 역할·라벨을 정해 사용한다. 색만으로 의미를 구분하지 않는다. 1920×1080 좌우 안전 여백96px, 제목48–56px, 핵심 라벨32–40px, 보조26–30px가 시작값이다. 영어Segoe UI, 한글Malgun Gothic, 수식Cambria Math, 코드Consolas 또는 승인 폰트를 사용한다. 실제 폰트로 폭을 측정한다. 하단 고정 자막의 박스와 그림자 공간을 먼저 예약하고 요약 띠·수식은 그 위에 놓는다. 이전 흰 레이아웃의 y405 요약 띠를 그대로 복사하지 않는다.

### 일반 설명과 코드의 의미 색 — semantic-text-code-colors-v1

2026-10-19 사용자 요청에 따라 소스코드를 한 색의 일반 문장처럼 출력하지 않는다. 검정 설명 배경·흰 본문·따뜻한 노란 제목은 유지하면서, 기존 브랜드 토큰에 문법/설명 역할을 연결한다. 승인된 흰 팔레트는 유지하고 그 배경에서 대비가 맞는 대응 토큰을 사용한다. 다른 편집기의 원색 테마나 예시 화면 색을 그대로 복사하지 않는다.

| 영역 | 구분할 역할 | 적용 기준 |
|---|---|---|
| 코드 | 키워드 / 함수·API / 변수·매개변수 / 숫자 / 문자열 / 주석 | 예: 키워드=따뜻한 노랑, 함수·API=청록, 변수·매개변수=본문색, 숫자=주황, 문자열=절제한 초록, 주석=보조 회색처럼 공통 의미 토큰으로 정의. 해당 언어의 실제 토큰을 기준으로 구분하며 부분 문자열 치환으로 식별자를 잘못 칠하지 않음. 매개변수/현재 관심 변수는 필요할 때 이름·밑줄·연결 라벨로 추가 구별 |
| 실행 상태 | 현재 실행줄 / 입력 / 바뀐 값 / 결과 | 문법색을 유지한 채 행 번호·왼쪽 표식·얇은 배경 띠로 현재 줄을 표시. 강조 중에도 키워드/값이 읽혀야 하고 색만으로 실행/성공을 판정하게 하지 않음 |
| 일반 설명 | 제목 / 핵심개념 / 기준값 / 변경값 / 주의 / 보조설명 | 제목·본문 기본색을 유지하고 핵심 단어/값만 청록·주황 등으로 강조. 기준/변경/주의는 짧은 이름·전후 배치·선/모양으로도 구별. 문단 전체나 한 문장을 무지개색으로 나누지 않음 |

한 화면에 필요한 역할만 사용하며 대본·수식·코드·도형에서 같은 대상의 색 의미를 이어 간다. 축의 X/Y/Z 색은 축/좌표 의미이고 문법색·오류/변경 상태색은 별도 역할이다. 함께 나오면 영역·축 이름·범례·행 표식으로 구분하고 같은 색이 서로 다른 뜻을 혼동시키면 강조를 줄이거나 재배치한다. 새 일반 글자·코드 토큰·주석은 실제 배경에서4.5:1 대비를 목표로 확인하며, 너무 흐린 주석이나 얇은 글씨를 색 구분의 대가로 허용하지 않는다.1080p와375px에서 실제 자막을 넣고 코드의 입력→현재 줄→값 변화→결과 및 일반 설명의 읽는 순서·가림을 확인한다. 기존 씬 계획에 `textColorRoles`, `codeTokenRoles`, `executionHighlight`를 필요한 장면에 기록하고 기존 시각 검수에 통합한다. 현재 선택 수정과 향후 명시 선택 영상에 적용하며 새 승인 절차나 미선택 영상 재제작을 추가하지 않는다.

## 얌얌코딩 영상 UI — yamyam-video-ui-v1

2026-10-14 사용자가 첨부한 `DESIGN.md` 사진의 **토큰·단순한 정보 위계·공통 컴포넌트·모바일 확인** 원칙을 영상에 맞게 적용한다. 사진의 웹 예시인 Inter, 파란 accent, 흰 surface, rem 크기, 클릭/hover 규칙을 그대로 복제하지 않는다. 이 절과 기존 `research-dark.ts`를 제작 전 확인하며, 운영 절차는 통합 규칙만 따른다.

- **한 화면에 한 가지 설명 초점.** 지금 볼 대상·동작·결과를 대사 순서대로 보여 준다. 카드나 배지를 채우기 위한 가짜 수치·의미 없는 영어·임의 대시보드·불필요한 상태 표시를 만들지 않는다. 반복되는 카드 격자보다 실제 게임/Unity 대상과 필요한 주석을 우선한다.
- **채널 정체성.** 검정 배경·흰 본문·따뜻한 노란 제목을 기본으로 하고, 원래 고양이·`얌얌코딩` 표기는 브랜딩과 필요한 작은 출처/서명 위치에서 절제해 사용한다. 매 카드에 로고/고양이를 반복하지 않는다. 원본2초 인트로·10초 회원 신원·썸네일의 별도 규격은 유지한다. 참고 채널의 UI·아이콘·문장을 복제하지 않는다.

- 같은 대상을 연결되는 씬에서 재사용하고 투영·앞뒤 가림·면·높이·관절 동작을 일관되게 유지한다. 사람/탈것이라는 이름만 붙인 큐브·막대 아이콘은 대체물이 아니다. 큐브/경계상자/행렬칸 자체를 설명할 때는 추상 도형이 적합하다.
- 카드에 그림자만 준 장식을 공간 설명으로 대체하지 않는다. 필요한 투영·공간 관계·가림과 내레이션에 맞는 이동/회전/비교가 보여야 한다. 2D가 더 명료하면2D를 쓰고 실제 깊이가 필요하면3D를 쓴다. 과도한 장식·네온·빛번짐보다 대상과 수식의 대비를 우선한다.
- 장면별 실제 대상/식별 세부/관절·작동부/시작·끝 상태/대사별 움직임/같은 대상의 연결/자막 공간을 제작 전에 적는다. 선택한 도구에서 독립 편집 가능한 씬과 자산을 사용한다. 편집 가능한 씬의 경계가 시청자의 설명 흐름을 끊지 않도록 전 장면의 대상·상태·라벨·화살표 도착점을 다음 장면의 출발점으로 이어받는다. 다른 자료로 전환할 때도 같은 질문이나 관찰 대상을 먼저 연결하며 서로 다른 출처/실행 상태를 같은 연속 촬영처럼 오인시키지 않는다. 씬마다 타이틀 카드·검정 화면·음악 페이드를 반복하지 않고 의미 있는 쉼만 계획한다. 내레이션의 끝·첫 문단과 화면/소리의 연결을 기존 씬 설계의 `transitionToNext`에 기록한다. Three.js·Motion Canvas·Manim·Unity 출력을 합성할 때도 동일 팔레트·타이밍과 실제 자막을 따른다.

## 실제 게임 위의 해설

### 설명 순서에 맞춘 움직이는 연결선과 경로

2026-10-14 사용자가 제시한 저세상개발자 쇼츠의 **점진적으로 연결되는 화살표, 현재 경로 강조, 상태 변화와 실제 시연의 연결**을 선택된 영상의 설명 문법으로 활용한다. 참고 분석과 관찰 범위는 `shared/publishing/animated-explanation-reference.json`에 기록한다. 원본의 그림·게임 컷·자막·템플릿을 제작 자산으로 복사하지 않고 우리 내용과 권리 확인 자산으로 구현한다. 원 제작자의 Unity/Motion Canvas 사용 여부는 확인되지 않았으며, 도구 추정과 화면 관찰을 구분한다.

- 먼저 대상과 기준점을 보여 주고, 내레이션이 관계를 설명할 때 **출발점 강조 → 선이 목적지까지 그려짐 → 도착점 반응 → 결과를 읽을 시간** 순서로 진행한다. 이동하는 점은 진행 위치, 화살촉은 방향, 점선은 미실행/조건부 관계처럼 의미를 정한다. 반복 흐름이 실제로 설명되는 경우에만 반복한다.
- 현재 설명하는 주 경로 하나를 우선 강조한다. 나머지 경로는 알아볼 수 있을 정도로 낮추고, 미확인·잠김·통과·실패를 글자/형태로도 구별한다. 기본 팔레트에서 노랑은 현재 초점, 청록은 확인된 경로, 회색은 대기, 빨강은 실패에 사용하되 기존 장면의 의미 있는 색 약속을 우선한다. 색이나 발광만으로 상태를 전달하지 않는다.
- 선형 진행, 분기 선택, 반복/되돌림, 합류처럼 설명할 관계에 맞춰 배치한다. 구조가 바뀌면 대상의 이름·아이콘·색을 유지하고 변화 전후를 비교할 시간을 둔다. 화살표마다 이동/의존/시선/데이터 전달 중 의미를 정하고 서로 다른 의미를 한 선에 섞지 않는다.
- 선 그리기 약0.35–0.8초와 도착 반응 약0.2–0.5초는 시안의 시작값이다. 실제 발화와 읽기 시간으로 조정하며 참조 영상의 실측값이나 고정 규칙으로 취급하지 않는다. 의미 없는 흔들림, 상시 펄스, 과한 바운스·발광으로 주의를 분산시키지 않는다.
- 직접 만드는 게임 동작·캐릭터 애니메이션·물리·상호작용·카메라 추적 시연은 Unity에서 제작하고, 필요한 화살표·경로·라벨·단계 강조는 Motion Canvas에서 합성한다. 공간/렌더링 원리 설명도 Unity를 우선 사용하고, Three.js는 위 선택표의 이점이 있는 경우에만 채택한다. 순수 관계 도식은 대개 Motion Canvas 단독으로 간결하게 제작할 수 있다. 도트/스프라이트·상태 변화·기존 씬 재사용이 설명에 적합하면 Unity2D를 선택하고 Unity 안에서 필요한 선·라벨까지 구현해도 된다. 별도 Motion Canvas 합성은 이해나 편집 효율이 나아질 때만 추가한다. Unity와 Motion Canvas를 항상 함께 쓰거나 Unity 결과를 무조건 다시 꾸미는 의무는 없다.
- Unity 합성은 동일 카메라/해상도/fps의 프레임 번호·시간과 대상별 화면 좌표/가림 상태를 sidecar 데이터로 내보내고 Motion Canvas 타임라인에 연결한다. Unity viewport의 아래 원점과 화면의 위 원점을 변환하고 crop/확대 변환도 함께 적용한다. 화면 밖·뒤·가려진 대상의 표식은 의도에 따라 숨기거나 별도 표시하며, 고정 화면 좌표를 움직이는 대상 추적으로 가장하지 않는다. 실제 공간에서 가려져야 하는 선은 Unity 공간에서 렌더링한다.
- 기존 씬 설계에 `relationshipMeaning`, `sourceTargetAnchors`, `revealCue`, `arrivalCue`, `stateEncoding`, `traceData`, `clearAtCut`을 필요한 장면에 추가한다. 단순한 장면에 불필요한 항목이나 화살표를 강제하지 않는다. 실제 구현의 측정/실행 결과인지, 이해를 돕는 도식인지 표시한다.
- 기존 1920×1080 검정/흰색/따뜻한 노랑과 고정48px 자막 중심(960,970)을 유지한다. 쇼츠의 세로 비율·상단 대제목·형광색·검정 자막 박스를 우리 롱폼에 일괄 복사하지 않는다. 실제 자막으로 등장 중간/도착/상태 전환/컷 경계를 확인하고, 연결선이 대상 내부·핵심 UI·자막을 침범하지 않도록 시작·끝 여백을 둔다.

이 표현은 설명 분량이다. 기술 샘플과 최종 변경 구간의 동작·추적·가독성을 기존 검수 원장에 함께 기록하며 새 승인 단계나 다른 영상의 자동 재작업을 추가하지 않는다.

## 실제 영상 위 관찰 표식 — footage-focus-annotations-v1

2026-10-16 사용자 요청에 따라 실제 게임·개발 시연을 먼저 보고, 대사에서 짚는 **대상·표면·그림자 경계·조작 설정·변화 결과를 화면 위에 직접 표시**한다. 전체 화면의 원래 색과 속도를 유지한다. 모든 순간에 상자를 띄우는 대신, 관찰할 근거가 보이고 설명에 도움이 되는 순간을 고른다. 짧은 소개 몽타주나 격한 전투에서 핵심을 가리면 생략하고 이유를 기존 씬 계획에 기록한다.

같은 날 사용자 보강: **단순 원·네모에 제한하지 않는다.** 사람·물체를 따르는 자유 윤곽선, 열린 곡선, 표면 경계, 빛/이동 경로, 관계 연결선과 필요한 반투명 영역을 내용에 맞춰 그린다. 제공한 두 이미지의 관찰 요점은 대상 윤곽과 경로를 실제 화면에 맞춰 연결하는 방식이며, 그 영상의 자산·수치·알고리즘은 우리 측정값으로 가져오지 않는다. 반투명 면이 꼭 필요하면 관찰할 원래 밝기/질감을 가리지 않는 범위로 제한한다.

### 설명 성질에 맞는 도형·기즈모 — property-matched-gizmos-v1

2026-10-19 사용자 요청: **대상의 어떤 성질을 설명하는지에 맞춰 도형·기즈모를 선택한다.** 표식 자체를 보여 주기보다 대사에서 짚는 기준 상태→변한 조건→결과를 읽게 한다. 아래 표현을 모두 한꺼번에 넣거나 모든 물체에 회전 링을 붙이지 않는다. 관계 화살표의 점진적 등장·상태 변화 규칙도 같은 설계에 통합한다.

| 설명 성질 | 적합한 표식 | 구분할 의미 |
|---|---|---|
| 회전·자세 | 중심을 공유하는3축 회전 링, X/Y/Z 라벨, 활성 축의 진행호/방향 화살표 | 월드 축과 몸체/로컬 축, 어느 축으로 어느 방향으로 도는지. 필요한 축을 발화 순서로 강조하고 링의 투영·기울기와 앞뒤를 일관되게 유지 |
| 이동·진행 | 시작/끝점, 방향 화살표, 점진적으로 그리는 경로 | 위치 변화·이동 방향·바라보는 방향을 구분. 화면 궤적과 월드 경로를 혼동하지 않음 |
| 거리·크기 | 두 끝점을 잇는 치수선·보조선·범위 괄호 | 무엇 사이의 거리인지, 길이/폭/높이와 단위·스케일. 화면 간격을 검증되지 않은 게임 월드 미터값으로 바꾸지 않음 |
| 각도 | 꼭짓점·기준 두 방향·각도 호 | 기준 방향과 양의 방향, 화면 평면 각도와3D 각도를 구분 |
| 경계·표면 | 윤곽선·열린 곡선·빈 영역·필요한 최소 반투명 면 | 설명하는 경계/면을 따라가며 원래 조명·질감·충돌 결과를 가리지 않음 |
| 힘·속도 | 작용점과 방향 벡터, 필요한 속도/힘 라벨 | 힘과 속도를 다른 양으로 구별. 화살표 길이·수치는 근거 있는 스케일일 때만 측정값으로 제시하며 움직임만 보고 힘을 단정하지 않음 |
| 시야·카메라 | 시야 범위·부채꼴·카메라 절두체 등 투영에 맞는 도형 | 카메라 위치·방향·투영 방식과 관찰 영역. 모르는 실제 시야각은 설명용 모형으로 분리 |

- **좌표와 근거.** 기존 씬 계획에 대상의 설명 성질/선택 이유·모양/뜻, 월드/로컬/화면 좌표계, 축과 양의 회전 규약·단위·필요한 적용 순서, 원점/추적 앵커, 투영·크롭 변환과 가림을 기록한다. X=빨강·Y=초록·Z=파랑은 축 라벨을 붙여 사용할 수 있으며 기존 의미 있는 축 색을 유지한다. 그 빨강을 오류, 초록을 성공으로 함께 읽게 만들지 않는다. 회전 기즈모의 링/진행호는 실제 회전의 설명이고 무관한 스캔·펄스 장식은 아니다.
- **측정과 안내.** 검증한 엔진/실행 데이터·직접 측정·해설용 모형·화면 관찰 중 근거를 구분한다. 상용 게임 영상만으로 불확실한 내부 축·회전각·좌표·힘을 복원한 것처럼 주장하지 않는다. 확실한 근거가 없으면 화면에서 확인되는 방향/윤곽으로 제한하거나 `해설용` 모형임을 표시하고 실제 값 주장을 하지 않는다.3D 축이나 링을 편집 안내로 겹칠 때도 관찰로 확정할 수 없는 축/자세는 게임 내부값이 아님을 명확히 한다.
- **등장과 가림.** 기준과 이름을 먼저 보여 주고 발화에 맞춰 해당 축/경로/치수만 진행·강조한다. 검증한 앵커와 카메라/크롭을 따라가고 가림·화면 이탈·컷에서 지운다.3D에 속한 표식은 앞뒤 가림을 따르며, 가린 구조를 보여 주는 투시 해설이 필요하면 점선/설명용 표시로 실제 가시 부분과 구별한다. 고정 자막·게임 UI·출처와 핵심 대상/결과의 여백을 지키고 작은 화면에서 읽기 어렵다면 표식 수·크기·배치를 조정한다.
