# 화면·설명 렌더링 제작 규격

운영·승인·재검수 범위는 [통합 제작 규칙](VIDEO_WORKFLOW.md)만 따른다. 이 문서는 장면 설계 때 적용하는 화면 규격이다.

## 설명에 따른 렌더러 선택

2026-10-14 사용자 승인에 따라 **Unity를 게임 시연과 대부분의3D 원리 설명의 주력 도구**로 사용한다. **Unity는 적합한2D 설명에도 사용**하고 **Motion Canvas는2D 도식·합성, Manim은 수학, Three.js는 필요한 경우의 선택 도구**로 둔다. 2D라는 이유로 도구를 고정하지 않으며 도트/스프라이트 애니메이션·게임 상태·기존 씬 재사용이 설명에 유리하면 Unity를 선택한다. 게임 동작과 조명·그림자·투영·깊이 등 원리 설명을 도구별로 강제 분리하지 않고 같은 Unity 씬·자산·촬영 구성을 재사용한다. Three.js는 브라우저 상호작용이나 기존 씬 재사용 등 장면별 이점이 명확할 때 선택하고 `rendererReason`에 적는다. 동일 장면을 두 도구로 중복 제작하지 않는다. 2.5D를 기본 해법으로 강제하지 않고 나머지 설명은 목적에 맞춰 도구를 선택한다. 사용자가 특정 렌더러를 지정한 장면은 그 지시를 우선한다. 현재 `game-lighting-history-01` 수정본은 공간·조명·그림자를 Three.js로 구현하고, 각 설명에 더 명료한 도구가 있으면 에이전트가 판단해 채택한다. 나머지 편의 자동 재제작은 하지 않는다. 같은 날 사용자 지시로 Blender는 제작 도구에서 제외한다. 2026-10-20 사용자 지시 `unity-content-unreal-rendering-v1`: **콘텐츠(게임 시연·게임 디자인·게임 수학의 동작 설명)는 Unity, Unity에서 시연할 수 없는 렌더링 기술은 Unreal**로 제작한다. Lumen·Nanite·가상 섀도 맵·하드웨어 레이트레이싱·패스 트레이서처럼 UE 고유 기능이 있어야 실제로 보여 줄 수 있는 기법이 대상이며, 렌더링 주제라는 이유만으로 Unreal로 옮기지 않고 Unity 렌더 파이프라인으로 같은 원리를 실제 실행할 수 있으면 Unity를 유지한다. 추가한 Unreal 프로젝트는 `unreal/VideoEditing`(UE5.8, Third Person 템플릿, Blueprint)이다.

| 도구 | 적합한 설명 | 구현 기준 |
|---|---|---|
| Unity | **자체 제작 게임 시연과 대부분의3D 원리 설명의 주력 도구이며2D 설명에도 선택 가능**. 도트 캐릭터·아이템·타일맵·스프라이트 애니메이션·상태 변화, 3D 구조·좌표계·카메라 투영·법선·깊이/가림·렌더링 원리, 캐릭터 이동·점프·공격·애니메이션, 상점/인벤토리·상호작용, 물리/충돌, 카메라 추적·레벨 이동, 실제 엔진의 셰이더·조명/그림자 동작 | 실제 씬·컴포넌트·게임 규칙을 실행해 전 상태→행동→결과를 촬영. 예: 100골드에서 30골드 구매 성공, 20골드에서 구매 거절. 에디터/렌더 파이프라인 버전·조건을 기록하고 실행값과 교육용 표식을 구분 |
| Unreal — 렌더링 기술 전용 | **Unity에서 시연할 수 없는 렌더링 기술**: Lumen 전역 조명/반사, Nanite, 가상 섀도 맵, 하드웨어 레이트레이싱, 패스 트레이서, 그 밖의 UE 고유 렌더 기능과 같은 테스트베드에서의 기법별 전환 비교 | `unreal/VideoEditing`의 레벨과 레벨 시퀀스로 제작해 Movie Render Queue로 촬영. 엔진 버전, 레벨/시퀀스 경로, 기법마다 켜고 끈 기능·콘솔 변수, 캡처 해상도/fps를 설계표에 기록하고 실제 엔진 출력·버퍼 시각화와 해설용 모형을 구분. 게임 콘텐츠 시연은 Unity 유지 |
| Motion Canvas | 2D 흐름도·움직이는 화살표·분기/합류·상태 라벨·타임라인·자막·화면 합성 | 예: Unity 구매 동작 위에 조건→처리→결과 화살표와 잔액 표시. 실제 값 표시는 Unity 실행 데이터에 연결. 순수 관계 도식은 단독 제작하고 정보 등장 순서·가독성을 우선 |
| Three.js — 선택 | 브라우저에서 직접 조작하는3D 설명, 기존 Three.js 씬 재사용 등 채택 이점이 분명한 장면 | 예: 웹에서 카메라/광원을 직접 바꾸는 설명. 원리 설명이라는 이유만으로 Unity에서 전환하지 않음. 선택 이유를 기록하고 실제 구현 출력과 교육용 모형을 구분 |
| Manim | 수식 유도·계산, 벡터·기하·행렬 변환, 그래프와 수학적 변화 | 예: 내적 계산→밝기 값, 변환 행렬→좌표 변화. 기호와 공간 대상의 대응을 유지하고 계산 순서를 발화에 맞춰 표시. 필요한 경우 3D 기능 사용 |

씬의 기존 설계표에 `renderer`, `rendererReason`, `implementationKind`, 전 상태→조작→결과, 사용할 실제 출력/교육용 표식과 자막 여백을 기록한다. `implementationKind`는 `actual-implementation` 또는 `conceptual-illustration` 등으로 구분하고 같은 화면에 혼합되면 요소별로 적는다. 라이브러리 이름만 바꾸고 기존 평면 도형을 그대로 출력한 것을 실제3D 전환이라 하지 않는다. 하나의 설명에 도구를 섞을 때에도 좌표계·같은 대상·색·라벨·카메라 연결과 타이밍을 유지한다. 필요 없는 도구/의존성은 추가하지 않는다.

추가한 Unity 프로젝트는 `unity/VideoEditing`이며 기존 `unity/` 프로젝트는 보존한다. 선택된 영상의 설명에 적합하면 에이전트가 Unity 씬을 제작·촬영할 수 있고 씬마다 별도 승인을 요구하지 않는다. **이번에 임포트한 보유 라이브러리에서 설명에 적합한 도트/스프라이트·모델·리그·애니메이션을 먼저 찾아 재사용**하고, 맞는 자산이 없으면 권리를 확인한 다른 자산을 선택한다. 원본 URL·제작자·버전·라이선스와 필요한 표시 조건을 기록한다. 기존 자산이 설명에 맞지 않을 때 필요한 부분을 수정하거나 제작한다. 프로젝트·씬 경로, 에디터와 렌더 파이프라인/패키지 버전, 결과에 영향을 주는 광원·카메라·물리 조건, 캡처 해상도/fps와 프레임/내레이션 대응을 기존 설계표에 기록한다. 씬·프리팹·스크립트로 독립 편집 가능하게 구성하고 실제 최종 자막 공간을 확보한다. 자체 제작 Unity 화면은 실제 엔진 구현이어도 **설명 분량**이며 독립 확보한 상용 게임 플레이로 계산하지 않는다. 소스와 `.meta`·패키지 잠금·프로젝트 설정은 [미디어/Git 규격](MEDIA_STORAGE.md)에 따라 보존하고 캐시·빌드·녹화 결과는 Git에서 제외한다.

**보유 에셋의 장면별 활용 — `imported-unity-assets-contextual-reuse-v1`(2026-10-20).** [에셋 목록](../shared/assets/unity-asset-library.json)과 [사용 안내](UNITY_ASSET_LIBRARY.md)를 먼저 확인하고 `Assets/ThirdParty/YamyamAssetLibrary`에서 대본의 대상·행동·전후 결과를 잘 보여 주는 캐릭터·소품·환경·스프라이트·리그·애니메이션을 고른다. 보유한 유료/무료 자산 모두 개별 사용 조건이 기준이며 임포트 완료를 영상 사용 허가로 간주하지 않는다. 자산 수나 특정 그림체를 강제하지 않고 불필요한 다운로드·무관한 장식보다 이해와 얌얌코딩의 가독성을 우선한다.

- 기존 씬 계획의 `assetRecords`에 라이브러리 제품 ID, 실제 에셋 경로/GUID, 원본 URL·제작자·버전/해시·라이선스·필요 표시 문구와 알려진 제한을 연결하고 `sharedAssetPaths`에 공용 참조를 남긴다. 같은 파일을 씬별로 복제하지 않는다.
- 선택한 프리팹·재질·스프라이트·리그/애니메이션이 해당 Unity/URP 장면에서 실제로 필요한 동작을 하는지 기존 대표 샘플과 최종 검수에서 확인한다. 라이브러리의 임포트/정적 대표 이미지 검수는 전체 애니메이션·모든 데모 씬·누락된 공급 리소스의 검증이 아니다. 해당 사용 범위만 확인하고 알려진 누락을 추측한 자산으로 복구했다고 표시하지 않는다.
- 공급 원본과 공용 프리팹은 보존하고 필요한 크기·색·동작 변경은 씬 인스턴스·프리팹 변형 또는 출처를 연결한 파생 파일에 둔다. 실제1080p·375px에서 대상 식별·실루엣·동작·자막 여백과 브랜드 역할 색을 확인한다. 파일·재배포는 기존 미디어/Git 규격을 따르며 자산 원본을 Git에 추가하지 않는다. 필요한 크레딧은 기존 게시 규칙에 따라 KO/EN 더보기 맨 아래에 모으고, 영상 내 의무 표시 조건과 충돌하면 조건에 맞는 대체 자료를 고른다.

선택한 Unity 장면과 이후 명시 선택 영상에 적용한다. 어울리지 않는 장면에 사용을 강제하거나 완성/미선택 영상을 자동 수정하지 않으며 도구 선택·실제/설명 분량·중간 승인 규칙은 그대로 유지한다.

**Unity2D 자산과 씬 저장.** 필요한 설명에 맞는 도트 자산을 찾아 캐릭터 동작·아이템 식별·그림체·색 의미·자막 대비를 확인한다. 이미 보유한 적합한 자산은 재사용하며 모든 설명에 도트 스타일을 강제하지 않는다. 원본 URL·제작자·버전/리비전·라이선스·출처 표시 조건·원본 해시와 원본 자산의 Git 재배포 가능 여부를 기록한다. 픽셀 밀도·스케일·카메라 크기를 맞추고 필요하면 Point 필터와 정수 배율을 사용해 의도하지 않은 번짐/떨림을 방지한다. 적용한 PPU·필터·압축·카메라/Pixel Perfect 설정은 결과에 관련된 것만 설계표에 남기며 모든 씬에 특정 설정을 강제하지 않는다.

Unity로 제작한 대본 씬마다 독립 편집 가능한 `.unity` 파일을 저장한다. 새 구성의 권장 위치는 `Assets/VideoScenes/<slug>/<scene-id>.unity`이며 기존 샘플·승인 씬을 이름만 맞추려고 옮기지 않는다. 같은 캐릭터·타일셋·프리팹·AnimationClip/Animator·스크립트·머티리얼은 공유 참조로 재사용하고 씬별로 필요한 시작 상태·동작·끝 상태·촬영 설정을 저장한다. 스프라이트 시트·분할/import 설정과 대응 `.meta`도 보존하되 이미지 등록과 라이선스는 미디어 규격을 따른다. 기존 설계표에 `assetRecords`, `sharedAssetPaths`, `sceneSaveStatus`와 실제 `scenePath`를 연결해 계획/저장을 구분한다. 장면별 파일 분리는 편집과 재사용을 위한 것이며 챕터마다 연출을 끊는 기준이 아니다.

같은 3D 장면에서 전체 공간→관찰할 면/픽셀→변경할 한 조건→계산 중간값→화면 결과의 순서로 설계한다. 광원 시점과 관찰자 시점은 이름과 위치를 구분한다. 카메라를 계속 회전시켜 정보를 늘리지 말고 관계를 보여 준 뒤 고정한다. 임의의 광선이나 색칠한 칸은 교육용 표식이며 실제 깊이 버퍼/측정 결과로 부르지 않는다. 짧은 대표 동작으로 공간·가림·글씨·실제 자막을 먼저 확인한 뒤 같은 체계를 전체 장면에 적용한다.

## 팔레트와 글자

신규 설명은 `research-black-v1` / `motion-canvas/src/styles/research-dark.ts`를 사용한다. 이미 승인된 흰 프로젝트는 `research-paper.ts`를 보존한다. 명시 수정된 `game-lighting-history-01`~`04`는 검정이다. 실제 게임·브랜딩·회원 엔딩·썸네일을 함께 검게 바꾸지 않는다.

빨강·초록 등 추가 색은 역할·라벨을 정해 사용한다. 색만으로 의미를 구분하지 않는다. 1920×1080 좌우 안전 여백96px, 제목48–56px, 핵심 라벨32–40px, 보조26–30px가 시작값이다. 영어Segoe UI, 한글Malgun Gothic, 수식Cambria Math, 코드Consolas 또는 승인 폰트를 사용한다. 실제 폰트로 폭을 측정한다. 하단 고정 자막의 박스와 그림자 공간을 먼저 예약하고 요약 띠·수식은 그 위에 놓는다. 이전 흰 레이아웃의 y405 요약 띠를 그대로 복사하지 않는다.

### 일반 설명과 코드의 의미 색 — semantic-text-code-colors-v1

2026-10-19 사용자 요청에 따라 소스코드를 한 색의 일반 문장처럼 출력하지 않는다. 검정 설명 배경·흰 본문·따뜻한 노란 제목은 유지하면서, 기존 브랜드 토큰에 문법/설명 역할을 연결한다. 승인된 흰 팔레트는 유지하고 그 배경에서 대비가 맞는 대응 토큰을 사용한다. 다른 편집기의 원색 테마나 예시 화면 색을 그대로 복사하지 않는다.

| 영역 | 구분할 역할 | 적용 기준 |
|---|---|---|

### 1. 한 장면·한 모델 테스트베드

- 기법 비교 영상은 **영상 전체에서 같은 장면·같은 카메라 구도·같은 대상 하나**를 기준으로 삼고 기법이 바뀔 때 그 장면만 다시 렌더한다. 예: 같은 골목에 라이트맵→섀도 맵→캐스케이드 섀도 맵→디퍼드→SSAO→SSR→레이트레이싱→패스 트레이싱을 순서대로 적용. 시청자는 달라진 것만 비교한다.
- 시스템 설명은 **한 모델**(예: 메인보드·메모리·확장 카드·케이블·마우스가 있는 저폴리 PC)을 공간에 두고 카메라가 설명 대상 부위로 이동한다. 각 부위에 이름표를 붙이고 다른 부위로 갈 때 모델을 교체하지 않는다. 사람·물건의 식별 세부 규칙은 아래 절을 따른다.

| 비교 격자 | 같은 장면2×2 또는 좌우 | 타일마다 기법 이름, 마무리 요약에 사용 |

카드가 나타날 때3D 세계는 어둡게 남긴다. 검정으로 완전히 교체하지 않는다. 카드 폭은1570px 이하, 자막 박스와 그림자 영역을 침범하지 않는다. 카드도 `explanation-visual-evidence-v1`의 `visualEvidence` 기록 대상이다.

### 6. 연속 공간과 전환

- 같은 공간 안 카메라 이동·줌·크로스페이드를 기본으로 한다. 하드컷은 같은 구도에서 기법을 바꾸는 A→B 비교에 쓴다.
- 데이터 이동은 경로를 따라 움직이는 점(케이블 위 점 등)으로 보여 주고 방향·순서를 발화에 맞춘다.
- 챕터 경계에 음악·타이틀·검정 화면 리셋을 넣지 않는 기존 규칙을 따른다.

### 7. 개론과 마무리

- 브랜딩2초 뒤 첫 화면은 주인공 장면과 최종 결과/대비다. 예: 완성 조명 장면을 보여 준 뒤 “처음에는 숫자 하나였어요”로 되감기. 개론2–4문장은 그 위에서 말하며 PPT 제목으로 시작하지 않는다.
- 마무리는 비교 격자 → 가져갈 판단 한 문장 → 회원 엔딩 순서다.

### 8. 쇼츠 적용

- 상단 고정 주장 문장1–2줄(흰색, 핵심어 `title` 노랑), 중앙 시연, 하단 자막 띠. 16:9/1:1 소스는 검정 띠 레이아웃, 9:16 소스는 전면 배치에 같은 위계를 적용한다.
- 대상에 붙는 단계 목록 칩: 제목 + 2–4단계, 현재 단계 `title`, 완료 ✓, 대기 `ink`. 캐릭터가 그 단계를 수행하는 동안 강조를 옮긴다.
- 같은 위치 상/하 분할 A/B에 각 쪽 라벨(문제 `red`/해결 `green`)과 측정 칩(예: `표적에 닿은 적8`, `서로 미는 양23.5 m/s`)을 둔다. 측정값은 **우리 구현**에서 읽은 값만 쓰고 `우리 구현`을 표시한다.
- 구독 요청 카드·채널명 표시·화면 내 출처 줄은 복제하지 않는다. 출처는 설명란 하단에 둔다. 고양이 리액션·세로 검수 규칙은 통합 규칙9절을 따른다.

### 설계와 검수

기존 씬 설계에 `testbedScene`, `termChip`(term/en/meaning/sourceKind/enterCue/exitCue), `pictureLabel`, `onSceneNumbers`, `evidenceCards`(kind/source), `recapGrid`를 필요한 장면에만 기록한다. 실제 자막을 합성한1080p와375px 움직임에서 칩 교체 타이밍, 라벨·수치·카드·자막의 충돌, 카드 뒤 세계 유지, 분할 A/B의 읽기 시간을 확인한다. 현재 선택 수정과 향후 명시 선택 영상·쇼츠에 적용하며 미선택 영상의 자동 재제작이나 새 승인 단계는 만들지 않는다.

### 1. 현상→원리→확인의 교대 구조

참고 쇼츠 한 편(파괴 연출, 약78초)의 실측 전개다. 롱폼 게임디자인의 각 챕터와 콘텐츠 쇼츠는 이 단위를 기본 리듬으로 삼는다.

| 구간 | 화면 | 역할 |
|---|---|---|
| 0–4초 | 실제 게임(게임명 칩) + 가리킬 대상 하나 | 플레이어가 보는 **현상** |
| 2초 | 짧은 반전 라벨 + 리액션 1초 | “사실은 눈속임” 같은 문제 제기. 큰 도장 대신 우리 토큰의 짧은 라벨과 고양이 리액션 |
| 7–17초 | 도식: 멀쩡한 사각형 → 미리 그린 균열 → 교체 | **원리**를 한 변수씩. 도식은 대상 하나·변화 하나 |
| 18–23초 | 실제 게임1 | 방금 말한 원리를 **확인**: “항상 같은 모양으로 무너진다” |
| 24–34초 | 도식: 충격 자국을 붙이고 → “이걸 데칼이라고 합니다” | 세부 기법 뒤에 **정식 명칭** |
| 35–41초 | 실제 게임2(닌텐도, 초록 원) | 명칭을 쓴 첫 확인 |
| 42–60초 | 도식 변형 → 실제 게임3, 도식 변형2 → 실제 게임4 | 같은 문제의 **다른 해법**을 장르가 다른 게임으로 |
| 61–73초 | 심화 도식(연결 노드·힘) → 실제 게임5의 디버그 화면 | 전문 깊이까지 올라간 뒤 실제 근거 |
| 74–78초 | 실제 게임 + 리액션 + “…을 제작한다고 하네요” | **마무리**: 개발사의 실제 선택 한 문장 |

- 도식과 실제 게임을 **5–10초 단위로 교대**한다. 원리 주장 하나에는 반드시 그 주장을 보여 주는 실제 게임 컷이 따라오고, 게임 하나는 주장 하나를 맡는다. 같은 게임을 여러 주장에 돌려쓰지 않는다.
- 쇼츠는 한 편이 이 단위 하나, 롱폼 게임디자인은 원본 참고의 챕터마다 이 단위를 적용하되 원본 순서·사례 역할을 유지한다. 컷은3–5초, 자막은 한 절(`caption-clause-keyword-v1`).
- 마무리는 교훈 요약이 아니라 **개발사의 실제 선택**(어떤 게임이 어떤 방식을 택했는지)으로 닫고 과장하지 않는다. 13편 실측: 길이46–79초(평균 약59초), 헤드라인은 편 전체에 하나로 고정, 정식 명칭 문장(“…이라고 합니다”)은 편당1–3회, 그 기법이 화면에 보인 직후에만 나오며(총18개 용어), 12편이 “…한다고 하네요”형 개발사 실제 관행 문장으로 끝나고 마지막 화면은 실제 게임이다. 우리도 편당 명칭 수를 기법 수에 맞추고 마지막 컷을 실제 게임(또는 자체 무대의 최종 결과)으로 둔다.

### 2. ‘플레이어 화면 | 실제 구조’ 나란히 보기

- 빌보드·창문 내부·거울·문 크기·카메라처럼 **보이는 것과 실제 구조가 다른** 주제는 왼쪽에 플레이어 카메라 화면, 오른쪽에 같은 순간을 바깥에서 본 구조(와이어프레임·카메라 절두체·복제된 방·마네킹 치수)를 같은 시간축으로 나란히 둔다. 한쪽만 움직이게 하지 않는다.
- Unity에서는 같은 씬을 플레이어 카메라와 관찰 카메라 두 대로 동시에 촬영하고, 관찰 카메라에만 절두체·법선·경계 기즈모를 켠다(`property-matched-gizmos-v1`). 상용 게임의 디버그 화면은 독립 확보한 녹화나 공식 개발 자료에서만 쓰고 ‘현재 화면’ 라벨로 출처 종류를 적는다.
- 전/후 비교(노멀 맵 켬/끔, 빌보드 켬/끔)는 같은 구도에서 한 조건만 바꿔 좌우 또는 교대로 보여 준다.

- **도식이 기법을 실제로 수행한다.** 참고 영상은 롤백 넷코드를 두 화면 재생으로(#8), 랙 컴펜세이션을 과거→현재 바와 잔상으로(#9), 카메라 보간을 실시간 수치로(#10), 히트 스톱을 도식 자체의 세피아 정지로(#13) 보여 준다. 정지 그림에 화살표만 얹지 말고 설명 무대 안에서 그 메커니즘을 구현해 돌린다. `implementationKind`는 `actual-implementation`(무대 안 구현)과 `conceptual-illustration`을 구분한다.
- **같은 시간축 좌우 화면.** 지연·동기화처럼 두 관찰자가 다른 것을 보는 주제는 파란 테두리=나, 빨간 테두리=상대처럼 색 테두리와 글자 라벨을 함께 붙인 두 화면을 같은 시간으로 재생한다.
- **시간 되감기.** 과거→현재 바, 반투명 잔상(과거 위치), 현재 위치 강조로 표현하고 각 잔상에 시점 라벨을 붙인다.
- 마네킹·소품·픽셀 캐릭터는 출처·해시·변형을 기록하고 큐브·막대 대체물 금지 규칙은 그대로다. 사물은 사각형/다각형 윤곽으로 단순화하되 설명에 필요한 구조(균열선·조각·연결 노드)는 그린다. 색은 `teal`=기준/대상, `red`=변화·파손·문제, `green`=결과/확인, `title`=현재 초점으로 고정하고 라벨을 함께 쓴다.
- 도식 한 장면에 변하는 것은 하나다. 키가 커지면 문·의자·캡슐이 차례로 어긋나는 식으로 **같은 원인의 결과를 소품별로 이어** 보여 준다.
- 얌얌코딩 고양이는 참고 영상의 마스코트처럼 도식 안의 **플레이어 대역**(총을 든 ‘나’, 서버 앞의 ‘나’)으로 쓸 수 있다. 리액션과 대역을 한 장면에서 겹치지 않게 하고 대역일 때는 표정보다 위치·행동이 읽히게 한다.

### 4. 실제 게임 컷의 표식과 표기

- 게임명은 왼쪽 위 작은 칩으로 컷마다 표시한다(내용 식별용; 출처·권리는 설명란). 초록 원=지금 볼 대상, 빨강 원=문제/버그, 화살표=시선 안내, 치수선=확인된 크기. 모르는 값은 `?`로 비우거나 `해설용`을 붙이고 영상만 보고 내부 값을 단정하지 않는다.
- 게임 컷은 그 주장에 필요한3–6초만 쓰고 가리킬 대상이 화면에 있는 구간을 고른다. 독립 확보·FHD·권리 규칙은 그대로다.
- 참고 영상의 영화 장면·밈 GIF·실사 격투 영상 같은 제3자 클립은 채택하지 않는다(13편 중9편에서 반전·반응 비트로 사용됨). 그 자리는 고양이 리액션이나 반전 라벨이 맡는다.

### 5. 세로 쇼츠 레이아웃

- 상단 헤드라인은 제목 그대로(핵심어 `title`), 중앙 시연, 하단 자막 띠. 세로 쇼츠에서는 ‘플레이어 화면 | 실제 구조’를 상/하로 쌓고, 자체 도식 씬(픽셀 과일·기사 등)은 Unity2D로 만든다.
- 고양이 리액션은 반전·원리 지시·마무리 등 필요한 3–6곳에만 두고 통합 규칙9절의 크기·배치를 따른다.

### 설계와 검수

기존 씬 설계에 `contentBeats`(phenomenon / reveal / principle / confirm / naming / variant / depth / closing), 각 비트의 게임명·주장·표식, `sideBySide`(playerView / structureView / sharedTimeline), `diagramStage`(3d-dark / 2d-pixel / math-board와 실제 씬 경로), 마네킹·소품·픽셀 캐릭터 자산 경로를 기록한다. 실제 자막을 합성한1080p와375px에서 교대 리듬의 읽기 시간, 좌우/상하 동기, 칩·원·치수의 가림을 확인한다. 현재 선택 수정과 향후 명시 선택 게임디자인 영상·콘텐츠 쇼츠에 적용하며 미선택 영상의 자동 재제작이나 새 승인 단계는 만들지 않는다.

## 상세 대상과 실제 공간 표현

- 사람: 머리·얼굴 또는 장비, 몸통·의복, 어깨/팔꿈치/무릎 등 관절, 손발, 대사와 맞는 자세·행동을 알아볼 수 있게 제작한다.
- 물건: 비례·윤곽과 특징적 구조/작동부를 그린다. 자전거의 프레임/바퀴/핸들/페달, 항공기의 동체/조종석/주익/꼬리처럼 동작을 이해하는 세부를 포함한다.
- 같은 대상을 연결되는 씬에서 재사용하고 투영·앞뒤 가림·면·높이·관절 동작을 일관되게 유지한다. 사람/탈것이라는 이름만 붙인 큐브·막대 아이콘은 대체물이 아니다. 큐브/경계상자/행렬칸 자체를 설명할 때는 추상 도형이 적합하다.
- 카드에 그림자만 준 장식을 공간 설명으로 대체하지 않는다. 필요한 투영·공간 관계·가림과 내레이션에 맞는 이동/회전/비교가 보여야 한다. 2D가 더 명료하면2D를 쓰고 실제 깊이가 필요하면3D를 쓴다. 과도한 장식·네온·빛번짐보다 대상과 수식의 대비를 우선한다.
- 장면별 실제 대상/식별 세부/관절·작동부/시작·끝 상태/대사별 움직임/같은 대상의 연결/자막 공간을 제작 전에 적는다. 선택한 도구에서 독립 편집 가능한 씬과 자산을 사용한다. 편집 가능한 씬의 경계가 시청자의 설명 흐름을 끊지 않도록 전 장면의 대상·상태·라벨·화살표 도착점을 다음 장면의 출발점으로 이어받는다. 다른 자료로 전환할 때도 같은 질문이나 관찰 대상을 먼저 연결하며 서로 다른 출처/실행 상태를 같은 연속 촬영처럼 오인시키지 않는다. 씬마다 타이틀 카드·검정 화면·음악 페이드를 반복하지 않고 의미 있는 쉼만 계획한다. 내레이션의 끝·첫 문단과 화면/소리의 연결을 기존 씬 설계의 `transitionToNext`에 기록한다. Three.js·Motion Canvas·Manim·Unity 출력을 합성할 때도 동일 팔레트·타이밍과 실제 자막을 따른다.

## 실제 게임 위의 해설

### 설명 순서에 맞춘 움직이는 연결선과 경로

2026-10-14 사용자가 제시한 저세상개발자 쇼츠의 **점진적으로 연결되는 화살표, 현재 경로 강조, 상태 변화와 실제 시연의 연결**을 선택된 영상의 설명 문법으로 활용한다. 참고 분석과 관찰 범위는 `shared/publishing/animated-explanation-reference.json`에 기록한다. 원본의 그림·게임 컷·자막·템플릿을 제작 자산으로 복사하지 않고 우리 내용과 권리 확인 자산으로 구현한다. 원 제작자의 Unity/Motion Canvas 사용 여부는 확인되지 않았으며, 도구 추정과 화면 관찰을 구분한다.

- 먼저 대상과 기준점을 보여 주고, 내레이션이 관계를 설명할 때 **출발점 강조 → 선이 목적지까지 그려짐 → 도착점 반응 → 결과를 읽을 시간** 순서로 진행한다. 이동하는 점은 진행 위치, 화살촉은 방향, 점선은 미실행/조건부 관계처럼 의미를 정한다. 반복 흐름이 실제로 설명되는 경우에만 반복한다.
- 현재 설명하는 주 경로 하나를 우선 강조한다. 나머지 경로는 알아볼 수 있을 정도로 낮추고, 미확인·잠김·통과·실패를 글자/형태로도 구별한다. 기본 팔레트에서 노랑은 현재 초점, 청록은 확인된 경로, 회색은 대기, 빨강은 실패에 사용하되 기존 장면의 의미 있는 색 약속을 우선한다. 색이나 발광만으로 상태를 전달하지 않는다.
- 선형 진행, 분기 선택, 반복/되돌림, 합류처럼 설명할 관계에 맞춰 배치한다. 구조가 바뀌면 대상의 이름·아이콘·색을 유지하고 변화 전후를 비교할 시간을 둔다. 화살표마다 이동/의존/시선/데이터 전달 중 의미를 정하고 서로 다른 의미를 한 선에 섞지 않는다.
- 선 그리기 약0.35–0.8초와 도착 반응 약0.2–0.5초는 시안의 시작값이다. 실제 발화와 읽기 시간으로 조정하며 참조 영상의 실측값이나 고정 규칙으로 취급하지 않는다. 의미 없는 흔들림, 상시 펄스, 과한 바운스·발광으로 주의를 분산시키지 않는다.
- 직접 만드는 게임 동작·캐릭터 애니메이션·물리·상호작용·카메라 추적 시연은 Unity에서 제작하고, 필요한 화살표·경로·라벨·단계 강조는 Motion Canvas에서 합성한다. 공간/렌더링 원리 설명도 Unity를 우선 사용하고, Three.js는 위 선택표의 이점이 있는 경우에만 채택한다. 순수 관계 도식은 대개 Motion Canvas 단독으로 간결하게 제작할 수 있다. 도트/스프라이트·상태 변화·기존 씬 재사용이 설명에 적합하면 Unity2D를 선택하고 Unity 안에서 필요한 선·라벨까지 구현해도 된다. 별도 Motion Canvas 합성은 이해나 편집 효율이 나아질 때만 추가한다. Unity와 Motion Canvas를 항상 함께 쓰거나 Unity 결과를 무조건 다시 꾸미는 의무는 없다.
- Unity 합성은 동일 카메라/해상도/fps의 프레임 번호·시간과 대상별 화면 좌표/가림 상태를 sidecar 데이터로 내보내고 Motion Canvas 타임라인에 연결한다. Unity viewport의 아래 원점과 화면의 위 원점을 변환하고 crop/확대 변환도 함께 적용한다. 화면 밖·뒤·가려진 대상의 표식은 의도에 따라 숨기거나 별도 표시하며, 고정 화면 좌표를 움직이는 대상 추적으로 가장하지 않는다. 실제 공간에서 가려져야 하는 선은 Unity 공간에서 렌더링한다.
- 기존 씬 설계에 `relationshipMeaning`, `sourceTargetAnchors`, `revealCue`, `arrivalCue`, `stateEncoding`, `traceData`, `clearAtCut`을 필요한 장면에 추가한다. 단순한 장면에 불필요한 항목이나 화살표를 강제하지 않는다. 실제 구현의 측정/실행 결과인지, 이해를 돕는 도식인지 표시한다.
- 기존 1920×1080 검정/흰색/따뜻한 노랑과 고정48px 자막 중심(960,970)을 유지한다. 쇼츠의 세로 비율·상단 대제목·형광색·검정 자막 박스를 우리 롱폼에 일괄 복사하지 않는다. 실제 자막으로 등장 중간/도착/상태 전환/컷 경계를 확인하고, 연결선이 대상 내부·핵심 UI·자막을 침범하지 않도록 시작·끝 여백을 둔다.

이 표현은 설명 분량이다. 기술 샘플과 최종 변경 구간의 동작·추적·가독성을 기존 검수 원장에 함께 기록하며 새 승인 단계나 다른 영상의 자동 재작업을 추가하지 않는다.

## 영상 위 그림 애니메이션 — drawn-over-footage-explanation-v1

2026-10-20 사용자 지시 “이런 실제 파악 영상은 설명 비율 6:4 안 맞춰도 돼. 영상 만들고 영상 위에 그림 애니메이션 그려서 설명해줘도 좋아”. 플랫폼 행사·상점 규칙·집계 숫자·도구 동작을 직접 확인하는 **실제 파악 영상**(`reality-check-no-ratio-v1`)에서는 직접 녹화한 화면이 곧 영상이고, 설명은 별도 PPT 대신 **그 화면 위에 손으로 그리듯 나타나는 그림**으로 한다. 다른 종류의 영상에서도 카드보다 그림이 더 잘 설명하는 장면에 선택할 수 있다.

- **무엇을 그리나.** 실제 대상에 붙는 밑줄·원·화살표, 단순 픽토그램(복권, 체, 별, 돋보기), 눈금·막대·카운터, 두 상태를 잇는 선. 획이 발화 순서대로 그려지고(0.3–0.8초 시작값) 잠시 머문 뒤 지워진다. 1080p 선 8–12px, 라벨 36–44px. 색 역할은 기존 토큰(노랑=현재 초점, 청록=관계/기준, 빨강=문제, 초록=결과)과 같고 라벨을 함께 쓴다.
