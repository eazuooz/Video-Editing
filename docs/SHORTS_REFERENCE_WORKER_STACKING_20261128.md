2. **한 줄 질문과 마지막 답을 먼저 정한다.** 처음 보여 줄 현상과 마지막에 되돌려 줄 답이 같은 대상에 관한 것인지 확인한다.
3. **원문에서 인과를 확인한다.** `문제 → 문제의 원인 → 개발 제약 → 선택한 방법 → 관찰 결과`를 적는다. 개발자 직접 설명, 일반 원리, 실제 화면 관찰을 구분한다. 자료에 없는 출시 압박·성능 이유·의도를 채우지 않는다.
4. **대본보다 먼저 동작표를 만든다.** 비트마다 `보여 줄 대상 / 시작 상태 / 조작 / 변화 / 보이는 결과 / 이어질 질문`을 적는다. 실제 화면이 그 문장을 증명하는지 확인한다.
5. **같은 Unity 무대에서 실패와 해결을 만든다.** 기존 공용 에셋을 사용하고 캐릭터의 걷기·시전·공격·접지를 구현한다. 대상·동작·시점을 유지한 채 설명할 변수만 바꾼다. 동작 없이 라벨만 교체하는 컷은 원리 시연으로 완료 처리하지 않는다.
6. **자연스러운 인과 문장으로 대본을 쓴다.** ‘왜냐하면 / 그런데 / 그래서 / 바꾸면 / 실제로 확인하면’의 관계가 끊기지 않게 한다. 이 접속어를 의무적으로 반복하라는 뜻은 아니다. 쉬운 예시 뒤에 용어를 붙인다.
7. **원래 목소리로 녹음하고 실제 단어 경계에 맞춘다.** 네 문단·네 컷을 필수 형식으로 고정하지 않는다. 필요한 비트 수에 맞게 음성을 유지하거나 다시 녹음한다. 화면을 기다리는 불필요한 무음, 문장 끝을 덮는 전환을 만들지 않는다.
8. **질문→문제→제약→해결→확인 실험→실제 응용→답의 순서로 편집한다.** 해당 자료에 없는 비트는 거짓으로 채우지 않고 가장 짧은 정직한 설명으로 연결한다. 총 비율은 맞추되 한 쌍씩 같은 길이를 강제하지 않는다.
9. **자막·강조·음악을 후반에 맞춘다.** 기존 얌얌 목소리·브랜딩·고양이·저작권 확인 음악을 쓴다. 강조는 조작/원인/결과 하나씩, 음악은 발화를 돕는 수준으로 덕킹한다. 참고 파일의 +0.17dBTP를 목표로 복제하지 않고 우리 음량·피크 기준을 지킨다.
